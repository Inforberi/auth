# Правила работы с проектом

## Читаемость и качество кода

Эти правила действуют для всех следующих изменений, а не только для этапа рефакторинга. Пишем для разработчика, который будет поддерживать проект.

- Сразу делать код читаемым, корректным и безопасным. Не оставлять смешение обязанностей и дублирование с расчётом на отдельную будущую уборку. Если для качественного решения нужно больше времени или токенов — это допустимо; экономия не должна ухудшать результат. Не усложнять решение без необходимости.
- Не повторять одну предметную проверку в HTTP и service. HTTP проверяет формат запроса, service один раз применяет правила domain, mapper переводит результат в HTTP-ответ. Повторная проверка допустима только для другой гарантии (например, актуальности данных внутри транзакции), а не «на всякий случай». Сохранять порядок валидации и обращения к зависимостям явно.
- Production-качество означает подтверждённую пользу для корректности, безопасности, производительности или поддержки, а не максимум кода и проверок. Выбирать простейшее достаточное решение. Для дополнительного слоя, обёртки, повторной проверки, запроса к зависимости или абстракции должно быть понятно, какую конкретную проблему оно решает; не добавлять их ради симметрии, гипотетического будущего или пометки «production».
- Перед добавлением нового механизма проверить, нет ли подходящего существующего. Перед удалением похожих проверок сравнить их гарантии, публичные ошибки и порядок выполнения: SQL constraints, проверку актуальности внутри транзакции, resource bounds и fail-closed не удалять как «дубли». Если польза спорная — сначала разобрать сценарий и зафиксировать решение, не наращивать код автоматически.
- Сохранять согласованное дерево из `docs/architecture.md`. Разделять файлы по самостоятельным сценариям и ответственности, не по каждой функции или типу. Связанные части держать рядом, искусственно разнесённые — объединять.
- Независимые HTTP-ручки держать в файлах своих сценариев вместе с request DTO и Swagger. Общие Handler/constructor/response размещать рядом в общем файле фичи. Не смешивать HTTP, бизнес-правила, SQL и сборку зависимостей.
- Использовать общий механизм HTTP-ошибок с локальными правилами фич, предусмотренный этапом 5.2h. Не размножать одинаковые switches и не создавать глобальный каталог ошибок всех модулей. Валидация, публичный контракт и безопасное логирование должны оставаться явными.
- Около 150 строк — ориентир для рукописного Go-файла, если разделение имеет смысл. Не разрывать связную операцию, не уплотнять код и не создавать `part1`/`part2` ради лимита. Тесты и generated-файлы не ограничивать по длине.
- Давать понятные имена; название файла должно отражать его сценарий или ответственность. Input/result сценария держать рядом с ним в service, предметные модели и правила — в domain, JSON DTO — в transport; не собирать разные контракты в общий results.go. Комментарии оставлять для причин, ограничений и нетривиальных гарантий, а не пересказа кода. Не создавать пустые пакеты, универсальные абстракции и файлы-заглушки ради симметрии.
- Перед завершением проверять читаемость изменённого кода и выполнять содержательные проверки по затронутому риску. Не добавлять лишние скрипты и не повторять весь набор проверок без причины. Непроверенное явно отмечать.

## Границы изменений

- Следовать `docs/auth-plan.md` и `docs/auth-implementation.md`; фиксировать фактический результат подэтапа. Запрос только на план или анализ не разрешает реализацию кода.
- Сохранять пользовательские изменения и состояние staging. Коммит выполнять только по запросу.
- Рефакторинг не должен незаметно менять API, безопасность, роль Redis или транзакционные гарантии. Не сбрасывать рабочую БД и не менять secrets без явного разрешения.
