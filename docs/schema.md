# Схема Auth

A5.2d-local: `auth.email_bindings` — один pending/target с approved email (без преждевременного user_emails reservation), approver/session binding, auth_version, keyed code verifier, TTL до пяти минут, code attempts и inline encrypted delivery job/lease/attempts. Expiry/due indexes обслуживают bounded retention/fair delivery. Completion создаёт verified contact по UNIQUE, повышает version, отзывает sessions и pending challenges, сохраняет existing factor; email_verification_audit расширен nullable actor/version для binding events с SQL constraints. Новый migration file не добавлялся: расширены исходные up/down. [Контракт](features/email-binding.md).

A5.2c-local: sessions хранят nullable email_reauthenticated_at/email_reauthenticated_id как snapshot подтверждения; MFA management повторно проверяет актуальные ownership/verification/version. Email challenges получили purpose login/reauthenticate и session_hash для protected flow, с SQL constraint против смешения. Code consume/session rotation/proof/email audit атомарны, lifetime/password/MFA proof не продлеваются. Existing outbox/retention/индексы переиспользованы; новых таблиц или migration files нет. [Контракт](features/mfa.md#подтверждение-управления-mfa-по-почте-a52c-local).

A5.2b-local: MFA enrollment хранит purpose enroll/replace; новые audit events покрывают step-up/replace/disable/recovery regeneration. Session MFA timestamp допускается после created_at для step-up, но после primary proof и до absolute deadline; primary/password/MFA proofs не обновляются простым refresh. Management атомарно повышает auth_version, отзывает sessions и удаляет pending MFA challenges. Source 000001 изменена без отдельной миграции; существующей БД нужен согласованный upgrade, не reset. [Публичный MFA API](features/mfa.md).

Источник: `migrations/000001_init` (up/down). Один экземпляр Auth обслуживает один проект; внутренний UUID пользователя не зависит от метода входа.

Оптимизация 6.8a: expiry indexes challenges/outbox, partial exhausted-job indexes; email_changes index совпадает с GREATEST(protect_until,recovery_expires_at). Retention/candidate cutoffs используют statement_timestamp, consumption/lease сохраняют текущие часы. Claim не запускает global cleanup; indexed bounded GC выполняется отдельно. Изменения исходной 000001 не применяются автоматически к существующей БД; [performance](operations/performance.md).

Схема recovery включена в исходную 000001: recovery digest/encrypted payload/TTL и nullable issued version/expiry в email_changes, owner index для lifecycle cleanup, recovery kind в outbox и recovered event в audit. Все recovery поля для старых intents остаются NULL, они не получают recovery authority. Срок начинается при защитном report; worker сохраняет intent до максимума protection/recovery expiry. Успешное восстановление меняет password credential и verified contacts, отзывает доступ и инвалидирует прежние intents/jobs одной транзакцией. Повторный административный block отменяет даже уже выданный recovery. Подробный контракт — [email change](features/email-change.md).

## Владельцы данных

A5.1/A5.2 добавляют `auth.mfa_totp` (encrypted secret/last step), `mfa_enrollments` (один pending/user, session/version/purpose binding, 10m TTL/5 attempts), `mfa_recovery_codes` (owner-bound keyed verifiers), `mfa_login_challenges` (primary/browser/version binding, один pending/user, не более 5m/5 attempts) и `mfa_audit` без secrets. Enrollment увеличивает auth_version и отзывает прежние sessions; ordinary issuance с enabled factor закрыта. Public bound completion атомарно потребляет фактор/challenge и создаёт общую сессию с nullable primary_method/primary_verified_at/mfa_verified_at; старые sessions не получают MFA автоматически. Audit/expired challenges очищает existing bounded retention. Reset не удаляет фактор, account deletion очищает secrets/recovery/challenges. [API и ограничения](features/mfa.md).

A4 добавляет `auth.roles`, `role_permissions`, `user_roles`, `users.access_version` и `auth.access_audit` с bounded role snapshot. Назначения отдельно от способов входа, optimistic role/assignment versions, FK/unique и индексы для owner/role/retention. Системная роль защищена от обычных mutations; bootstrap и полная last-admin защита block/delete остаются отдельным шагом. [Контракт](features/roles-permissions.md).

A3.1 добавляет `auth.linked_identities`: exact issuer (до 512 байт) + subject (до 255 байт), COLLATE C/составной PK и user_id FK. A3.3 добавляет UNIQUE `(user_id,issuer)` для одной identity/provider/account; его owner-prefix заменяет отдельный индекс user_id. Создание external-only user/identity/profile атомарно, email/password необязательны. При soft deletion ownership остаётся у tombstone; automatic identity release не реализован. Явный authorized unlink освобождает identity, не объединяя будущую регистрацию с прежним UUID. [Контракт](features/external-identities.md).

A3.2/A3.3 добавляют `auth.identity_audit`: user UUID, identity_created/identity_linked/identity_unlinked, auth_version/time, без issuer/subject/token. Запись атомарна с mutation и UNIQUE race rollback, FK сохраняет audit при soft deletion. Индекс created_at/id и existing bounded retention применяют SECURITY_AUDIT_RETENTION_DAYS (по умолчанию 180). Telegram flows в SQL не хранятся: single-use state/binding/verifier/nonce и link purpose/user/session hash живут зашифрованными в Redis 5 минут. Unlink повышает auth_version и отзывает sessions атомарно. [Контракт](features/telegram-login.md).

5.5 добавляет `auth.email_changes` (user/contact/session/version binding, отдельные confirm/report digests, state/expiry/protection window, encrypted completion payload), `auth.email_change_outbox` (mail intents/lease/retries) и `auth.email_change_audit` (user/change UUID/event без email/raw token). Один pending intent на пользователя; старый подтверждённый контакт сохраняется при переводе password credential на новый. Audit переживает expiry cleanup intent; restrict user/contact FK не разрешает незаметную потерю security history. Удаление/retention согласуется в 5.6; [подробности](features/email-change.md).

5.7c добавляет в account_provisions durable password_change_required и temporary_password_issued_at. Pending user остаётся закрыт для ordinary login/session/reset до atomic complete; activated_at выставляется только при установке постоянного пароля. Password audit поддерживает temporary issued/reissued/started/completed с actor при operator issuance и auth_version. Existing retention policy 180 дней применяется к этим events; idempotency metadata не очищается как audit. [Контракт](features/temporary-passwords.md).

Первые четыре таблицы имеют `created_at/updated_at`; BEFORE UPDATE trigger поддерживает `updated_at`. Основные дочерние записи имеют каскадные FK при явном hard delete. Status/deletion audit используют restrictive FK actor/target: hard delete не должен незаметно стирать историю, его retention/anonymization policy определяется в 5.6b. Сам SQL soft-delete не делает cleanup; внутренний DeletionService физически удаляет credentials/profile/challenges/change intents/outbox, отзывает сессии и очищает их metadata. Email reservations, UUID и audit сохраняются; [контракт](features/account-deletion.md).

Email нормализуется приложением: trim + lower, максимум 255 байт, только адрес без display name, комментариев и обёртки `<…>`. SQL дополнительно проверяет базовую нормализацию, длину и наличие `@`; полный разбор адреса остаётся в приложении. Уникальность после deletion сохраняется до retention release; blocked-before-deletion reservation автоматически не освобождается. Release удаляет contact, повторная регистрация создаёт новый UUID/неподтверждённый контакт.

5.6b добавляет `users.email_reuse_blocked` (CHECK: только с deleted_at), nullable `email_released_at` и partial index по due deleted owners без уже завершённых reservations. Block marker записывается атомарно при deletion из предыдущего status; не вычисляется по audit, который очищается отдельно. Released marker ставится в той же транзакции после удаления последнего contact; старые tombstones не сканируются повторно. Users/tombstones и restrictive FK сохраняются. Expression index на `LEAST(revoked_at,expires_at,absolute_expires_at),id` поддерживает retention завершённых sessions, индексы `(created_at,id)` — purge пяти audit tables. Worker не чистит active users/contacts/sessions и не управляет payment history. Bounded SQL/повторная регистрация и текущие ограничения — [retention](features/account-deletion.md#worker-и-повторная-регистрация).

PK/UNIQUE уже создают необходимые индексы. `(user_id, id)` поддерживает ownership FK и выборку контактов владельца; отдельные дублирующие индексы не добавлены. Индексы административных фильтров появятся вместе с реальными запросами.

Регистрация создаёт user → contact → password credential → profile в одной транзакции. Конкурентный конфликт `user_emails_email_key` преобразуется в существующий `ErrEmailAlreadyExists`; другие DB errors сохраняются. Поиск credential по email идёт через контакт, регистр не влияет на совпадение.

## Применение и границы

До первого production release схема развивается в исходной миграции 000001, без промежуточных миграций. Уже применённая старая версия **не обновится автоматически**: для существующей БД нужен отдельно согласованный перенос. Не выполнять down/reset рабочей БД ради этой схемы. В этом этапе рабочие данные не изменялись.

Verification, специализированные audit/outbox и verified-email gate смены пароля реализованы в 5.1. Регистрационная транзакция через composition callback включает challenge/outbox/audit; их failure откатывает регистрацию. Resend блокирует контакт/пользователя и заменяет challenge. Confirm проверяет expiry/status и меняет verified_at/consumes/audit одним commit. Подробности — [verification](features/email-verification.md). В 5.2 добавлены SQL session ledger и recovery: password reset/change повышают auth_version, отзывают все сессии и пишут audit одной транзакцией. Login issuance повторно проверяет status/version; stale refresh не воскрешает session. Подробности — [recovery](features/password-recovery.md). Общие account policies/audit, полная session security, роли и billing остаются впереди.

## Минимальная проверка

Обычный `task check` запускает unit tests и lint. Реальная schema-проверка opt-in: переменная `AUTH_SCHEMA_TEST_DATABASE_URL`, команда `go test ./internal/auth/methods/password/repository/postgres -run TestPostgresSchema -count=1 -v`.

Fixture допускает только localhost, пользователя/БД `auth_schema_test` и отсутствие исходной схемы `auth`. Использовать исключительно отдельный временный PostgreSQL: тест применяет SQL up/down/up и записывает тестовые данные. Без переменной он пропускается. Временный контейнер создаёт и удаляет оператор; новый sh-скрипт не добавлен.

7 октября 2026 на отдельном PostgreSQL 18.6 подтверждены up/down/up, repository round-trip, timestamps, UNIQUE/FK/CHECK, cascade delete, rollback регистрации, soft-deleted email reservation и конкурентная регистрация. Это проверка SQL/репозиториев, не полная HTTP/security acceptance.

9 октября проверка повторена для 5.1: registration+outbox rollback, cooldown/replacement, expiry/replay, concurrent consume, audit failure rollback, blocked account, lease/stale completion, retry limit и ciphertext cleanup. Redis concurrent limiter проверен отдельно. Рабочая БД не затронута.

9 октября проверка повторена для 5.2: reset cooldown/replacement/expiry/replay, ровно один concurrent consume, audit rollback, stale session issuance/refresh, атомарные reset/change с отзывом сессий и blocked account. Проверено на отдельном PostgreSQL 18.6; SQL delivery использует test double.

5.3 добавляет публичный UUID, не связанный с token/hash. Отзыв оставляет ledger-запись с `revoked_at`: действующий список её не возвращает, физическая очистка/retention остаются отдельной задачей. Logout-all увеличивает `auth_version`; проверка caller, отзыв и audit атомарны. Расширена исходная 000001 для свежих экземпляров. Уже применённую схему нельзя исправить повторным `migrate up`: нужен отдельно согласованный перенос, не reset рабочей БД.

5.4 добавляет account status use case: user row lock, expected `auth_version`, смена active/blocked + увеличение version + revoke всех сессий + удаление reset/verification challenges (outbox каскадно) + status audit одной транзакцией. При unchanged status и актуальной version запись не меняется; stale version — conflict, deleted account не разблокируется. Unblock тоже повышает version и не возрождает старые tokens/challenges. Для смены статуса использовать `account/service/StatusService`, а не отдельные UPDATE status/revoke/audit. Автоматический SQL trigger для этих бизнес-операций не добавлялся; прямой SQL не является поддерживаемым lifecycle workflow. Старый login snapshot после block/unblock не может выпустить новую сессию.

10 октября TestPostgresSchema прошёл на отдельном PostgreSQL 18.6: up/down/up и весь прежний набор, дополнительно block/unblock/no-op/conflict, actor/audit failure rollback, blocked/deleted credential/session checks, invalidation challenges/outbox, stale login snapshot, concurrent issuance/refresh/status writes и cancellation. Реальная рабочая БД не изменялась; новая audit table также требует отдельно согласованного переноса уже применённой схемы.
