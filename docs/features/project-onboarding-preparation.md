# Подготовка настроек и первого администратора проекта

MP3-onboarding-preparation,20 октября2026. Opt-in `project-prepare -schema -secrets -password -onboarding` после [установки технического пароля](project-secrets-preparation.md#установка-технического-пароля--20-октября). Без -password новый флаг отвергается до подключений. Успех возвращает `stage: onboarding_prepared`, не ready/созданного администратора. Credentials/setup token/digest не включаются в ответ.

## Что подготавливается

- `auth.auth_settings`: парольный метод включён, public registration/Google/Telegram registration выключены; email OTP/Google/Telegram/JWT exchange/native выключены. Password email verification — disabled: при закрытой регистрации это не делает чужой email verified; отдельный setup подтверждает почту первого администратора существующим кодом. Изменение политики позже — защищённое управление настройками, не повтор bootstrap.
- `auth.initial_setup`: только singleton и SHA256-digest независимого project setup secret. Нет пользователя, email/password hash, role assignment, MFA factor, pending intent или initialized marker. Общего/default пароля администратора нет.
- `project_meta.identity`: configuration_prepared=true и matching setup_operator_hash. Эти поля, настройки и setup pin коммитятся атомарно. Existing private schema creation расширена без новой migration; старому project_meta нужен controlled forward upgrade. Auth migration/grants не менялись, initial bootstrap поверх активной БД запрещён.

Bootstrap setup secret уже находится внутри encrypted catalog bundle, независим от DB password/project encryption key. `credentials.SetupProof` раскрывает только digest+binding, fmt/JSON редактированы; raw setup secret/другие ключи не возвращаются. `ReadSetupProof` использует тот же bounded current-authority transaction/AEAD decoder, что и DB reader, без двойного decrypt/нового шифрования. На ошибке/failed commit наружу не возвращается proof. Digest тоже не публиковать.

## Гарантии выполнения и повторов

1. Trusted schema binding, restricted target profile, receipt установки пароля, actual sealed DB/NOLOGIN runtime/ACL/OIDs проверяются **до** временного открытия БД.
2. Общий существующий lifecycle schema/onboarding открывает доступ только executor, проверяет shared marker/actual OIDs на новом соединении и повторно attests schema/role. Для успеха обязателен reseal; cleanup установлен до неоднозначного открытия. При outage/kill bounded cleanup может не завершиться: возможен только прежний executor-only crash-open, продолжение через ownership journal, не ready. Runtime LOGIN/CONNECT не включаются.
3. Project transaction держит schema transaction lock → существующий Access lock → private identity row; settings/setup helpers используют тот же Access lock. Реальные users/roles, unmarked settings/setup, неправильные binding/proof или утрата подготовленных rows дают отказ, не adoption/reset.
4. Используются существующий SQL initializer настроек (новый transaction-owned entry point) и существующий setup singleton lock/pinning. Дубликатов setup/password/MFA сценария, новых crypto primitives/dependencies/ENV/HTTP/Swagger нет.
5. Сохранённые settings должны иметь исходную version1/политику, setup pin — тот же digest. Replay не переписывает settings/setup/marker, не меняет pending intent и не открывает завершённый setup. Drift не сбрасывается к defaults; missing prepared setup/settings не воссоздаются автоматически.
6. Current catalog authority проверяется до открытия, перед project commit и после reseal. При позднем suspend могут остаться начальные записи в закрытой БД; успех/ready/access не публикуются. Разные БД не превращаются в общую атомарную транзакцию.

Вся операция bounded20s, project rollback/close1s и access cleanup3s; прежний target session lock сохраняется, обычный invocation использует до3 SQL connections без нового пула/workers. SQL presence checks — EXISTS, нет сканирования пользователей для подсчёта/импорта и нет изменения Auth hot path. Capacity/GC не измерялись.

## Изолированный HTTP-профиль onboarding

`router.NewProjectOnboarding` принимает только доверенный origin проекта, существующий SetupHandler, callback текущего допуска, HTTP capacity/proxy policy и logger. Здесь нет общего набора Auth handlers или наследования конфигурации платформы. Профиль пока **не подключён** к основному серверу.

Разрешены только `POST /api/v1/setup/start` и `POST /api/v1/setup/complete`. Повторно используются существующие setup handler/DTO/error mapping, ограничения размера JSON и проверка `X-Setup-Token`. Новый профиль не реализует второй setup flow и не меняет требования email/MFA существующего сервиса.

- Требуются TLS и точное совпадение Host, включая настроенный порт. X-Forwarded-Host/Forwarded/X-Forwarded-Proto не заменяют эти проверки; deployment с TLS termination потребует отдельно согласованного trusted ingress, plaintext fallback здесь отсутствует.
- Для обоих POST обязателен единственный точный project Origin. Cross-origin CORS не включён; OPTIONS и остальные методы не дают доступ к setup. Platform Origin не разрешается автоматически. Это same-origin профиль, не готовое подключение будущей общей админки.
- На каждом допустимом POST вызывается `Admit(ctx)`: false →404, ошибка/отменённый context →503 без деталей каталога; положительный ответ не кешируется. App factory подставляет конкретный SQL reader, описанный ниже, а не внешний bool callback. Сам HTTP-профиль сохраняет этот внутренний middleware-контракт; к основному серверу он ещё не подключён.
- Неверные Host/Origin, неизвестные маршруты и неподдерживаемые методы не вызывают catalog callback или SetupHandler. Login/register/recovery/roles/settings/platform/JWKS/Swagger/health не регистрируются. Ответы не кешируются, собственных session cookies профиль не создаёт.
- Используется существующий bounded HTTP admission; бюджет относится к экземпляру handler, а не ко всему процессу/fleet. Дальнейший dispatcher обязан учитывать суммарные бюджеты.

Проверка допуска — до выполнения setup, не распределённая транзакция с project SQL. Уже допущенный запрос потенциально завершится после suspend; публикация ready и дальнейший допуск требуют отдельного fencing/readiness протокола. Один успешный callback не разрешает обычные Auth routes.

## Сборка проектного runtime — 21 октября 2026

`app/auth.NewProjectOnboarding` собирает только существующий setup и изолированный HTTP-профиль. Вход: доверенный catalog Project/PreparationReservation, typed `credentials.OnboardingKeys`, явный SMTP allowlist/HTTP limits/proxy policy; зависимости — borrowed project pool, обычный catalog API pool и общий Redis/hasher/logger. Допуск проверяет конкретный SQL reader, произвольный callback не принимается. Нет Auth.New на проект, новых pool/workers, process-global current project или закрытия чужих клиентов при отказе.

`PreparationRepository.ReadOnboardingKeys` использует прежнюю защищённую read transaction: current reservation/binding/flag/metadata, AEAD, результат только после commit. Typed value содержит только project encryption key/setup secret, не DB password или signing key; fmt/GoString/JSON редактированы. Getter raw secret — внутренний privileged API, не способ его доставки пользователю. Доступ к reader/ciphertext остаётся у restricted preparation loader, не ordinary API. Ключи нельзя выбирать по непроверенному Host/параметрам HTTP.

Порядок cold-open, общий deadline5s:

1. Проверить trusted descriptor (enabled/provisioning, version/generation, origin/slug/project binding), наличие зависимостей и HTTP policy; derive только project realm scope. Snapshot не заменяет актуальный допуск.
2. Проверить существующий operator runtime profile обычного catalog pool; создать `NewOnboardingAdmission` для точной reservation/binding/descriptor и вызвать его `Check`. Без сохраняемого разрешения/при отказе не читать project SQL. `CheckCurrent` для offline stages **недостаточен**. Физическая activation ещё не реализована этим reader.
3. Read-only `CheckOnboardingRuntime`, bounded3s: actual current_database/session_user/current_user, имена/OIDs/owner и shared database marker, runtime LOGIN без привилегированных flags/memberships, точный DB ACL/CONNECT без CREATE/TEMP/grant option, schema ownership/доступ, CRUD без TRUNCATE/grant option и protected recovery/restore denial. Setup pin должен совпасть с keys proof, setup не завершён, policy остаётся начальной безопасной version1. Нельзя подставить owner/superuser/соседний pool. Private project_meta не открывается runtime ради этой проверки. Это snapshot при сборке и compatibility probe, не full schema drift scanner/периодическая авторизация или межкластерная attestation.
4. Создать scoped SMTP cipher/лимитер и прочитать credentials из существующего `auth.smtp_settings`. Только явный allowlist и RequireTLS; нет Initialize/ENV seed/fallback. Missing settings, чужой ciphertext или незаданный target дают отказ без перезаписи. Mailer читает актуальные SQL credentials при отправке; успешная загрузка не доказывает доступность SMTP. Seed settings до cold-open — отдельный ещё не реализованный protected provisioning шаг, тестовая SQL-запись не означает готовое UI/API.
5. Собрать прежний SetupService с независимыми project setup/MFA ciphers, project Redis namespace, общим hasher и project slug как TOTP issuer. Email/MFA/recovery guards не меняются. Повторно вызвать SQL admission перед возвратом handler; профиль использует этот же reader на каждом setup POST.

Factory не меняет LOGIN/CONNECT/ACL/маркеры и не открывает listener. Caller владеет pool lifecycle и trusted endpoint/TLS/binding; pool/версия/authority могут измениться после probe, registry/physical activation должны обеспечивать revalidation/drain/fencing. Redis остаётся обязательным; отсутствие сетевого вызова к нему при assembly не означает SQL fallback. Настоящие setup запросы сохраняют прежние Redis limits/fail-closed. Новых ENV, зависимостей и Swagger DTO нет.

## Сохраняемый SQL-допуск — 21 октября 2026

`platform.project_preparations.onboarding_admitted` по умолчанию false; CHECK запрещает true без secrets_created. Это разрешение обслуживать **только setup**, не состояние ready/созданный администратор/физическое открытие БД.

- Restricted `PreparationRepository.PermitOnboarding` использует общую transaction с current-authority locks (realm → project → preparation), проверяет сохранённый encrypted binding и расшифровывает только onboarding material. Перед UPDATE выполняется actual `CheckOnboardingRuntime` с настоящим ограниченным project pool и setup proof. Nil/неверный pool, stale epoch, tamper, ошибка/timeout/commit failure не дают успешного результата метода. При потере ответа commit флаг может уже сохраниться: повторно сверять текущее состояние, не объявлять гарантированный rollback и не сбрасывать данные. API caller не может подставить bool вместо probe. Доверенность endpoint/target/TLS по-прежнему обязан обеспечить loader, не пользовательский DSN.
- Первый UPDATE атомарен с catalog authority; replay повторно проверяет runtime, но `WHERE NOT onboarding_admitted` не делает лишнего UPDATE. Runtime probe — отдельная БД, не распределённая транзакция и не вечная гарантия её состояния; неуспешный replay сам по себе не отзывает прежде сохранённое разрешение. Physical protocol обязан закрывать catalog admission до reseal/drain; этот lifecycle пока не подключён. Publisher получает общий бюджет3s, rollback1s; отмена передаётся и в callback работы под transaction.
- Обычный catalog API получает только SELECT на явные non-secret reservation/binding колонки. Нет чтения ciphertext/key_id/format_version/created_at secret row, INSERT/UPDATE permission flag, новых DDL или root key. Existing operator/preparation profiles обновлены под эти минимальные grants. Restricted secrets loader не сохраняется в HTTP runtime.
- `OnboardingAdmission.Check` выполняет один bounded3s SELECT без UPDATE/locks по пользовательским строкам: enabled/provisioning, initialized platform realm, exact version/generation/nonce/operation/target, исходный slug/origin, secrets_created/admitted и существующий matching secret metadata binding. Разрешение не кешируется. Отказ текущего state →false, SQL/permission/cancellation failure →error; HTTP mapper оставляет404/503 без частных деталей. Сам reader также отказывается работать с credential, которому доступен ciphertext или запись admission flag.
- `Reserve` нового epoch сбрасывает permission, сохраняя прежний retained secret marker. После committed suspend/изменения epoch старый reader не допускает новые запросы; resume с новым version не оживляет старое разрешение. Уже начатый project SQL commit этим не отменяется. Publisher держит current authority locks до своего commit, но caller ещё должен связать catalog grant с физическим activation/recovery protocol.

Source initial catalog/grants расширены без новой migration file. Existing installation требует controlled forward upgrade; source bootstrap/reset поверх активной БД не выполнять. Явный physical LOGIN/CONNECT activation/restart/reseal/revoke/drain реализован ниже; его production caller/reconciliation, SMTP provisioning, setup authority delivery и публикация server dispatcher ещё открыты. Не включать обычный Auth router или ready только по admission bit.

## Физическая активация и остановка — 21 октября 2026

`Target.ActivateOnboarding` и `CloseOnboarding` — закрытый PostgreSQL provisioning-протокол, не HTTP-ручки и не новый режим CLI. Входы: trusted target session, точная reservation/binding, restricted catalog repository, codec и проектный pool. Обычный API не получает target credentials/root key. Существующий `project-prepare -onboarding` по-прежнему оставляет БД sealed/NOLOGIN; сервер не вызывает новый протокол автоматически.

Порядок активации:

1. Bounded20s, dedicated target session и прежний advisory lock. Проверить maintenance profile и форму/scoping reservation/binding; имена вывести из project UUID. Конкурентный target executor получает Busy. Caller закрывает dedicated session при любом результате; не удерживать её на время жизни HTTP runtime и не возвращать в pool.
2. `WithdrawOnboarding` сохраняет false **до** target writes. Realm → project → preparation locks; exact retained reservation/operation/version/generation/secret metadata. Работает и после suspend, но не может отозвать новую catalog epoch. Повтор false не делает UPDATE. Недоступность каталога/неоднозначный commit — ошибка, не доказанное закрытие.
3. Проверить current setup proof через прежний AEAD reader. Перед target writes проверить actual names/OIDs/ownership/shared marker, password receipt/schema_started, generation, safe role flags/memberships и точный DB ACL; чужие/неучтённые ресурсы не усыновлять. Сохранить `opening` с operation/version/generation в maintenance journal. Затем одним target commit: LOGIN, runtime CONNECT, ALLOW_CONNECTIONS=true и `open`; повтор exact open не переписывает target row. Current authority проверяется перед открытием и до target commit; между БД нет общей транзакции.
4. Создать временный pool из доверенной конфигурации caller (MaxConns1, MinConns/MinIdleConns0), то есть выполнить **новую аутентификацию**, не переиспользовать старую сессию. `PermitOnboarding` повторно проверяет действующие role/grants/binding/setup/policy под catalog authority locks. Лишь затем сохраняется admission и ещё раз проверяется current authority. Borrowed pool не закрывается и не перенастраивается; временный probe pool закрывается.

При ошибке после withdrawal выполняется bounded5s best-effort `CloseOnboarding` с независимым от отмены cleanup context. Ошибка cleanup присоединяется к исходной. Процесс/target session/network outage может помешать остановке: сохраняемый journal требует нового явного reconciliation, а не заявления об успешном rollback. Потеря commit reply также не означает отсутствия physical/catalog commit.

Порядок остановки/restart recovery:

1. Взять target lock и **подтверждённо** отозвать catalog admission. При ошибке withdrawal не менять physical access и не выдавать успех.
2. Под ownership/journal guards атомарно сохранить `closing`, NOLOGIN, REVOKE CONNECT и ALLOW_CONNECTIONS=false. LOGIN/CONNECT влияют только на новые подключения — живые соединения требуют отдельного drain.
3. Завершить только соединения с точными database OID/runtime OID: партии до128, общий бюджет3s, ожидание termination до1s на backend. Executor временно делает `SET LOCAL ROLE` только в роль этого проекта; source schema installer даёт ему SET TRUE/INHERIT FALSE. Нет `pg_signal_backend`, SUPERUSER, наследуемого CONNECT или права убивать соседние/DBA sessions. Поля backend_type для NOINHERIT могут быть скрыты, фильтрация использует открытые datid/usesysid/pid. Завершение backend откатывает незавершённую транзакцию; уже committed изменения не отменяются.
4. Только после пустого списка sessions сохранить `closed`. Чужое соединение не убивать: вернуть conflict и оставить `closing` для retry. Каждый batch — отдельная transaction, без устаревшего transaction stats snapshot. Close имеет общий бюджет10s. Repeated closed не переписывает target journal.

Journal переживает dedicated session. Новый executor может повторить opening/open того же epoch или закрыть opening/open/closing. Текущая catalog epoch может закрыть **более старый** target journal с тем же immutable binding до продвижения resource generation; stale caller не может закрыть новую epoch. Offline Prepare отказывается менять generation открытого journal. Утрата/подмена marker/OIDs/ownership, несовместимые flags/ACL и противоречивое состояние — отказ, не автоматическое исправление/DROP/reset.

Admission — право на setup HTTP, не узкий набор SQL-привилегий: runtime сохраняет существующие Auth grants. Caller обязан публиковать только прежний setup allowlist. Нет normal Auth router/ready/first admin/SMTP provisioning/секрета в stdout. Trusted endpoint/TLS/DNS/cluster identity остаются обязанностью loader; runtime probe и markers не заменяют restore/anti-rollback/fleet fencing.

Source `storage-target.sql`/target profile и первоначальный schema installer расширены без новой migration file. Existing installations требуют controlled upgrade, включая ограниченный SET grant; source bootstrap поверх рабочей БД не запускать. [Проверки и ограничения](../planning/history.md#результат-mp3-physical-onboarding--21-октября-2026).

## Что ещё не включено

Этот этап **не запускает UI и не публикует project setup endpoint**. Factory, SQL admission и явный physical activation/recovery реализованы, но ещё нет production caller/loader/dispatcher, автоматического reconcile/drain при suspend и protected SMTP provisioning. Доставка raw setup secret доверенному владельцу/доступ оператору требуют отдельного протокола, не ссылки с секретом в URL или CLI stdout. Не копировать credentials платформенного администратора в проект и не трактовать platform session как SSO.

Завершение первого администратора переиспользует [существующий setup](initial-setup.md): email proof/password policy/MFA/recovery и durable initialized marker; SMTP/provider/MFA readiness не выдумывается. Текущий setup требует MFA, выбор обязательности ещё в отдельном A6.3m. Configuration prepared не означает готовый SMTP или существующего администратора. Далее — protected initial SMTP/setup authority delivery, trusted loader/dispatcher/reconciliation, first-admin/configuration readiness и binding/ready. Не открывать обычные Auth endpoints только на основании этого marker.
