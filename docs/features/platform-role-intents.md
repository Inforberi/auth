# Подготовка создания роли владельцем платформы

MP2.7, обновлено24 октября 2026. Здесь описаны catalog intent, краткоживущий admission и проектная SQL-транзакция создания роли. Подключены к [opt-in HTTP bridge](platform-roles-api.md); проверки HTTP-блока Luna завершены: V1 tests/race/SQL/API/scanner и V2 targeted lint/race PASS. Само сохранение intent роль не создаёт. Общий протокол — [ADR005 §3](../adr/005-independent-projects.md#3-одна-сессия-оператора-без-пользовательского-sso).

## Контракт

`Project/repository/postgres.PrepareRoleCreation` принимает текущий platform principal и конкретный `domain.RoleCreation`: UUID операции/проекта, ожидаемые version/generation, key/name/description/permissions/MFARequired и причину. Обычные правила роли переиспользуются из Access domain; порядок permissions канонизируется без изменения входного slice. Пользователь не задаёт actor, realm, action или permission проверки.

Требуется `platform.project_access.manage`, а не только `platform.projects.manage`. Существующий `AuthorizeMutation` проверяет и удерживает текущие realm/user/permission/session/password/TOTP/role guards. Порядок: authority → project row → immutable intent. Вся транзакция ограничена тремя секундами, после ожиданий срок proofs проверяется перед commit. Пока A6.3m не выполнен, текущая platform policy требует password+TOTP.

Допускается только enabled/ready проект с точными version/generation, штатным именем БД и согласованными reservation/storage/schema метаданными подготовки и secrets. Shared project lock конфликтует с lifecycle writers; runtime не получает UPDATE на provisioner metadata и не читает ciphertext. Снимок содержит target, database, reservation и database/owner/runtime OID, schema version. Это **каталоговые метаданные**, не доказательство физической аттестации подключения.

`platform.project_role_intents` хранит неизменяемый снимок запроса, realm/actor/project/binding и время. Actor принадлежит платформе, а не выдуманному пользователю проекта. Platform runtime получает SELECT и INSERT только заданных столбцов; не UPDATE/DELETE/TRUNCATE и не INSERT времени. Runtime profile отвергает расширенные права. Исходная catalog migration дополнена без отдельной upgrade migration; существующие установки этим не обновляются автоматически.

UUID операции уникален в этом сценарии. Повтор сначала заново проверяет authority и актуальную цель: совпадение actor/realm/project/version/generation/binding/request возвращает исходное время без UPDATE. Отличающийся запрос или binding — conflict. Конкурентные одинаковые INSERT дают одну запись; ожидание ограничено общим deadline. Ошибка вставки не оставляет частичного результата.

После `INSERT ON CONFLICT DO NOTHING` существующая запись читается отдельным SQL statement: в Read Committed конфликтующий winner может быть невидим снимку самого INSERT, но видим следующему запросу. [PostgreSQL 18 — Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html).

Возвращается только UUID/время/replayed. Ни сессия, ни секреты, ни подписанный capability не создаются. После потери ответа можно повторить тот же запрос; `unavailable` сам по себе не доказывает rollback.

## Проектная транзакция — 21 октября 2026

`CreatePlatformRoleInTransaction` реализует проектную часть, а не авторизованный bridge. Она принимает caller-owned transaction, отдельный `PlatformActor`, non-secret `credentials.Binding`, команду и реальный permission catalog/MFA capability выбранного проекта. Тип actor задаёт атрибуцию и не является доказательством прав.

До Access lock на actual transaction connection выполняется [общий SQL runtime profile](project-runtime-profile.md): identity/version/source checksum, owner и контрактные table/view/sequence privileges без private/DDL/elevated capability. Он заменил прежний меньший identity-only guard, не добавлен поверх него. Текущий catalog admission и trusted server/credential provenance остаются отдельными гарантиями. Затем существующий transaction-scoped Access lock сериализует редкие изменения ролей; горячие пользовательские чтения его не берут.

Новый запрос применяет общие role rules, проверяет permissions в project catalog и MFA capability. SQL-вставка роли/permissions общая с обычным Access create, но обычные project actor/delegation проверки не меняются. `super_admin`/system role создавать этим путём нельзя. Пользователей, memberships и сессий операция не создаёт.

Роль, permissions и `auth.platform_role_creations` фиксируются одной project transaction. Последняя таблица — конкретный audit/receipt: platform realm/actor, operation/project UUID, полный non-secret binding, canonical request и исходный role snapshot. FK ведёт к роли, но не к выдуманному project user. UUID операции уникален в проектной БД; точное совпадение возвращает исходный snapshot без UPDATE и без повторного применения capability policy к уже committed результату. Изменённый actor/binding/request даёт conflict. Реальную platform authority и target caller обязан заново проверить и перед replay. Snapshot — исторический результат операции, не актуальное состояние роли после её последующих изменений.

Project runtime имеет SELECT и column INSERT, но не изменение/удаление/подмену времени receipt; platform runtime в своей БД не имеет к этой таблице доступа. Existing schema/runtime probes учитывают это исключение из обычного Auth CRUD. Стандартная audit retention не очищает receipts; до отдельного контракта хранения очистку не добавлять. FK сохраняет аудируемую роль; будущий delete-role flow должен явно учитывать эти ссылки. Initial Auth source/grants дополнены без новой migration: существующим БД нужен controlled upgrade, а не повторный init/reset.

Функция ограничивает свою работу тремя секундами, но **сама не делает commit/rollback**. Caller обязан rollback при любой ошибке и не возвращать успех до собственного commit. Потерянный commit reply не доказывает rollback. Реальная SQL-приёмка проверяет запись, replay, параллельность, отказ аудита, явный caller rollback и immutable grants; production caller/HTTP ещё отсутствуют.

## Окончательный допуск и выполнение — 24 октября 2026

Пользователь согласовал стандартную границу отзыва для межбазового административного действия: **commit admission — окончательная авторизация конкретной команды**. Отзыв прав/session или suspend до этого commit запрещает новый допуск; после него уже допущенная операция может завершиться в пределах короткого бюджета. Обычный отзыв пользовательских сессий не меняется. Прежнее требование удерживать catalog locks до project commit заменено этой явной границей в [ADR005](../adr/005-independent-projects.md#3-одна-сессия-оператора-без-пользовательского-sso).

`AdmitRoleCreation` в общей managed transaction заново проверяет актуальные platform proofs/AccessManage, удерживает authority/project locks, сверяет exact project/version/generation/binding и ранее сохранённый immutable intent с тем же actor/realm/request. Одного intent недостаточно. В `platform.project_role_admissions` записывается отдельный UUID попытки, связанный с operation UUID, с SQL expiry не дальше трёх секунд и не позже срока proofs. Возврат разрешён только после успешного catalog commit. Ошибка/потерянный ответ catalog commit не выдаёт usable admission: нужен новый авторизованный запрос.

Результат — непрозрачный process-local `AdmittedRoleCreation` с приватными неизменяемыми данными команды и atomic one-use flag, не сериализуемый клиентский ticket и не очередь. Монотонный local deadline консервативно отсчитывается от начала admission-вызова, поэтому время SQL/commit/transport сокращает оставшийся бюджет. Часы двух независимых серверов БД не сравниваются. Изменение исходного request после возврата не меняет допущенную команду.

`Execute` принимает project pool либо borrowed connection из trusted assembly через узкий `RoleProjectDatabase` контракт. Она владеет bounded Read Committed transaction, проверяет полный SQL runtime profile на этом же соединении, вызывает общий project writer и делает commit. До SQL ставятся local `transaction_timeout`/`statement_timeout` по оставшемуся бюджету; эти значения не уходят в pool после завершения транзакции. [PostgreSQL18](https://www.postgresql.org/docs/18/runtime-config-client.html#GUC-TRANSACTION-TIMEOUT), [pgx5.10 transaction contract](https://github.com/jackc/pgx/blob/v5.10.0/tx.go). Local deadline и server transaction timeout ограничивают обработку, но не обещают мгновенного отзыва уже принятой записи, управления сетью или отмены уже выполненного commit.

Project audit/receipt содержит исходный admission UUID без межбазового FK. Replay с новым допуском сравнивает actor/realm/binding/request, возвращает исходную роль и сохраняет исходный admission ID в receipt. SQL error до commit откатывается; ошибка commit консервативно даёт `ErrRoleOutcomeUnknown`, не утверждение rollback и не автоматическую выдачу нового operation ID. Повтор с тем же operation/request после нового current admission читает durable receipt вместо создания ещё одной роли.

После подтверждённого project commit append-only `platform.project_role_outcomes` сохраняет role snapshot и admission/operation связь. На завершение только аудита выделена отдельная cleanup-context секунда; она не разрешает новые project writes. Неудача этого шага возвращает известный project результат с `CatalogRecorded=false`, а не ложный rollback. Повтор с новым current admission сверяет receipt и дописывает catalog outcome. Существующий outcome не обновляется; несовпадающий snapshot не затирается. TTL/retention этих административных ledger ещё не определены — обычный Auth audit retention их не удаляет.

Реальные SQL tests проверяют revoke до нового допуска / разрешённое завершение после revoke, четыре concurrent admissions / одна роль, one-use, expiry без записи, недоступный каталог после admission и последующее восстановление. Lost-COMMIT-ack test исполняет настоящий project commit, затем fault adapter возвращает `io.ErrUnexpectedEOF`: восстановление идёт по receipt. Это контролируемая fault injection, не фактический сетевой обрыв. Новых зависимостей, публичных routes, ENV, очередей или фоновых исполнителей нет. Initial SQL изменён только для новых установок; рабочие БД не обновлялись автоматически.

## SQL runtime registry — 24 октября 2026

`ExecuteWithRuntime` заимствует соединение из [ограниченного реестра](project-runtime-registry.md) по exact admission binding/version/generation и вызывает прежний Execute с тем же deadline. Reader credentials отдельный SELECT-only, endpoint только configured target, network TLS/SCRAM, каждый physical connect проходит SQL profile. Pool lease сохраняется до project commit/outcome; ошибочная БД или отсутствие capacity не вызывают fallback. Это внутренняя связь, без HTTP/server wiring и без изменения authority.

## Публикация и оставшиеся gates

Защищённое чтение своей операции и восстановление catalog outcome по project receipt реализованы [отдельно](platform-role-outcomes.md). Они требуют current read authority, не выдают admission и не повторяют project mutation. [Проверки отдельным агентом](../planning/history.md#результат-mp27-role-outcomes--24-октября-2026).

SQL-связка, runtime profile, trusted registry, local lifecycle/resident sync, ресурсные bounds и локальные authority/transport/concurrency матрицы проверены в предыдущих блоках. Теперь добавлен [HTTP create/read/reconcile](platform-roles-api.md) с явным project scope до runtime access; новый HTTP блок проверен Luna (V1 tests/race/SQL/API/scanner, V2 lint/race PASS). Dispatcher использует прежний admission/ExecuteWithRuntime, без другого SQL пути или user impersonation. Новые MFA-required роли fail closed до готовности project capability. Owner-managed readiness, полная feature assembly/worker scheduler, назначения/пользователи/settings bridge, credential rotation и fleet приёмка остаются открытыми. SQL fingerprint не означает доверие к произвольному DSN. Существующие project-user сценарии не меняются.
