# Подключаемый каталог разрешений

## Назначение

Каталог описывает действия, которые backend проекта умеет защищать. Auth использует его для выбора permissions при создании ролей; backend данных применяет права к действиям, строкам и полям, включая read/write/filter/sort/export. Каталог не содержит пользователей, назначений, секретов или правил выполнения SQL. Он не аутентифицирует внешний backend и не реализует фильтрацию данных автоматически.

Текущий вариант — локальный operator-controlled JSON-файл при запуске. Ручная подготовка файла и будущая отправка от доверенного backend используют один формат, parser и валидацию. HTTP import, скачивание по URL, hot reload и автоматическая синхронизация не реализованы.

## Формат v1

[Рабочий пример](../examples/access-catalog.json) содержит разрешения для просмотра сотрудников, телефона и зарплаты, а также шаблоны «Оператор» и «Бухгалтер».

```json
{
  "version": 1,
  "permissions": [
    {
      "key": "employees.phone.read",
      "name": "Просмотр телефона",
      "description": "Чтение телефона сотрудника",
      "group": "Сотрудники"
    }
  ],
  "roleTemplates": [
    {
      "key": "operator",
      "name": "Оператор",
      "permissions": ["employees.phone.read"]
    }
  ]
}
```

`version` — версия формата, не номер обновления каталога. Поддерживается только 1. `permissions` объявляет поддерживаемые действия; `roleTemplates` необязателен. Permission и шаблон имеют стабильный key, понятное name и необязательное description; permission дополнительно имеет group. Действующие роли остаются самостоятельными SQL-записями с UUID/version.

Встроенные `access.roles.manage` и `access.assignments.manage` добавляются сервером. Их нельзя переобъявить файлом. Шаблон не может иметь зарезервированный key `super_admin`; выбор management permissions в обычном шаблоне не обходит проверку делегирования при последующем создании роли.

Ограничения: файл до 256 KiB, до 509 продуктовых permissions + трёх встроенных (`access.roles.manage`, `access.assignments.manage`, `accounts.email.bind`), до 64 шаблонов и 128 permissions на роль. Metadata ограничения соответствуют [основному контракту](roles-permissions.md). UTF-8, неизвестные поля, повторные JSON-поля (включая case variants), лишний JSON после документа, неподдерживаемая version, дубли keys и неизвестные ссылки шаблонов проверяются явно. JSON nesting ограничен 16. Метаданные — обычный текст, не HTML или инструкции. Новый core permission не выдаётся автоматически существующим ролям; первичный admin/grant — защищённый bootstrap/operator workflow.

## Проверка и preview

Из корня проекта:

```bash
task access:preview FILE=docs/examples/access-catalog.json
task access:preview FILE=candidate.json CURRENT=current.json
```

Либо без Task:

```bash
go run ./cmd/access-catalog -file candidate.json -current current.json
```

Без CURRENT сравнение выполняется со встроенным каталогом. Вывод — JSON с added/removed/changed permissions и шаблонами, ключи отсортированы. Изменение порядка permissions в шаблоне не считается изменением его прав. Команда только читает файлы: не открывает БД, не перезаписывает конфигурацию и не назначает роли. Preview не проверяет ссылки в реальной БД; это делает сборка Access при запуске.

## Явное применение оператором

1. Проверить изменения командой preview и отдельно поведение проверок permission keys в backend данных.
2. Выбрать проверенный файл и задать `ACCESS_CATALOG_FILE` в конфигурации установки. Пустое значение означает только встроенные permissions; ошибочный путь/невалидный документ не игнорируются.
3. Для контейнера смонтировать файл read-only по указанному пути. Сам env не копирует файл в образ. Относительный путь разрешается от рабочей директории процесса; предпочтителен явный путь внутри контейнера.
4. Развернуть одинаковое содержимое на всех экземплярах Auth и перезапустить их. Каталог загружается один раз; изменения файла у работающего процесса не применяются.

Это operator deployment, не административная операция через browser API. Файл должен находиться под контролем оператора, не в каталоге пользовательских загрузок. LoadFile принимает обычный локальный файл (в том числе разрешённый через deployment symlink), не директорию/device/URL; объём повторно ограничен при чтении, даже если файл вырос после stat.

Сборка `internal/app/access` использует существующий PostgreSQL pool. До выдачи Service выполняется один startup query с deadline 3s: все permissions, записанные в SQL-ролях, должны существовать в выбранном каталоге. Удаление/переименование используемого key даёт conflict и закрывает запуск, не меняя роли или их права. Сначала следует явно изменить зависимые роли через защищённые use cases; простое переименование key не переносит старые назначения. Query проверяет role_permissions, не сканирует пользователей или все назначения; он не выполняется в пути каждого запроса.

Загрузка не пишет SQL и не создаёт новые права в ролях. Добавленные permissions становятся вариантами выбора; чтобы выдать их, надо явно создать/изменить роль и назначить её с existing delegation/version/fresh-auth/audit guards. Совпадение key шаблона с существующей ролью не изменяет её; попытка явно создать вторую роль с тем же key даёт conflict. Шаблоны доступны через `App.Access.Templates()`, use cases — через `App.Access.Service`, а создание по выбранному шаблону использует обычный CreateRole. Никакого template auto-apply нет.

## Что остаётся

- Защищённое применение и аудит runtime-настроек, DB-backed version/conflict и согласованность нескольких экземпляров — A6; текущий файл не является живой общей конфигурацией.
- UI preview/выбор шаблона/подтверждённое применение — A7 после MFA и last-admin guards. Системное bootstrap/управление ещё не реализовано.
- Передача того же формата через API — при конкретной внешней интеграции с отдельным межсервисным trust contract. Каталог сам по себе не доказывает полномочия backend и не разрешает browser импорт.

Схема/миграции/dependencies/Swagger этим шагом не меняются. Запуск без файла использует встроенные права, но не создаёт первого администратора.
