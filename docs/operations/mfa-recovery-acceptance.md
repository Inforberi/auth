# Приёмка восстановления MFA — 13.1d.4

Статус на 15 октября 2026: локальные автоматические проверки выполнены ранее; внешняя приёмка **не выполнена**. Этот документ — порядок проверки, не отчёт об успешном запуске. Контракт API и операторские команды — [MFA](../features/mfa.md) и [admin-recovery](../features/admin-recovery.md); гарантии и границы — [план](../planning/mfa-recovery.md).

## Перед запуском

- Выделить разрешённое изолированное HTTPS-окружение и синтетические аккаунты. Указать origin, версию приложения, конфигурацию методов входа и ответственного за остановку эксперимента. Не использовать рабочую БД или копию пользовательских данных.
- Подготовить отдельные runtime и персональную operator DB identity по существующему runbook. Секреты передавать через принятый secret manager; не сохранять DSN, QR, cookies и коды в отчёте или истории терминала.
- Подготовить authenticator, подтверждённый тестовый ящик, SMTP с требуемым TLS и браузерный клиент. UI пока нет: нужен согласованный тестовый клиент на разрешённом origin, который сохраняет HttpOnly cookie; Swagger сам по себе не доказывает браузерную совместимость.
- Утвердить независимую проверку владельца. Знание пароля, email, request UUID или наличие challenge не заменяет её. Назначить оператора и канал уведомления для аккаунта без verified email.
- Явно разрешить временные сбои Redis/SMTP и остановку тестового экземпляра. Ограничить их этим окружением; заранее определить восстановление зависимостей и наблюдение очереди.
- Только после подготовки включить необходимые flags в тестовом окружении. Проверить startup с отдельными runtime/operator полномочиями. Не включать recovery в рабочей установке ради приёмки.

## Основной сценарий

1. Для тестового пользователя заранее настроить действующий TOTP и recovery codes; сохранить одну обычную сессию для проверки отзыва. Записать несекретные исходные status, auth_version и роли.
2. Выполнить реальный primary login. Получить `mfa_required`, challenge и `__Host-mfa-login`; убедиться, что полноценная сессия не создана.
3. Из того же браузера отправить POST `/api/v1/auth/mfa/recovery/start` с `{challenge}`. Ожидать `operator_approval_required`, request UUID, новый secret/URI и expiry. Добавить candidate в authenticator. До завершения действующий фактор и сессия не должны измениться.
4. Оператор независимо проверяет владельца, сверяет окружение, target, request и version; выполняет `mfa-approve` по runbook с точным подтверждением. Оператору не передаются candidate secret или коды пользователя.
5. В пределах TTL отправить POST `/api/v1/auth/mfa/recovery/complete` с `{requestId, challenge, code}` и той же cookie. Ожидать десять новых recovery codes один раз, удаление прежних login/session cookies и отсутствие новой сессии. Коды сохранить только у тестового владельца, не в отчёте.
6. Проверить отзыв ранее созданной сессии, увеличение auth_version на один, неизменность password/contact/status/ролей/setup marker и единственное событие успешного completion. Старые TOTP/recovery codes больше не дают вход; новый TOTP позволяет обычный primary + MFA login. Не проверять новый TOTP повторно в уже потреблённом time step.
7. Дождаться письма в реальном тестовом ящике: правильный ранее verified адрес, событие и request UUID, без QR/secret/codes. SMTP acceptance без письма в ящике не закрывает эту проверку. Для аккаунта без verified email проверить `notification_queued=false` и независимое уведомление оператором.
8. Повторить для каждого разрешённого в выпуске primary method и административного аккаунта. Если provider secrets ещё не выданы, соответствующий вариант оставить NOT RUN, не подменять реальный callback тестовым.

## Отказы и конкуренция

Для независимых случаев начинать новый flow: успешное завершение, новый primary и истечение TTL делают старый запрос непригодным.

| Проверка | Ожидаемая гарантия |
| --- | --- |
| Чужой браузер, отсутствующая/дублированная cookie, неверный Origin, неизвестные JSON-поля, GET | Нет замены фактора, выдачи сессии или утечки candidate; соблюдён HTTP-контракт |
| Нет approval, другой request, cancel, expiry, reissue, новый primary | Старое полномочие не позволяет complete; актуальный фактор не снимается |
| Отозваны operator membership/LOGIN, изменён пользователь/version/разрешённый primary | Approval не обходит текущие проверки; blocked/deleted аккаунт не восстанавливается |
| Неверный TOTP, reissue и обычный MFA login | Предел попыток и общий guessing budget сохраняются; нет бесконечного перебора через новые requests |
| Два complete на разных экземплярах; complete одновременно с normal MFA login/password reset | Не более одного совместимого победителя, нет частичного replace/audit/notification или двух наборов codes |
| Redis недоступен перед start/complete | Fail-closed, 503 по контракту; фактор/сессии не меняются. После восстановления допустим повтор только актуального flow |
| SMTP недоступен после completion | Замена уже совершена, job сохранена; bounded retries, затем retained failed job, без повторной смены MFA |
| Остановка delivery во время lease, затем restart | Нет потери job; lease позволяет повторную обработку. Возможное повторное письмо не повторяет auth mutation |
| Отключение recovery после commit | Новые routes закрыты, ранее committed уведомления продолжают отправляться |
| Потеря HTTP-ответа после commit | Нет повторной выдачи codes через replay. Владелец входит новым TOTP и использует существующую protected regeneration |

Сбои моделировать управляемо, не удалением таблиц или ослаблением ограничений. Для SQL commit/rollback сначала использовать существующие изолированные integration tests; не внедрять аварийные SQL hooks в приложение. После неоднозначного результата сверять несекретные audit/метаданные, не выполнять слепое повторное одобрение. Разбор и адресный retry failed job — только по runbook отдельным DBA-полномочием.

## Что уже подтверждено локально

Источники результатов — [history, 13.1d.1–d.3](../planning/history.md), а не повторный запуск при составлении этого документа:

- Unit/HTTP: gates, JSON/Origin/cookies, ошибки, guessing budget и Redis failure через test double; CLI exact confirmation и санитизация ошибок.
- Disposable PostgreSQL: restricted runtime/operator grants, recheck operator identity/membership, rollback, replay/races, outbox lease/backoff/exhaustion и HTTP → SQL approval → completion. Это не запуск реального браузера и CLI оператором в HTTPS-окружении.
- SMTP transport: локальный protocol fixture; SQL delivery faults: test double и контролируемые состояния lease. Это не доставка через внешний SMTP и не реальная остановка процесса.

Эти проверки не доказывают независимость человеческой проверки владельца, работу authenticator/браузера/внешней почты, TLS/secret manager или поведение нескольких развёрнутых экземпляров при сетевых сбоях.

## Фиксация результата

Для каждого случая записать PASS / FAIL / NOT RUN, время, commit, конфигурацию без секретов, тестовый request UUID, ожидаемый и фактический результат, ссылку на обезличенное evidence и ответственного. На 15 октября 2026 **все внешние случаи выше — NOT RUN**: окружение и участники не предоставлены для этого захода.

Перед закрытием 13.1d.4 нужны результаты основного сценария, применимых отказов и операторской процедуры; устранённые FAIL и явно зафиксированные ограничения выпуска. Отложенные primary methods не объявлять проверенными. Нагрузку/RPS, длительный memory/GC profiling и общий production readiness оценивать отдельно по [performance](performance.md) и финальной приёмке, не по одному recovery flow.

После drill восстановить тестовые зависимости и flags, отозвать временные operator grants, убрать тестовые secrets/codes по принятой процедуре и проверить отсутствие оставленных failed jobs без владельца инцидента. Общую БД и очереди не очищать.
