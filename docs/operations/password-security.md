# Политика паролей и обновление хешей

## Новые пароли

Проверка `domain.ValidatePassword` применяется один раз в service: register, change,
reset, activation, protected recovery и завершение временного пароля.
HTTP проверяет формат запроса и переводит ошибки, но не повторяет политику.
Существующий контракт сохранён: 8–128 байт, буква, цифра и заглавная буква.
Пароли не обрезаются и не нормализуются. Периодическая смена не введена.
Login и reauthentication проверяют существующий пароль, не новую политику.

Файловый blocklist и встроенный список из 24 паролей удалены по согласованному
упрощению A1. Нет файла, env, дополнительного policy-пакета или lookup.
Проверка распространённых/скомпрометированных паролей отложена: пароль вроде
`Password1` проходит нынешнюю проверку состава, поэтому защита от угадываемых
паролей ниже, чем с полноценным blocklist. Не выдавать длину/состав за проверку
утечек; distributed limits и hash resource budget сохранены.

Register возвращает существующие ошибки длины/состава; остальные сценарии —
400 `password_policy`. Ошибки `password_blocked` больше нет.
Сохранённые пароли/аккаунты массово не меняются.

## Argon2id и rehash

Новый профиль: v19, memory 65536 KiB (64 MiB), time 3, parallelism 4,
salt 32 байта, key 32 байта. Старый профиль time 1 / parallelism 32 /
key 256 байт проверяется по параметрам сохранённого PHC, без массового update.
Parser строго проверяет формат/version/числа/base64 и ограничивает выделение
памяти: memory ≤256 MiB, time ≤10, parallelism 1–32, salt 8–64, key 16–256.

После успешного обычного password login слабый профиль обновляется:

1. Проверка старого хеша через общий bounded hash budget.
2. Генерация replacement вне SQL transaction и без проверки нового пароля.
3. User lock + active/version check, CAS старого хеша.
4. Создание сессии с исходной auth_version и обычными проверками актуальности.

Сравнение стоимости консервативное: если старый memory или time выше target,
rehash пропускается, чтобы не понизить стоимость. Изменение parallelism само
по себе не повод для rehash; длинные salt/key не требуют сокращения.
При обновлении старого time 1 профиль целиком становится новым.
Неизменный профиль не получает GenerateHash или дополнительный SQL.

Если hash budget занят на шаге 2, необязательное обновление пропускается:
вход разрешается после обычной проверки сессии, rehash повторится позднее.
Cancellation/ошибки генерации/SQL прерывают вход; сессия не создаётся.
Два параллельных rehash сохраняют первый CAS winner. Reset/change/block/delete
меняют version/status под user lock: старый rehash не возвращает старый пароль
или доступ. Rehash сам не увеличивает auth_version, не отзывает сессии и не
создаёт событие смены пароля. CAS-конфликт change-password с параллельным rehash
может потребовать повторить change-password; проверки authority не ослаблены.

## Границы приёмки

Это не заявление полного соответствия NIST: существующие 8 байт и composition
правила отличаются от его современной рекомендации. До release отдельно
согласовать минимальную длину для password-only/MFA. Проверка утечек —
отдельное отложенное расширение, не реализованная гарантия текущего сервиса.
Password managers/paste и UI ошибки проверяются при реализации UI.

Новый time cost увеличивает CPU на новых/обновляемых паролях; первый вход старым
хешем может выполнить два Argon2 вычисления. Shared non-queued budget сохранён.
Для обычного нового профиля одновременно занято до 64 MiB на hash slot; legacy
compare может потребовать до parser bound 256 MiB на slot, плюс остальной runtime.
Реальная mixed API capacity, P95/P99, память/GC и CPU — этапы 6.8b/6.8c,
не результат unit/SQL/fuzz тестов.

Основания: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
для upgrade при успешном входе и [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
описывает требования к политике, которым текущий сервис полностью не соответствует.
Argon2 API сверено с установленным x/crypto v0.56.0
через `go doc`: Context7 не нашёл документацию нужного пакета.
