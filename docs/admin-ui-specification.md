# Возможности Auth и требования к будущему интерфейсу

Дата сверки: **11 ноября 2026**. U2 source foundation подготовлен14 ноября: [режимы, migration и ограничения](features/settings-source.md); целевая проверка Luna завершена. Новое поле source в settings read и read-only отказ ENV описаны отдельно от будущих installer/UI.

Что доработать для управления почти всеми повседневными настройками из панели: [план U1–U7](planning/ui-management.md). Это будущие изменения, а не дополнение к перечню уже реализованных API.

**Согласованное будущее требование, 13 ноября:** два режима — прикладная конфигурация через ENV без UI либо сохраняемые настройки через management API с нашей панелью, UI CRM или прямым API-клиентом. В управляемом режиме — defaults и генерация собственных секретов; снаружи только необходимая конфигурация запуска и получение корневых ключей. Внешние provider credentials вводит владелец. Это ещё не реализованный переключатель. [Источники настроек и границы](planning/ui-management.md#11-два-режима-управления--согласовано-13-ноября).

**Дополнение к будущим требованиям:** управляемая установка без ручного ENV, генерация и защищённое сохранение внутренних секретов, UI/API операции безопасной смены keys/DB credentials и независимое восстановление при недоступной панели. Владелец видит статус и управляет жизненным циклом, но не получает raw текущие секреты. Возможность смены внешних credentials зависит от делегированных полномочий. [Контракт и ограничения, ещё не реализованы](planning/ui-management.md#12-установка-и-управляемая-смена-секретов-без-ручного-env).

**Контракт будущей реализации U1, 14 ноября:** [полная классификация ENV, scope/defaults, установка, secrets, API semantics, матрица экранов и последовательность работ](planning/ui-u1-contracts.md). Этот контракт уточняет планируемое поведение; существующие методы и их ограничения в разделах ниже не меняются до реализации.

Документ предназначен владельцу продукта, дизайнеру и разработчику будущего UI. Он описывает существующий backend понятными пользовательскими действиями: какие экраны нужны, что на них показывать и какие ограничения учитывать. Это описание возможностей, а не разрешение начинать реализацию интерфейса.

Текущее поведение сверено с обработчиками, маршрутизацией, DTO и документами фич. Наличие маршрута в Swagger не означает, что он включён в каждом проекте: нужны разрешённый метод, готовые зависимости и подходящий режим запуска. Старые разделы документации с описанием прошлых этапов могут отличаться от действующего кода.

## 1. Как устроен продукт

Это единый backend авторизации с несколькими вариантами использования.

| Вариант | Что получает владелец проекта |
| --- | --- |
| Обычный сайт | Пользователи регистрируются и входят разрешёнными способами |
| Закрытый сервис или админка | Самостоятельная регистрация закрыта; доступ выдаёт администратор |
| Auth для CRM или другого backend | Auth определяет пользователя; бизнес-данные остаются в CRM. Роли можно хранить в CRM либо использовать роли и permissions Auth |
| Несколько независимых проектов | Одна общая панель управляет проектами; у каждого свои пользователи, политики и проектная БД |
| Browser-приложение | Вход через защищённую cookie-сессию |
| Приложение или внешний API | Access JWT и, для поддержанных native-сценариев, refresh token |

### 1.1. Три разных участника

**Пользователь проекта** входит на сайт или в приложение. Он управляет своей безопасностью и своими сессиями.

**Администратор проекта** управляет пользователями, ролями и настройками конкретного проекта в пределах выданных permissions.

**Оператор общей панели** управляет каталогом проектов и доступными общепанельными операциями из отдельной административной сессии. Владелец общей панели имеет дополнительные полномочия. Эта сессия не превращается в пользовательскую сессию любого проекта.

В UI нельзя смешивать «Моя безопасность», «Пользователи проекта» и «Администраторы общей панели»: это разные владельцы данных и разные полномочия.

### 1.2. Данные и изоляция

- Общая БД содержит каталог проектов, данные общей панели, её администраторов и служебные сведения подключения.
- У проекта отдельная БД пользователей, сессий, ролей и проектных настроек.
- Одинаковые email или UUID в разных проектах не означают один общий аккаунт.
- PostgreSQL определяет действительность сессий и прав. Redis используется для распределённых ограничений и защиты ресурсов.
- Наличие общей панели не означает SSO для пользователей разных проектов. Общий пользовательский SSO отложен.

**Для макета:** выбранный проект должен быть постоянно виден. На опасных действиях показывать его название повторно. Не переносить пользователя или роль в другой проект через простое переключение селектора.

## 2. Какие интерфейсы нужны

Это предложенная навигация, а не требование создать все страницы сразу.

### 2.1. Общая административная панель

- Вход оператора, второй фактор и восстановление.
- Первичная настройка владельца, когда установка ещё не инициализирована.
- Список проектов и карточка проекта.
- Состояние подготовки и готовности проекта.
- Пользователи выбранного проекта и их текущие назначения.
- Роли выбранного проекта и доступные общепанельные операции с ними.
- Администраторы/безопасность общей панели в пределах реально существующих API.
- Собственная безопасность оператора.

**Не выдавать желаемое за готовое:** графики посещаемости, число пользователей онлайн, история всех действий и сводные бизнес-метрики требуют подходящих read API. Наличие SQL-аудита не означает готовый dashboard или журнал в UI.

### 2.2. Настройки конкретного проекта

Предлагаемые вкладки:

1. Общее состояние и готовность.
2. Способы входа и регистрация.
3. Второй фактор.
4. Пользователи.
5. Роли и разрешения.
6. Email и SMTP.
7. Google и Telegram.
8. Сессии и JWT.
9. Сроки хранения данных.
10. Техническое подключение и ограничения, доступные администратору.

Не все вкладки уже имеют полноценные изменяемые API. Различия перечислены ниже.

### 2.3. Пользовательские страницы

- Вход; регистрация, если разрешена.
- Ввод email-кода.
- Второй фактор после входа; первичная обязательная настройка фактора.
- Подтверждение email и повторное письмо.
- «Забыл пароль» и установка нового пароля.
- Активация приглашения; замена временного пароля.
- Смена email, сообщение «это не я», защитное восстановление.
- Собственные устройства и выход.
- TOTP, резервные коды, email/Telegram как второй фактор, предпочитаемый метод.
- Привязка/отвязка Google и Telegram, если пользователь соответствует ограничениям backend.

## 3. Публичный вход и регистрация

### 3.1. Вход по email и паролю — API есть

Поля: **email**, **пароль**. Действия: «Войти», «Забыли пароль?», переход к регистрации, если она разрешена.

Backend может вернуть:

| Ответ | Что делает UI |
| --- | --- |
| `200` | Вход завершён; браузер получил HttpOnly session cookie |
| `202` | Первый шаг пройден, но вход ещё не завершён: показать нужный второй фактор или обязательную настройку |
| `403 email_not_verified` | Объяснить необходимость подтверждения и предложить повторное письмо |
| `404 method_disabled` | Метод недоступен; не показывать успешный вход или бесконечный повтор |
| Неверные данные | Общая ошибка входа без раскрытия состояния чужого аккаунта |
| `429` / `503` | Пауза/временная недоступность; учесть `Retry-After` |

**API:** `POST /api/v1/auth/login/email`.

Выключение парольного способа запрещает новые входы, но само по себе не равно выходу всех ранее вошедших пользователей. Для отзыва доступа есть отдельные операции.

### 3.2. Самостоятельная регистрация — API есть

Поля backend: **email**, **пароль**. Поле повторения пароля можно добавить в форму как локальную помощь пользователю; register API его не принимает. Не добавлять в JSON имя, телефон, роль или признак администратора: действующий контракт не содержит их.

Проверка пароля: 8–128 байт, минимум буква, цифра и заглавная буква. UI помогает выполнить условия, окончательное решение принимает backend.

Поведение зависит от настройки подтверждения email:

| Режим | Что произойдёт |
| --- | --- |
| Подтверждение обязательно | Аккаунт создан; `201` содержит `verificationRequired=true`, сессия не выдаётся. Показать «Проверьте почту» |
| Подтверждение необязательно | Аккаунт создан; выдаётся сессия, ставится письмо подтверждения |
| Подтверждение отключено | Аккаунт создан; автоматическое письмо не ставится. Адрес от этого не становится подтверждённым |
| Саморегистрация запрещена | Пользователь не может создать аккаунт этой ручкой |

**API:** `POST /api/v1/auth/register/email`.

После создания аккаунта возможен отдельный сбой выдачи сессии или ответа. Не повторять регистрацию бесконечно: аккаунт мог уже сохраниться. Предложить вход или восстановление.

### 3.3. Вход по одноразовому email-коду — API есть, с ограниченным профилем

1. Пользователь вводит email.
2. Нажимает «Получить код».
3. В том же браузере вводит восьмизначный код из письма.
4. При необходимости проходит дополнительный фактор; после успешного завершения получает сессию.

**API:** `POST /api/v1/auth/email-otp/request`, `POST /api/v1/auth/email-otp/confirm`.

Это **вход**, не подтверждение email и не второй фактор. Текущая реализация предназначена для существующего активного пользователя с подтверждённым login email и постоянными парольными credentials. Она не создаёт нового пользователя и не добавляет парольный метод Google-only/Telegram-only аккаунту.

Код вводится в исходном браузере: используется отдельная flow cookie. Сохранять ведущие нули. Повторная выдача заменяет прежний код. Общий ответ «Если вход доступен, мы отправим код» не подтверждает наличие аккаунта или доставку.

### 3.4. Google и Telegram — API есть при готовом провайдере

Кнопка «Войти через Google» или «Войти через Telegram» начинает защищённый переход к соответствующему провайдеру. Текущая реализация использует OIDC, а не произвольный OAuth-провайдер по введённому URL.

- Начало: `POST /api/v1/auth/google/start` / `/telegram/start`.
- Завершение: `GET /api/v1/auth/google/callback` / `/telegram/callback`.
- UI использует URL, который вернул backend; не формирует произвольный redirect и не подставляет чужой callback.
- Завершение связано с исходным браузерным процессом. Истёкший или повторный callback не является новым входом.
- В зависимости от политики новый внешний аккаунт может быть создан, либо саморегистрация будет запрещена.
- Пользователь определяется связкой провайдер + его уникальный идентификатор. Совпадение email не объединяет аккаунты.
- При требуемом MFA вход не заканчивается одним успешным ответом провайдера.

Google и Telegram — отдельные переключатели и отдельные секреты. Telegram-вход и Telegram-бот для второго фактора — разные подключения.

## 4. Почта, пароль и восстановление

### 4.1. Подтверждение email

Экран: адрес/пояснение, кнопка подтверждения, состояния «Ссылка истекла» и «Запросить новое письмо».

- `POST /api/v1/auth/email/resend` — запросить письмо.
- `POST /api/v1/auth/email/verify` — подтвердить токен.
- Открытие ссылки само ничего не меняет: frontend выполняет явный POST после действия пользователя.
- Подтверждение не создаёт новую сессию и не меняет пароль.
- `202 accepted` при запросе письма не доказывает существование адреса или доставку.

### 4.2. Забытый пароль

Экран 1: email и «Отправить ссылку». Экран 2: новый пароль и повторение. Экран 3: результат и переход ко входу.

- `POST /api/v1/auth/forgot-password` принимает email.
- `POST /api/v1/auth/reset-password` принимает `token`, `newPassword`, `confirmPassword`.
- Успех меняет пароль и отзывает сессии; автоматического входа нет.
- Reset не снимает произвольную административную блокировку, не подтверждает email и не создаёт пароль у внешнего аккаунта без парольных credentials.
- Неизвестный, истёкший и уже использованный токен не должны давать UI возможность различать чужие аккаунты.

### 4.3. Смена известного пароля

Поля: текущий пароль, новый пароль, повторение нового. `POST /api/v1/auth/change-password`.

Нужны действующая сессия и допустимое состояние аккаунта, включая подтверждённый email. После успеха сессии отзываются, пользователь входит заново. Предупреждение об этом показать до отправки формы.

### 4.4. Смена email с защитой старого владельца

Это отдельный сценарий, а не прямое редактирование строки email в профиле.

1. Владелец запрашивает смену на новый адрес с подтверждением текущего пароля/свежести действия.
2. Новый адрес получает письмо подтверждения; старый — уведомление безопасности.
3. До подтверждения вход остаётся по старому адресу.
4. Подтверждение нового адреса завершает смену и отзывает сессии.
5. Старый владелец может сообщить «Это не я» в допустимое окно.
6. До завершения смены такое сообщение отменяет запрос. После завершения — защитно блокирует аккаунт и запускает отдельное восстановление через старую почту.
7. Восстановление требует отдельного токена и нового пароля, а затем нового входа.

**API:** `/api/v1/auth/email/change`, `/confirm`, `/report`, `/recover` — POST.

Экран должен различать «смена ещё ожидает подтверждения», «смена завершена», «запрос отменён», «аккаунт защитно заблокирован» и «восстановление завершено». Не обещать восстановление без доступа к почте или после истечения защитного срока.

### 4.5. Первая почта для аккаунта Google/Telegram

Это контролируемая администратором операция, а не свободное поле «Добавить email».

- Администратор разрешает конкретный адрес для конкретного пользователя: `POST /api/v1/admin/users/{id}/email-binding`.
- Владелец, уже вошедший в этот аккаунт, подтверждает код: `POST /api/v1/auth/email/binding/confirm`.
- Нужен внешний аккаунт без прежних email/парольных credentials и без несовместимого pending-состояния.
- Администратор не получает почтовой код и не подтверждает адрес за владельца.
- После успеха сессии владельца отзываются; роли, пароль и новый способ входа автоматически не создаются.

### 4.6. Экран по ссылке из письма

Для verification/reset используются query-токены, для invitation/email-change есть fragment-токены. Разбирать нужно формат конкретного сценария. Токен нельзя выводить в логи, аналитику, сторонние запросы или хранить как обычную настройку.

После чтения убрать секрет из видимого URL. Переход по ссылке показывает экран; изменение выполняется явным действием и POST. Нужны состояния «уже использовано», «истекло/недействительно» и понятный следующий шаг без раскрытия лишних деталей.

## 5. Личный кабинет и устройства

### 5.1. Что известно о текущем пользователе

`GET /api/v1/auth/me` сейчас возвращает `userId` и `sessionId`. `GET /api/v1/auth/access` — эффективные permissions.

**Ограничение для дизайна:** это не готовое API полного личного профиля. Не считать, что из `/me` уже можно получить ФИО, аватар, телефон, произвольные поля CRM или редактировать их. Список/карточка пользователей в административном API — другой сценарий с отдельными правами.

### 5.2. Список устройств и выход

| Действие | API | Что показать |
| --- | --- | --- |
| Посмотреть свои активные сессии | GET `/api/v1/auth/sessions` | Устройство/User-Agent, IP, доступные даты и отметка текущей сессии по данным ответа |
| Следующая страница | Тот же GET с `before` | Подгрузка по cursor, не придуманная offset-пагинация |
| Завершить одну сессию | DELETE `/api/v1/auth/sessions/{id}` | Подтверждение; при завершении текущей — экран входа |
| Выйти здесь | POST `/api/v1/auth/logout` | Завершить текущую сессию |
| Выйти везде | POST `/api/v1/auth/logout-all` | Предупредить о выходе на всех устройствах |
| Повернуть секрет сессии | POST `/api/v1/auth/session/rotate` | Техническая операция, обычно без отдельной пользовательской кнопки |
| Передать интерактивную активность | POST `/api/v1/auth/session/activity` | Техническая часть поддержанного сценария; не имитировать активность фоновым вечным ping |

Список собственных сессий ограничен страницами до50 записей. Секреты сессий наружу не возвращаются. «Выйти везде» не равно «Заблокировать пользователя»: разрешённый новый вход остаётся возможным.

### 5.3. Повторное подтверждение личности

Чувствительное действие может попросить пароль и/или второй фактор, хотя пользователь уже вошёл.

- `POST /api/v1/auth/reauthenticate/password` — повторить текущий постоянный пароль; возвращает срок свежего подтверждения и обновляет cookie.
- `POST /api/v1/auth/mfa/step-up` — подтвердить дополнительный фактор для чувствительного действия.
- `/api/v1/auth/reauthenticate/email/request` и `/confirm` — отдельный поддержанный email-proof для управления MFA; это не универсальная замена пароля или строгого фактора.

В макете нужен переиспользуемый диалог «Подтвердите действие». Backend решает, какое доказательство подходит. Обычный вход и наличие роли администратора не означают бессрочное разрешение на опасные операции.

### 5.4. Привязанные Google/Telegram-аккаунты

- `POST /api/v1/auth/{provider}/link` начинает привязку.
- Общий callback завершает её в исходном браузерном процессе.
- `DELETE /api/v1/auth/{provider}/link` отвязывает аккаунт.

Ограничения действующей реализации: link/unlink требуют постоянного пароля и свежего парольного подтверждения. При отвязке backend требует сохранить пригодный парольный вход, включая актуально включённый password method и подтверждённые credentials. Простое наличие ещё одного внешнего провайдера не является универсальным разрешением на отвязку.

Для Google-only/Telegram-only пользователя нельзя рисовать безусловно доступную кнопку отвязки. При успешной отвязке сессии отзываются. Отдельного безусловного «отвязать всё от лица администратора» здесь нет.

## 6. Второй фактор и безопасность пользователя

### 6.1. Что поддержано

| Способ | Назначение | Важное различие |
| --- | --- | --- |
| TOTP | Коды из приложения-аутентификатора, например Google Authenticator | Основной строгий дополнительный фактор |
| Резервные коды | Одноразовый запасной способ при потере TOTP | Показываются при выдаче; использованный код повторно не работает |
| Email как MFA | Код на подтверждённую почту после пароля | Только отдельный разрешённый проектный профиль; не равен TOTP по уровню доверия |
| Telegram как MFA | Код в подготовленном приватном чате с ботом после пароля | Отдельный Bot API канал; не равен Telegram-входу и строгому TOTP |

SMS/телефонный второй фактор не реализован. Произвольные приложения «как Google Authenticator» не являются отдельными провайдерами: они работают с одним стандартом TOTP.

### 6.2. Личная страница «Безопасность»

Показывать фактическое состояние, а не только желаемые переключатели:

- подключён ли TOTP;
- сколько резервных кодов осталось;
- требуется ли MFA политикой проекта, ролью или административным статусом;
- разрешено ли отключение;
- есть ли постоянный пароль и подтверждённая почта;
- нужны ли свежие парольное и MFA-подтверждения;
- состояние email/Telegram-факторов через их отдельные status API;
- предпочтительный способ: автоматически, TOTP, email или Telegram, если доступны.

Источники: `GET /api/v1/auth/mfa/status`, `/mfa/email`, `/mfa/telegram`, `/mfa/preference`. Общий status не заменяет все отдельные ответы.

### 6.3. Подключение и замена TOTP

1. Подтвердить допустимые текущие proofs.
2. Начать настройку: `/mfa/totp/enrollment`.
3. Показать QR/секрет только в защищённом процессе настройки, не как постоянно читаемое поле карточки пользователя.
4. Ввести текущий шестизначный код и завершить `/mfa/totp/enrollment/confirm`.
5. Показать выдаваемые резервные коды; предложить безопасно сохранить их.

Отдельные операции: protected replacement (`/mfa/totp/replacement`, `/confirm`), отключение (`DELETE /mfa/totp`), перевыпуск recovery codes (`POST /mfa/recovery-codes/regenerate`). Во всех путях префикс `/api/v1/auth`.

Отключение и замена могут отзывать действующие credentials. Последний обязательный фактор нельзя удалить обычным переключателем. Администратору не должна быть доступна кнопка чтения чужого TOTP-секрета или резервных кодов.

### 6.4. Подключение email/Telegram как второго фактора

Общий пользовательский процесс: **проверить владение каналом → отдельно включить фактор → при необходимости заново войти**.

Email: подготовка `/mfa/email/preparation`, подтверждение `/confirm`, затем включение `/mfa/email`. Нужна принадлежащая пользователю подтверждённая почта и допустимый парольный профиль.

Форма подготовки email передаёт `email`; подтверждение — `binding` и `code`. Включение/отключение самого подготовленного email/Telegram-фактора не требует придуманного JSON с Telegram ID или чужим userId: владелец и подтверждённая подготовка определяются backend.

Telegram: `/mfa/telegram/preparation` возвращает временную ссылку на бота и binding; пользователь открывает бота, получает код, вводит его в исходном браузере через `/preparation/confirm`, затем отдельно включает `/mfa/telegram`. Простое открытие ссылки не подключает фактор.

Подключение/замена/удаление защищены proofs, актуальной политикой и версиями. Включение может отозвать сессии. Подготовленный канал — ещё не включённый второй фактор.

### 6.5. Второй фактор при входе

После `202` UI показывает метод и срок challenge. До успешного завершения нельзя открывать защищённый продукт как для вошедшего пользователя.

- TOTP/recovery/Telegram завершаются подходящим `/mfa/login/complete`.
- Email использует отдельные `/mfa/email/login` и `/mfa/email/login/complete`.
- При обязательном первом подключении TOTP используются `/mfa/login/enrollment` и `/confirm`.
- Для native-токенов существуют отдельные completion/enrollment API; browser-cookie challenge нельзя перенести туда.

В текущем проектном профиле email и Telegram допускаются как дополнительный фактор после **пароля**. Email-код + email-код не считается независимой MFA; Telegram-вход + Telegram-код также не разрешён этой политикой. Административные и строгие операции не открываются одним слабым email/Telegram proof.

### 6.6. Предпочтительный метод

`GET/POST /api/v1/auth/mfa/preference`. Значения: `totp`, `email`, `telegram`; пустая строка означает автоматический выбор.

Это текущий проектный API. Аналогичная публикация preference в standalone/общей панели не подтверждена; наличие общего MFA engine не добавляет туда этот маршрут автоматически.

Автоматический порядок: TOTP → email → Telegram. Выбрать можно подключённый и допустимый фактор; политика имеет приоритет над предпочтением. Недоступный выбранный канал не означает скрытый обход MFA через другой метод. При удалении выбранного фактора предпочтение может сбрасываться в автоматическое.

### 6.7. Потерян второй фактор

Отдельные сценарии:

1. Войти с одноразовым резервным кодом, если он сохранён.
2. Для поддержанного процесса запросить восстановление: `/mfa/recovery/login`, `/mfa/recovery/start`, `/mfa/recovery/complete`.
3. Получить отдельное независимое одобрение recovery-оператора по защищённой эксплуатационной процедуре.
4. Подключить новый TOTP и сохранить новые резервные коды; войти заново.

Это не кнопка «снять MFA без проверки». Обычный runtime не одобряет сам себя. Потеря всех факторов не превращает email-ссылку в универсальный обход; часть восстановления требует offline/CLI-действия, а не готовой UI-ручки.

## 7. Общая панель и проекты

### 7.1. Первый запуск и первый владелец

**API есть для первичной настройки установки**, но это не повторяемый способ создать ещё одного администратора.

1. Включённый setup получает доверенный секрет установки `X-Setup-Token` и разрешённый Origin. Этот секрет нельзя заранее вшивать в публичный frontend.
2. `POST /api/v1/setup/start`: `email`, `password`, необязательный `mfaMode`.
3. На почту приходит код. Если выбран режим с обязательной MFA, backend также возвращает материал настройки TOTP.
4. `POST /api/v1/setup/complete`: `token`, `emailCode`, подходящий `totp`.
5. Создаётся первый владелец и фиксируется факт завершённой установки. При подключении TOTP выдаются резервные коды.
6. Автоматического входа нет — далее обычный вход.

`mfaMode`: `optional`, `administrators`, `required`; по умолчанию `administrators`. При `optional` первый владелец может завершить setup без TOTP; технический MFA-компонент при этом должен быть доступен.

**Для макета:** секрет установки, email, пароль, режим MFA → подтверждение почты/при необходимости TOTP → сохранение резервных кодов → вход. Состояние «Установка уже завершена» закрывает процесс. Перезапуск, потеря пароля или удаление владельца не открывают setup заново. Публичного GET «установка завершена?» в текущем контракте нет.

У независимого проекта owner-managed режим не означает обязательное создание копии оператора в каждой проектной БД. Техническая подготовка проекта и первичная настройка владельца общей панели — разные процессы.

### 7.2. Список и карточка проектов — API есть

`GET /api/v1/platform/projects`, `GET /api/v1/platform/projects/{id}`.

| Данные | Что показать |
| --- | --- |
| `id` | Постоянный UUID проекта |
| `slug`, `name` | Техническое короткое имя и отображаемое название |
| `origin` | Доверенный HTTPS-адрес проекта |
| `desiredState` | `enabled` — разрешён; `suspended` — приостановлен |
| `phase` | `pending`, `provisioning`, `failed`, `ready` — стадия подготовки |
| `version`, `generation` | Служебные версии для безопасных команд, не редактируемые поля |
| `createdAt`, `updatedAt` | Даты |

Фильтр списка: `phase`; размер страницы `limit` 1–100, default50; следующая страница `before=nextCursor`. Не реализованы серверные поиск по имени, произвольные сортировки, total count и фильтр `desiredState`.

Две независимые подписи: **готовность** и **приостановка**. Проект `ready + suspended` подготовлен, но закрыт для доступа. `ready` не доказывает исправность реального SMTP, Google/Telegram, DNS/TLS или наличие UI.

### 7.3. Создание проекта — API есть для регистрации намерения

`POST /api/v1/platform/projects` принимает:

| Поле | Назначение |
| --- | --- |
| `operationId` | UUID команды, сохраняемый при повторе того же действия |
| `slug` | DNS-safe короткое имя, 1–63 байта; зарезервированные имена запрещены |
| `name` | Название, до200 байт UTF-8 |
| `reason` | Причина/служебное пояснение, до500 байт, без секретов |

Origin строит backend из slug и настроенного домена. Браузер не задаёт DSN, имя физической БД, storage target, credentials, готовность или UUID владельца.

Успех создаёт **каталоговую запись `pending`**, а не автоматически готовый сервис. Повтор того же operation ID с тем же действием возвращает прежний результат, не второй проект.

### 7.4. Подготовка и готовность — существующая эксплуатационная возможность

Уже есть привилегированный `cmd/project-prepare`: отдельная БД, SQL-роли, схема, ключи, технические credentials, managed/onboarding configuration и проверки. Это существующий backend/CLI-процесс.

**Но обычного HTTP «Подготовить проект полностью» пока нет.** Создание записи, retry и CLI preparation — не одна готовая команда из UI. Backend-основы не равны автоматическому мастеру «нажал создать → БД и все настройки уже готовы». В текущей общей панели нельзя обещать кнопки `/prepare` или `/activate`, которых нет в router.

Для будущего полностью UI-управляемого создания нужны отдельные согласованные orchestration/management API и отображение их результата. Не запускать DDL, shell или чтение технического DB-пароля из браузера.

### 7.5. Приостановка, возобновление, повтор — API есть

| Действие | API | Смысл |
| --- | --- | --- |
| Приостановить | POST `/api/v1/platform/projects/{id}/suspend` | Закрыть проектный доступ; данные сохраняются |
| Возобновить | POST `/api/v1/platform/projects/{id}/resume` | Снять приостановку; прежняя стадия подготовки сохраняется |
| Повторить подготовку | POST `/api/v1/platform/projects/{id}/retry` | Для подходящего failed-проекта вернуть намерение в pending; не гарантирует запуск физического executor |

Тело: `operationId`, `expectedVersion`, `expectedGeneration`, `reason`. Нужны соответствующие platform permissions и свежие доказательства. `resume` не является восстановлением резервной копии.

### 7.6. Удаление/восстановление проекта — пока план

HTTP удаления физического проекта, корзины, preview удаления и restore в текущем operator router нет. **Приостановку нельзя назвать удалением.**

Согласованное пожелание для будущего UI: только подтверждённый владелец; точное имя проекта; предупреждение о пользователях и потере данных; дополнительные подтверждения для непустого проекта; fresh proofs; отдельный привилегированный executor. Ownership, сроки отмены и backup/restore нужно согласовать до реализации. Готовой кнопки «Восстановить удалённую БД» нет.

### 7.7. Операторы общей панели

Есть отдельный вход/authority и политика безопасности операторского контура. Основные permissions:

- `platform.projects.read` / `platform.projects.manage`.
- `platform.project_users.manage`.
- `platform.project_access.manage`.
- `platform.project_settings.manage`.
- `platform.operators.manage` — ключ существует, но **полноценный HTTP CRUD команды операторов не реализован**.

Наличие permission key не означает существующую форму создания оператора. Первый владелец получает права через setup; проектный `super_admin` не становится оператором общей панели.

`GET/POST /api/v1/platform/settings/mfa` меняет MFA-политику самой общей панели. Она не является общей строкой настроек для всех проектов.

### 7.8. Если владелец панели потерял доступ

- Обычное восстановление пароля — через почту при допустимом профиле.
- Если почта недоступна, существует защищённый `cmd/admin-recovery` с явным выбором platform realm и отдельными техническими полномочиями. Новый пароль не снимает MFA.
- Потеря фактора и всех резервных кодов требует независимого recovery-одобрения; CLI `mfa-approve`/`mfa-cancel` не превращены в общую кнопку «сбросить MFA» в панели.
- Если потеряны пароль и фактор, это два этапа, а не повторный initial setup.

## 8. Пользователи и выдача доступа

### 8.1. Список пользователей — API есть

Локально: `GET /api/v1/admin/users`. Из общей панели: `GET /api/v1/platform/projects/{id}/users`.

| Фильтр/поле | Поддержка |
| --- | --- |
| `status` | `pending`, `active`, `blocked` |
| `email` | Точное нормализованное совпадение, не поиск по части строки |
| `limit` | 1–100, по умолчанию50 |
| `before` | Cursor следующей страницы |
| `expectedVersion`, `expectedGeneration` | Дополнительно обязательны у platform project query |

Колонки: UUID, статус, дата создания, `displayName`, email, `emailVerified`. Имя/email могут отсутствовать. Поиск может найти сохранённый контакт, отличный от показанного предпочтительного email.

**Нет готовых:** поиска по имени/телефону, произвольных полей CRM, bulk-редактирования, экспорта, корзины удалённых и счётчика пользователей онлайн. Список не возвращает роли для каждой строки; не проектировать массовое N+1-чтение всех карточек ради таблицы.

### 8.2. Карточка пользователя — API есть

Локально: `GET /api/v1/admin/users/{id}`. Из общей панели: `GET /api/v1/platform/projects/{id}/users/{userId}` с project revisions.

| Группа | Данные ответа |
| --- | --- |
| Основные | `id`, `status`, `displayName`, `email`, `emailVerified`, `createdAt`, `deletedAt` |
| Состояние безопасности | `passwordConfigured`, `temporaryPasswordRequired`, `mfaEnrolled` |
| Контакты | `contacts[{email,verifiedAt}]` |
| Внешние аккаунты | `externalIssuers[]`, без секретного provider subject |
| Роли | `roles[{id,key,name,system,version}]` |
| Версии | `authVersion`, `accessVersion` |

Встроенный список ролей карточки не содержит полный набор их permissions и `mfaRequired`: для этого нужен role detail. Сохранённый `passwordConfigured` или `mfaEnrolled` не гарантирует, что этот способ сейчас разрешён настройками.

Нет просмотра текущего/временного пароля, hashes, recovery codes, TOTP secret или raw tokens. Карточка по UUID может вернуть сохранённую tombstone удалённого аккаунта; это не возможность восстановить его.

### 8.3. Создать пользователя без отправки приглашения

`POST /api/v1/admin/users`: `idempotencyKey`, необязательный `email`, `invite:false`.

Создаёт pending-пользователя. Не создаёт постоянный пароль, действующую сессию или роль. Роли назначаются отдельно. В существующем create DTO нет имени, телефона, готового пароля, `verified` или произвольных profile fields.

Для формы важно не писать «Доступ уже работает», если создан только pending UUID.

### 8.4. Приглашение по почте

Та же ручка с `invite:true` и email. Backend ставит письмо в доставку; plaintext token не возвращается администратору.

- Перевыпуск: `POST /api/v1/admin/users/{id}/invitation`, новый `idempotencyKey`.
- Активация владельцем: `POST /api/v1/auth/invitations/activate`.
- Форма активации: `token` из приглашения, `password`, `confirmPassword`.
- Новая ссылка отменяет предыдущую; повтор исходной idempotent-команды не является «отправить ещё раз».
- Активация сама не назначает роль и не выдаёт сессию; пользователь затем входит.

Показать «Приглашение принято к отправке», а не безусловное «Письмо доставлено».

### 8.5. Временный пароль

Создание: `POST /api/v1/admin/users/temporary-password` с `idempotencyKey,email`. Перевыпуск: `POST /api/v1/admin/users/{id}/temporary-password` с `idempotencyKey`.

Пароль генерирует сервер, а не администратор. Первая выдача возвращает `userId`, `expiresAt`, `password`; повтор команды не возвращает plaintext снова. Нельзя обещать кнопку последующего «Посмотреть пароль».

Пользователь вводит временный пароль в специальном процессе:

1. `POST /api/v1/auth/temporary-password/login` — начать обязательную установку.
2. `POST /api/v1/auth/temporary-password/complete` — завершить установку постоянного пароля с требуемыми доказательствами.
3. До завершения временный пароль не является обычным полноценным доступом. Сам временный пароль не подтверждает email.

Reissue работает для подходящего pending temporary account, а не как сброс пароля любого active-пользователя. Старый временный пароль/незавершённая установка перестают работать. Безопасную передачу получателю организует администратор; plaintext не писать в журнал действий/аналитику.

Первая форма передаёт `email,password` временного входа; завершение — выданный `token`, новый `password`, `confirmPassword`. Не подменять их полями `newPassword` из другого reset API: названия контрактов различаются.

### 8.6. Блокировка, разблокировка, удаление

| Действие | Локальный API | Данные |
| --- | --- | --- |
| Заблокировать | POST `/api/v1/admin/users/{id}/status` | `status:"blocked"`, `expectedAuthVersion` |
| Разблокировать | Тот же POST | `status:"active"`, `expectedAuthVersion` |
| Удалить аккаунт | DELETE `/api/v1/admin/users/{id}` | JSON `expectedAuthVersion` |

Права отдельные: `accounts.users.status.manage`, `accounts.users.delete`. Одного права чтения или создания недостаточно. Нужны актуальная сессия и допустимые fresh proofs; backend защищает последнего пригодного системного администратора.

Блокировка отзывает доступ. Разблокировка не оживляет прежние сессии и не заменяет активацию pending-пользователя. Удаление необратимо в текущем account API; это не корзина и не мгновенное удаление всех audit/reservation/backup-данных. Не рисовать «Восстановить пользователя» как существующую команду.

**Граница общей панели:** read bridge пользователей есть, но локальные create/invite/temp-password/status/delete не опубликованы под platform project users API. Для единой операторской панели этих действий потребуются отдельные доверенные management API. Platform cookie нельзя подставить в локальный endpoint проекта.

### 8.7. История действий и аудит

Backend ведёт security audit и receipts отдельных административных операций. Полноценного API просмотра всех audit events, истории входов/доставки и выгрузки журнала для панели не обнаружено. В макете такой журнал нужно пометить будущим, а не заполнять вымышленными данными из якобы готового endpoint.

Для собственных межбазовых role-операций есть read/reconcile результата, см. раздел9. Это не общий audit browser и не разрешение читать чужие операции.

## 9. Роли, разрешения и внешний backend

### 9.1. Модель доступа

**Permission** — конкретное разрешение, например `crm.orders.read`. **Роль** объединяет permissions. **Назначение** связывает роль с пользователем. Можно иметь несколько ролей; действующий доступ определяется backend, а не выбранной строкой UI.

- Собственные права: `GET /api/v1/auth/access` → `accessVersion`, `roleIds`, `permissions`.
- Права выбранного пользователя: `GET /api/v1/admin/users/{id}/access` при соответствующих полномочиях.
- Custom роль сама по себе не является новым методом входа.
- Не требуется использовать роли Auth для CRM: можно взять только идентификацию, а бизнес-роли хранить в CRM.

### 9.2. Каталог разрешений — чтение через API, изменение deployment

`GET /api/v1/admin/permissions` возвращает `permissions[{key,name,description,group}]`.

В UI можно группировать и искать **полученные** permissions, выбирать их для роли. Но ручки «Создать permission», runtime upload/import, URL-синхронизации с внешним backend или hot reload каталога **пока нет**. Definitions приходят из доверенного `ACCESS_CATALOG_FILE`/project manifest, не из произвольного браузерного JSON.

Поэтому пожелание «создавать свои разрешения в UI» нужно включить в будущий backend-блок. Готовность custom roles не означает готовность редактора permission definitions.

Внутренние шаблоны ролей существуют как deployment definitions, но endpoint списка шаблонов не опубликован. UI не должен обещать загрузку шаблонов через несуществующий API.

### 9.3. Список и форма роли

- GET `/api/v1/admin/roles?after=…&limit=…` → metadata и `nextAfter`.
- GET `/api/v1/admin/roles/{id}` → metadata + `permissions`.
- POST `/api/v1/admin/roles` — создать custom роль.
- POST `/api/v1/admin/roles/{id}` — полностью заменить определение custom роли с `expectedVersion`.

| Поле | Поле формы и ограничения |
| --- | --- |
| `key` | Стабильный технический ключ, до96 байт, lowercase/digits/underscore/dot по правилам backend |
| `name` | Понятное название, до200 байт UTF-8 |
| `description` | Описание, до2000 байт |
| `permissions[]` | Только известные каталоговые keys, без wildcard/повторов; до128 на роль |
| `mfaRequired` | Требовать MFA у носителей роли, при готовом MFA-компоненте |
| `version`, `system` | Read-only |

Создание роли никому её не назначает. System роль нельзя редактировать этой формой. Update — не PATCH: UI должен отправлять полное корректное определение. Для `mfaRequired` пропуск на update сохраняет прежнее значение.

Расширение роли/усиление требований может потребовать повторного входа её пользователей. Нет готового API удаления роли, bulk assignment, импорта или копирования роли одной командой. Копирование в макете пока можно трактовать только как заполнение новой формы и обычный create после явного действия.

### 9.4. Назначить и снять обычную роль

POST/DELETE `/api/v1/admin/users/{id}/roles/{roleId}`. Оба метода требуют JSON `expectedRoleVersion`, `expectedAccessVersion`.

Нужны `access.assignments.manage`, допустимое делегирование и fresh proofs. Нельзя выдать себе привилегии; нельзя этим способом назначать system super_admin. Сейчас предел — **32 роли на пользователя**; его UI-настройка пока не реализована.

Роли можно назначить подходящему pending-пользователю заранее, но это не завершает активацию. Новые полномочия не должны автоматически появляться в старой сессии без предусмотренного обновления authority. Для local JWT остаётся его окно до expiry.

### 9.5. Системный администратор проекта

POST/DELETE `/api/v1/admin/users/{id}/administrator` с `expectedAuthVersion`, `expectedAccessVersion`, `expectedRoleVersion`.

Это отдельный flow, не обычный пункт произвольной custom-роли. Выдающий должен иметь системные полномочия; целевой пользователь должен быть пригоден к административному входу по актуальной политике. Последнего пригодного владельца нельзя убрать. Custom роль с похожим названием или большим набором permissions не заменяет system super_admin.

### 9.6. Действия с ролями из общей панели

Есть отдельные platform bridge API:

- Чтение списка/карточки ролей проекта.
- Создание обычной custom роли.
- Grant/revoke обычной роли пользователя.
- Чтение и сверка результата собственной операции.

Они используют project `expectedVersion/expectedGeneration`, role/access versions, `operationId` и `reason`. Результат может быть `committed` или временно `unknown`; при unknown нельзя автоматически повторять с новым operation ID.

**Текущие границы:** platform bridge не поддерживает редактирование/удаление роли, system super_admin grant/revoke, а создание/назначение роли с `mfaRequired=true` закрыто текущей readiness-сборкой. Локальный project API и общий bridge имеют разный набор возможностей.

У platform origin нет отдельного permissions-catalog endpoint для динамической формы выбора прав. Platform bridge использует доверенный каталог установки, который может отличаться от project-local каталога. Для единого интерфейса это нужно явно решить, а не молча смешивать списки.

GET `/api/v1/platform/projects/{id}/role-operations/{operationId}` и POST того же пути с `/reconcile` читают/уточняют только операцию исходного actor. Это не повтор исполнения команды и не просмотр любого чужого operation UUID.

### 9.7. Поля и строки внешней CRM

Auth может сообщить, кто пользователь и какие permission keys ему разрешены. Backend CRM применяет их к своим данным.

Пример: `crm.orders.amount.read` разрешает показать сумму, `crm.orders.cost.read` — себестоимость. CRM проверяет эти keys и возвращает только разрешённые поля. Auth сам не знает структуру каждой таблицы CRM и не удаляет поля из чужого HTTP-ответа.

Аналогично «только свои записи» — проверка ownership в CRM, не результат одного наличия `orders.read`. Скрыть колонку во frontend недостаточно: запрет должен работать на backend данных.

В будущем внешний backend может передавать доверенный каталог своих permissions для удобной настройки, но готового discovery/import/sync API такой интеграции сейчас нет. Swagger описывает ручки, но сам по себе не определяет бизнес-политику доступа к каждой строке/полю.

## 10. Настройки входа и MFA

### 10.1. Форма «Способы входа» — API есть

Локально: GET/POST `/api/v1/admin/auth/settings`. Нужны `auth.settings.manage`, готовая capability и требуемые свежие proofs для записи. GET позволяет прочитать форму; POST полностью заменяет `policy` и требует `expectedVersion`.

| Точное поле | Подпись в интерфейсе | Поведение |
| --- | --- | --- |
| `policy.methods.password` | Вход по email и паролю | Разрешает новые парольные входы |
| `policy.methods.emailOtp` | Вход по коду из письма | Отдельный основной способ входа, не MFA |
| `policy.methods.google` | Вход через Google | Требует готового Google adapter и credentials |
| `policy.methods.telegram` | Вход через Telegram | Именно OIDC-вход, не бот MFA |
| `policy.registration.enabled` | Разрешить самостоятельную регистрацию | Общий запрет/разрешение нового публичного создания |
| `policy.registration.google` | Разрешить создание аккаунта через Google | Дополнительно требует общий registration gate и Google method |
| `policy.registration.telegram` | Разрешить создание аккаунта через Telegram | Аналогично для Telegram |
| `policy.passwordEmailVerification` | Подтверждение email | `disabled`, `optional`, `required` |
| `policy.tokenIssuance.sessionExchange` | Разрешить JWT из сессии | Новая выдача JWT завершённым browser-session |
| `policy.tokenIssuance.native` | Разрешить native JWT-вход и refresh | Независимо от cookie exchange, при готовом native adapter |

Все boolean в полном policy payload передаются явно, включая `false`. `version` не редактируется. Изменение ENV после seed не заменяет сохранённую политику.

Read-only части GET:

- `availableMethods` — какие методы способен обслужить этот экземпляр/assessment.
- `readiness`, когда доступна: версия/время наблюдения и готовность конкретных features с причиной отказа.
- `tokenProfiles` — подготовленные параметры JWT, см. раздел12.

Сохранённое «включено» и готовность реализации — разные вещи. Нельзя включить неподготовленный метод: например, отсутствуют credentials/SMTP/ключи/route capability. Для закрытия небезопасного перехода могут сработать `auth_method_not_ready` или защита последнего пригодного администратора.

### 10.2. Примеры комбинаций

| Потребность | Настройка |
| --- | --- |
| Открытый сайт по паролю | Password on, registration on; verification по выбору |
| Закрытая админка | Password on, registration off; пользователей создаёт администратор |
| Сайт Google + пароль | Оба метода on; provider-registration управляется отдельно |
| Подтверждение почты обязательно | `passwordEmailVerification=required` |
| Только внешние входы | Возможность зависит от готовности методов и защитных ограничений; не обещать универсальную отвязку/парольное управление external-only аккаунтом |
| JWT для внешнего backend после browser login | Session exchange on, native может быть off |
| Native без cookie exchange | Native on, session exchange может быть off |

Все публичные методы могут быть выключены в допустимой конфигурации; это не создаёт резервный вход автоматически. Выключение метода не удаляет пользователей/identities и не означает logout всех существующих сессий.

### 10.3. Политика обязательности MFA — API есть

Локально GET/POST `/api/v1/admin/auth/settings/mfa`; для самой общей панели GET/POST `/api/v1/platform/settings/mfa`.

Read: `{version,policy:{mode}}`. Write: `{expectedVersion,policy:{mode}}`.

| `mode` | Подпись | Смысл |
| --- | --- | --- |
| `optional` | По желанию пользователя | Личная подключённая MFA и обязательность назначенной роли всё равно соблюдаются |
| `administrators` | Обязательно администраторам | Для административного входа обязательно; для остальных по личной/ролевой политике |
| `required` | Обязательно всем | Все пользователи текущего контура проходят MFA |

Начальное значение схемы — `administrators`; при первом setup можно выбрать другой поддержанный режим. Для общей панели и каждого проекта это отдельные настройки, не один глобальный переключатель.

`optional` не выключает MFA engine и не удаляет уже подключённые факторы. Усиление политики может отозвать текущие сессии/незавершённые входы, включая сессию инициатора. После успешного сохранения UI должен быть готов попросить новый вход.

### 10.4. Разрешить email/Telegram вторым фактором

- GET/POST `/api/v1/admin/auth/settings/mfa/email`.
- GET/POST `/api/v1/admin/auth/settings/mfa/telegram`.

Read: `{version,allowed}`. Write: `{expectedVersion,allowed}`. По умолчанию `false`. Это проектные настройки; готовность runtime и доставки проверяется отдельно. Разрешение проекта не подключает фактор каждому пользователю автоматически.

Отключение канала запрещено, пока существуют использующие его factor bindings (`email_factor_in_use` / `telegram_factor_in_use`). Это не кнопка «принудительно оставить всех без MFA».

**Общая версия:** MFA mode, email allowed, Telegram allowed и Bot API settings используют одну строку версии. Если другая вкладка изменила её, нужно перечитать состояние, а не отправлять старую форму поверх.

### 10.5. Что доступно из общей панели

Bridge GET/POST `/api/v1/platform/projects/{id}/auth/settings` позволяет менять **несекретную Auth policy** выбранного проекта. Read требует актуальные project version/generation; write дополнительно `operationId`, `expectedPolicyVersion`, `reason`, полную policy. Есть read результата собственной операции `/auth/settings/operations/{operationId}`.

Этот bridge не является универсальным API для SMTP, provider secrets, Telegram bot или MFA-policy проекта. Нужен явный будущий способ безопасного управления этими вкладками из одной операторской сессии, если именно такой UI выбран.

## 11. Почта, провайдеры, Telegram и хранение данных

### 11.1. SMTP — API есть

GET/POST `/api/v1/admin/auth/settings/smtp`. Read: `version`, `config`, `passwordSet`. Write: `expectedVersion`, полная `config`, необязательный `password`.

| Поле | Подпись | Что учитывать |
| --- | --- | --- |
| `config.host` | SMTP-сервер | Только доверенный разрешённый target, не любой URL |
| `config.port` | Порт | 1–65535; UI не должен придумывать сохранённое значение |
| `config.username` | Логин | Может отсутствовать у relay без AUTH |
| `config.from` | Email отправителя | Адрес без display name по текущему контракту |
| `config.domain` | Домен SMTP-клиента | Значение идентификации SMTP, не проверка DNS сайта |
| `config.requireTls` | Требовать STARTTLS | В production/project SMTP отключение запрещено |
| `password` | Новый пароль | Только write; текущий пароль не читается |
| `passwordSet` | Пароль сохранён | Bool, а не маска пароля и не доказательство доставки |

Пароль omitted/null — сохранить. Непустая строка — заменить. Пустая строка — удалить только при допустимом relay без username. Смена host/port/username требует явного действия с паролем. Не отправлять UI-маску вместо секрета.

**«Проверить соединение»:** POST `/api/v1/admin/auth/settings/smtp/test` с `expectedVersion`. Проверяет сохранённую конфигурацию и соединение/STARTTLS/AUTH; **не отправляет тестовое письмо**. Ответ `connected` не гарантирует доставку адресату. Preview или «Отправить выбранный шаблон себе» — отдельная ещё не готовая возможность.

SMTP allowlist, encryption keys и эксплуатационные ограничения не редактируются этим API. Даже администратор с правами не может использовать форму как произвольный сетевой прокси.

### 11.2. Google и Telegram OIDC — API есть

GET/POST `/api/v1/admin/auth/settings/providers/{provider}`, где provider — `google` или `telegram`.

| Поле | Подпись | Смысл |
| --- | --- | --- |
| `clientId` | ID приложения провайдера | Google client ID либо канонический числовой Telegram ID |
| `clientSecret` | Новый секрет приложения | Write-only |
| `clientSecretSet` | Секрет сохранён | Read-only bool |
| `version` / `expectedVersion` | Версия конкретного провайдера | Не общая версия Auth policy |

Отдельные шаги: сохранить credentials → убедиться в готовности deployment/callback → разрешить метод в Auth policy. Сохранение секрета не означает автоматического включения метода или успешной проверки у реального провайдера.

Omitted/null secret с прежним client ID — сохранить; непустой — ротация; пустой — очистка только при выключенном методе. Изменить client ID можно только с явным secret action, выключенным методом и без несовместимых привязанных identities. Иначе backend отклоняет смену, чтобы существующие аккаунты не перепривязались к другому приложению.

Callback/issuer/сетевые budgets остаются доверенной deployment-конфигурацией. Произвольный «Добавить OAuth-провайдера» через текущий API не поддержан. Bot API token не является Telegram OIDC secret.

### 11.3. Telegram-бот для MFA — проектный API есть

Это отдельная вкладка от Telegram-входа.

| API / поле | Действие или данные |
| --- | --- |
| GET `/api/v1/admin/auth/settings/mfa/telegram/bot` | `version`, `botId`, `username`, `botTokenSet`, `webhookSecretSet` |
| POST того же пути | `expectedVersion`, необязательный `botToken`, `rotateWebhookSecret` |
| POST `/api/v1/admin/auth/settings/mfa/telegram/webhook` | `expectedVersion`; зарегистрировать доверенный webhook |

ID/имя бота определяются ответом Telegram, не произвольными полями UI. Token проверяется backend и сохраняется зашифрованно. Не переданный token сохраняется; пустая строка не является удалением. Отдельный endpoint удаления bot credentials не реализован.

Webhook secret генерирует сервер и не возвращает plaintext. Можно запросить его ротацию; затем требуется заново зарегистрировать webhook. URL строится из доверенного origin проекта, а не вводится произвольной строкой.

Смена бота запрещена, пока есть несовместимые подключения его фактора. Успех регистрации webhook в Telegram не доказывает доступность ingress. Для функционирования канала нужны project capabilities и настройки, а не только токен.

Входящие сообщения принимает технический `POST /api/v1/auth/mfa/telegram/webhook`; это не browser-admin action и не endpoint, куда UI должен отправлять пользовательские коды.

### 11.4. Шаблоны писем — поставляемые письма есть, редактор пока в плане

Backend уже формирует и отправляет письма нужных сценариев: verification, reset, email OTP, приглашения, email-change/security notices, MFA и восстановление в поддержанных профилях. Тема/содержимое формируются реализацией сценария.

**Не реализованы** управляемые из UI сохранение HTML, загрузка файла, draft/publish, preview, reset-to-default, rollback и отправка теста выбранного шаблона. Точных management DTO/permission keys ещё нет. Не изображать несуществующий template CRUD как готовую функцию.

Согласованное пожелание для будущего дизайна:

- Каталог сценариев писем с поставляемым вариантом по умолчанию.
- Раздельные области проекта и общей панели.
- Тема, HTML и текстовая версия.
- Загрузка HTML и список разрешённых переменных конкретного сценария.
- Безопасный preview; черновик и опубликованный вариант.
- Возврат к поставляемому шаблону и контроль версий.
- Тестовая отправка с отдельными правами и лимитами.

Все эти элементы пометить **будущим backend-блоком**, не смешивать с существующим SMTP connection test. Дизайн не должен разрешать исполняемый код/произвольные секретные переменные внутри шаблона.

### 11.5. Сроки хранения — API есть

GET/POST `/api/v1/admin/auth/settings/retention`. Read: `version`, `policy`. Write: `expectedVersion`, полная `policy`, `confirmShortening`.

| Поле | Подпись | Начальное значение | Что означает |
| --- | --- | --- | --- |
| `policy.emailReservationDays` | Резервировать email после удаления | 30 дней | Когда адрес может перестать быть зарезервированным после удаления аккаунта |
| `policy.sessionDays` | Хранить завершённые сессии | 30 дней | Хранение уже недействительных записей, не длительность входа |
| `policy.securityAuditDays` | Хранить аудит безопасности | 180 дней | Хранение событий security audit |
| `confirmShortening` | Подтверждаю сокращение хранения | false | Нужен при уменьшении хотя бы одного срока |

Диапазон каждого срока — целое число дней от1 до106751. Ноль не выключает очистку. Значения30/30/180 — seed/defaults, а не принудительная замена уже сохранённых настроек.

При сокращении показать риск удаления данных и получить явное подтверждение. Увеличение срока не восстанавливает уже очищенные записи. Сохранение не запускает немедленную очистку; новые сроки подхватит фоновая работа. Размер партии и период cleanup задаются deployment, не этой формой. Это не управление резервными копиями.

## 12. JWT и подключение других приложений

### 12.1. Два способа получить JWT

| Вариант | Как работает | Для чего UI |
| --- | --- | --- |
| JWT из браузерной сессии | Пользователь уже вошёл с cookie; backend выдаёт JWT для разрешённого внешнего backend | Настройка доступности обмена и страница интеграции |
| Самостоятельный native/API-вход | Поддержанный клиент входит по паролю или email-коду, при необходимости проходит MFA и получает access + refresh | Настройка доступности native-профиля; отдельный клиент приложения |

Два режима включаются независимо. Это не выбор «либо сессии, либо JWT для всей установки». Browser admin API остаётся cookie-based; нельзя просто подставить Bearer JWT вместо административной cookie.

**Native API не является обычным браузерным login API:** он отклоняет `Origin`, `Cookie`, `Authorization` и query-параметры в соответствующих credential-запросах. Не подключать эти ручки к SPA как альтернативу браузерному cookie-flow. Для frontend/BFF нужно выбрать поддержанный способ интеграции.

### 12.2. Что показать в разделе JWT

**Уже изменяемо через Auth policy:**

- Разрешён ли новый обмен browser session → JWT: `policy.tokenIssuance.sessionExchange`.
- Разрешён ли native-вход и refresh: `policy.tokenIssuance.native`.

**Можно показывать как техническую информацию, но нельзя обещать её сохранение текущим API:**

- готов ли JWT-компонент;
- issuer проекта;
- срок access token;
- подготовленные audiences — внешние сервисы-получатели;
- scopes/permissions, разрешённые каждому audience;
- режим проверки и гарантии отзыва;
- готовность introspection/native/JWKS;
- кто управляет этими параметрами и нужен ли rollout.

Эти сведения доступны в read-only `tokenProfiles` там, где профиль предоставляет metadata. Metadata экземпляра не доказывает, что весь кластер и внешний backend уже настроены одинаково.

### 12.3. Строгая и локальная проверка

| Режим | Что происходит | Что написать рядом с выбором |
| --- | --- | --- |
| `strict` | Внешний backend проверяет JWT и актуальность доступа через Auth | Требует связи с Auth; учитывает актуальный отзыв сессии, блокировку и права |
| `local` | Внешний backend проверяет подпись и допустимость JWT локально | Меньше сетевых обращений, но уже выданный JWT может действовать до истечения срока после отзыва |

Это настройка доверенного профиля ресурса, а не параметр, которым пользователь произвольно понижает защиту запроса. Для чувствительных административных permissions действуют дополнительные запреты; local нельзя рекламировать как универсальный безопасный режим для любой операции.

### 12.4. Основные операции интеграции

| API | Назначение |
| --- | --- |
| POST `/api/v1/auth/token/exchange` | Выдать access JWT из актуальной browser session для разрешённых audience/scope |
| GET/HEAD `/.well-known/jwks.json` | Получить публичные ключи проверки JWT; приватные ключи наружу не выдаются |
| POST `/api/v1/internal/auth/token/introspect` | Внешний backend проверяет JWT с отдельными service credentials, а не пользовательской cookie |
| POST `/api/v1/auth/native/password/login` | Native-вход по паролю |
| POST `/api/v1/auth/native/email/request`, `/confirm` | Native-вход по email-коду |
| POST `/api/v1/auth/native/mfa/complete` | Завершить поддержанный MFA-вход native-клиента |
| POST `/api/v1/auth/native/mfa/email/login`, `/complete` | Явный email second factor после пароля в допустимом профиле |
| POST `/api/v1/auth/native/mfa/enrollment`, `/confirm` | Обязательная настройка TOTP в native-flow |
| POST `/api/v1/auth/token/refresh` | Повернуть refresh token и получить новую пару credentials |
| POST `/api/v1/auth/token/logout` | Отозвать конкретную refresh family/API-сессию |

Прямой native Google/Telegram-вход не следует считать готовым по наличию browser OIDC endpoints.

### 12.5. Refresh и завершение доступа

- Refresh одноразовый: после успешного обмена клиент заменяет сохранённый refresh новым.
- Одновременные refresh нужно сериализовать. Повторное использование известного старого credential может отозвать всю связанную цепочку доступа.
- Нет универсального безопасного автоматического повтора старого refresh после потерянного ответа.
- Refresh не расширяет scope, уровень MFA или абсолютный срок.
- Отключение выдачи JWT не стирает уже выданные local tokens; для strict актуальность проверяется онлайн.
- Выход одной native-family не равен выходу со всех устройств пользователя.

### 12.6. Настройка внешнего backend

Для интеграции нужны: доверенный issuer, audience, публичные ключи/JWKS, выбранный режим, нужные permission keys. Для strict дополнительно нужны URL introspection и отдельные credentials сервиса.

В репозитории есть middleware/consumer SDK `pkg/authjwt`; внешний backend всё равно обязан проверять доступ к своим объектам и полям. Наличие JWT не переносит бизнес-данные в Auth и не создаёт CRM автоматически.

Не включать секрет consumer, приватный ключ, raw JWT или refresh в обычную карточку проекта/логи/аналитику. Кнопка «Создать/ротировать integration credentials» требует реально поддержанного management API, а не только существующего config loader.

## 13. Технические настройки и границы UI

Пользователь хочет в будущем управлять настройками через UI. Но **существующая переменная ENV не означает существующий API её редактирования**.

### 13.1. Что относится к эксплуатации

Следующие группы реально есть в backend, но значительная часть управляется при запуске/через файлы и требует отдельного management-контракта для UI:

| Группа | Примеры | Как отражать сейчас |
| --- | --- | --- |
| HTTP и TLS | Порт, сертификаты, таймауты, размер заголовков/тела | Информация об установке/инструкция, не обычная горячая форма |
| Origins/CORS и reverse proxy | Разрешённые HTTPS origins, доверенные proxy CIDR | Настройка deployment; неверное изменение способно закрыть вход или открыть лишний origin |
| PostgreSQL | Подключения и общий бюджет пулов, технические роли | Не показывать рабочие пароли и не разрешать произвольное подключение из браузера |
| Redis | Подключение, пароль, pool/deadlines и scoped budgets | Эксплуатационная настройка; при отказе защищённые операции не переходят в unlimited mode |
| Хеширование | Параллелизм, память, ожидание, параметры проверки | Не предлагать пользователю «ускорить» вход ослаблением hashing |
| Вход/OTP/reset/MFA | TTL, cooldown, число попыток, ограничения пользователя/IP/проекта | Показывать единицы и назначение. Сохранение зависит от конкретного API, не от наличия ENV |
| Доставка | Разрешённые SMTP targets, encryption keys, worker budgets | Отдельные эксплуатационные полномочия |
| JWT | Signing keys, trusted audiences, consumers, TTL и budgets | Разделять read-only projection и сохраняемые policy switches |
| Runtime проектов | Trusted storage targets, master keys, число resident pools, draining | Управляет backend/deployment, не произвольный DSN из формы |
| Восстановление | Отдельные recovery credentials/операторы/CLI | Не превращать в общую кнопку обхода безопасности |
| Swagger и dev-инструменты | Включение, Basic access, dev SMTP test | Не делать их публичной частью production-панели |

Точные ENV и их актуальные defaults находятся в `.env.example`, `internal/config` и конфигурации владельцев фич. Не копировать реальные секреты в дизайн или документы. Детальный пользовательский справочник групп — [Auth guide](auth-guide.md#9-настройки-env), но при расхождении действует текущий код.

### 13.2. Как объяснять лимиты в UI

Вместо «Global limit: 100»:

- «Запросов восстановления на проект в минуту».
- «Отправлять код повторно не чаще чем раз в … секунд».
- «Срок действия кода, минут».
- «Одновременных вычислений пароля».
- «Проверок JWT в минуту на подключённый сервис».

Лимит попыток — не количество зарегистрированных пользователей и не измеренная мощность backend. Предел на одного пользователя/адрес/IP/consumer не равен общему пределу проекта. Если ограничений несколько, сработает более строгий.

Чувствительные production-параметры нельзя делать безусловно редактируемыми для любого администратора проекта. Нужны область действия, права, допустимый диапазон и понятное сообщение о перезапуске/rollout.

### 13.3. Сессии: четыре разных понятия

- Срок неактивности: когда сессия перестаёт действовать без допустимого продления.
- Абсолютный срок: предел, за который сессию не продлевают даже при активности.
- Свежесть подтверждения: сколько действует повторно предъявленный пароль/фактор для опасных действий.
- Хранение завершённых записей: когда фоновая очистка удаляет уже недействительные записи.

Изменение срока хранения не выдаёт пользователю более долгий доступ. Retention30 дней не означает сессию длительностью30 дней.

Подтверждённые defaults конфигурации, а не значения существующей установки:

| Параметр | Подпись | Default |
| --- | --- | --- |
| `SESSION_TTL` | Скользящий срок обычной сессии | 168h |
| `ABSOLUTE_SESSION_TTL` | Абсолютный срок обычной сессии | 336h |
| `SESSION_REFRESH_THRESHOLD` | Порог условного продления | 24h |
| `SESSION_FRESH_AUTH_TTL` | Срок повторного подтверждения в session config | 5m; отдельные SQL guards могут иметь фиксированное окно5m |
| `ADMIN_SESSION_IDLE_TIMEOUT` | Неактивность административной сессии | 30m |
| `ADMIN_SESSION_ABSOLUTE_TTL` | Абсолютный срок административной сессии | 12h |
| `ADMIN_SESSION_ACTIVITY_INTERVAL` | Интервал подтверждения интерактивной активности | 1m |
| `JWT_ACCESS_TTL` | Срок access JWT | 2m, допустимы целые секунды1s–5m |
| `JWT_REFRESH_IDLE_TTL` | Срок неактивности native refresh | 168h |
| `JWT_REFRESH_ABSOLUTE_TTL` | Абсолютный срок native refresh | 336h |

Для этих длительностей отдельного сохраняемого settings editor сейчас нет. При проектировании будущей формы нужно также перенести действующие проверки совместимости сроков, а не только добавить числовые поля.

### 13.4. Фоновая работа и диагностика

Письма и security notices доставляются фоновыми компонентами, очистка удаляет устаревшие записи ограниченными партиями. Поэтому принятие запроса и получение письма — разные события.

Есть `/health/live` и `/health/ready`. Это техническое состояние процесса/зависимостей, не количество пользователей онлайн, не история доставки и не измеренный RPS. Не обещать UI очереди, мониторинг всех писем или метрики нагрузки без отдельного доступного API.

### 13.5. Резервные копии и восстановление

**Сейчас есть CLI**, не готовый management API: `task backup`, `task restore`, расписание backup-компонента, checksum/archive preflight, защитная pre-restore копия и восстановление с последующей инвалидизацией Auth credentials. Restore-wrapper оставляет API остановленным; безопасное открытие доступа — отдельный recovery этап.

**Для будущего UI согласован scope13 ноября:** список копий и заданий, создать/проверить/скачать/удалить по отдельным правам, расписание и хранение, preview и подтверждённое восстановление конкретного проекта либо общей БД. Стартовый профиль:24h/7 копий, затем настраивается. Подробности и критерий готовности — [U3.1](planning/ui-management.md#u31-резервные-копии-и-восстановление-из-админки).

Нужно показывать состав и пригодность копии: БД без необходимых ключей недостаточно. Ключи/credentials не возвращаются браузеру, копии не публичны. Старые сессии не должны оживать после restore; старые постоянные права/пароли требуют отдельной сверки/recovery. Панель не передаёт произвольный DSN/SQL или непроверенный внешний dump привилегированному executor. Для восстановления самой БД панели учитывать временную недоступность UI и независимый статус операции. Сейчас эти будущие кнопки не имеют management HTTP-контрактов.

## 14. Общие состояния и правила интерфейса

### 14.1. Версии и изменения настроек

Многие формы читают `version`, а сохраняют `expectedVersion`. Это защита от ситуации, когда два администратора одновременно меняют одну настройку.

При конфликте не перезаписывать форму молча. Показать «Настройки изменились. Обновите данные», позволить перечитать и осознанно повторить изменение. Для API с полной заменой policy отправлять весь обязательный документ; пропущенный boolean не означает автоматически `false`.

### 14.2. Состояния экрана

Для каждого экрана макет должен учитывать:

| Состояние | Что видит пользователь |
| --- | --- |
| Загрузка | Понятный индикатор; опасное действие временно недоступно |
| Нет данных | Объяснение и допустимое первое действие |
| Нет прав | Отсутствие действия или явное объяснение; скрытая кнопка не заменяет backend-проверку |
| Метод выключен | «Отключён настройками», не «Ошибка сервера» |
| Возможность не подготовлена | Что именно нужно настроить; backend может не публиковать маршрут |
| Нужно подтверждение | Пароль/допустимый фактор, затем повтор действия в текущем контексте |
| Конфликт версии | Обновить состояние, не повторять бесконечно |
| Истёк challenge | Начать поддержанный процесс заново |
| Ограничение частоты | Подождать, показать срок повтора, если доступен |
| Временный отказ зависимости | Не показывать успех; дать безопасный следующий шаг |
| Результат неизвестен | Не повторять опасную операцию автоматически; проверить её состояние/receipt, где это предусмотрено |
| Сессия отозвана | Очистить локальное представление пользователя и вернуться ко входу |

### 14.3. Опасные операции

Удаление, блокировка, смена роли администратора, смена email, отключение последнего способа входа/фактора, ротация credentials — разные действия. Для них нужны соответствующие backend-предпосылки, а не один универсальный диалог «Вы уверены?».

В подтверждении показывать конкретный объект, выбранный проект и последствия: отзыв сессий, необратимость, запрет входа. Если backend требует явное подтверждение или version, UI должен передать их точно; придуманная frontend-проверка не заменяет контракт.

### 14.4. Секреты

- Read API обычно отдаёт признак наличия/маску, а не прежнее секретное значение.
- Для ввода нужны разные действия «Оставить прежний», «Заменить», «Удалить», только если именно эти действия допускает контракт фичи.
- Не подставлять маску вроде `••••••` в POST как настоящий пароль.
- Временный пароль и резервные коды выдавать только в допустимом моменте; не обещать повторный просмотр.
- Не сохранять password, OTP, TOTP secret, raw token, private key и service credentials в localStorage/analytics.
- Browser-cookie HttpOnly: frontend не читает её содержимое и не переносит cookie между проектами.

### 14.5. Доступность и понятность макета

Включить клавиатурный ввод, понятные подписи, показ/скрытие вводимого пароля, вставку OTP с ведущими нулями, длинные email/названия ролей, пустые списки и узкий экран. Ошибку формы связывать с конкретным полем, если backend раскрывает её безопасно.

Для OAuth/OIDC и писем предусмотреть возврат в исходный браузер, истечение процесса, повторное открытие и конфликт вкладок. Не рассчитывать, что все ответы одинаковы по форме или регистру JSON: контракт конкретного endpoint является источником истины.

## 15. Что ещё нужно для UI

Эта часть предотвращает ситуацию, когда дизайн обещает действие, которого пока нет в backend.

### 15.1. Можно проектировать на основе существующего backend

- Основные cookie-входы: пароль, Google/Telegram OIDC, email OTP в допустимом профиле.
- Саморегистрация и выбор обязательности подтверждения email.
- Verification/reset/email-change/protected recovery.
- Собственные сессии, выход, повторное подтверждение личности.
- TOTP/recovery codes, проектные email/Telegram MFA и предпочтение допустимого метода.
- Поддержанные операции общей панели над проектами/ролями/пользователями и локальные административные операции.
- Сохраняемые Auth/MFA/provider/SMTP/retention настройки в пределах контрактов ниже.
- Cookie→JWT и native-профили; read-only сведения о подготовленных token resources.

### 15.2. Нужно отдельно согласовать или доработать

- Сам UI, макет, визуальная система, маршруты frontend и способ его сборки ещё не реализованы этой документацией.
- Управление **всеми** ENV, файлами ключей и deployment targets из одной формы пока не существует. Для таких групп нужны безопасные backend-команды и права.
- Редактор/загрузка произвольных email-шаблонов не должен считаться готовым только потому, что backend уже умеет отправлять письма.
- Полный личный профиль с произвольными именем/аватаром/телефоном и его редактирование не следует из текущего `/me`.
- Автоматические данные dashboard, пользователи онлайн, общий просмотр всех security audit events, история delivery и real-time графики требуют соответствующих read API.
- Не все локальные проектные действия доступны из общей операторской сессии. Нельзя обойти это подстановкой project UUID или cookie из другого контура.
- Управление callback/issuer/keys/consumer secrets через UI требует отдельного management API там, где сейчас только deployment config.
- Отображение разрешённых способов входа **до авторизации** требует согласованного публичного источника конфигурации; защищённый admin settings нельзя открыть всем ради кнопок.
- Автоматический SSO между независимыми проектами не реализован.

### 15.3. За пределами текущего выпуска

Оплата, подписки, entitlements/квоты продукта, общий SSO, организации/multi-app, passkeys, SMS-MFA, Telegram Mini Apps/Stars не входят в текущий выпуск. Не рисовать их как работающие настройки. Назначение роли после оплаты в будущем можно интегрировать отдельным доверенным backend, но готовая платёжная система из этого не следует.

### 15.4. Как использовать документ при подготовке макета

1. Выбрать, какой контур рисуется: общая панель, проектная админка или пользовательский кабинет.
2. Выбрать сценарий и выписать из документа входные условия, поля, действия и последствия.
3. Разделить изменяемые значения, read-only metadata и будущие возможности.
4. Нарисовать основной путь, отсутствие прав, конфликт версии, подтверждение действия и отказ зависимости.
5. Сопоставить действие с endpoint из раздела16 и DTO Swagger/фичевой документации.
6. Отдельно перечислить желаемые действия без API. Их сначала согласовываем как backend-задачи, затем подключаем к UI.
