# План JWT-доступа — A6.4

Общая безопасность сервиса, **особенно действующих opaque sessions**, описана отдельно в [AS1–AS12](auth-security.md). Этот JWT-план её дополняет, а не заменяет; подтверждённые session/Auth дефекты исправлять до включения новых профилей.

Статус: J1-контракт зафиксирован 17 октября 2026 в [ADR 004](../adr/004-jwt-access-profiles.md); **JWT runtime ещё не реализован**, J2–J7 открыты. Первоначальный план согласован 16 октября; 17 октября пользователь подтвердил стандартный Bearer JWT и отдельный native/API профиль. Backend-реализация выполняется после локальных A6.3c блоков, до backend-приёмки и UI; внешние gates A6.3 не закрываются этим решением. Не обещаем невзламываемость или произвольный RPS: гарантии подтверждаются тестами, аудитом и измерениями.

## Что есть и что добавляем

Сейчас browser использует opaque `__Host-session`, а SQL ledger — актуальные session/status/auth_version. `Auth`/`NoRefreshAuth` проверяют SQL через session service. Sensitive writes повторно авторизуются в своей транзакции. Redis — limits, не замена SQL authority. BrowserProtection проверяет exact HTTPS Origin; CORS по умолчанию выключен, preflight разрешает Content-Type, но **ещё не Authorization**. JWT выдачи, bearer middleware, refresh families и introspection API сейчас нет.

JWT — формат credential после успешного входа, не новый primary method вроде пароля/Telegram. Он не отменяет verification, MFA, activation, temporary-password completion, блокировки и разграничение прав. Вход через Google/Telegram не позволяет использовать provider ID token как наш API access token.

Планируемые профили, включаемые независимо от primary methods:

1. **Cookie/session** — нынешний browser/BFF профиль по умолчанию, без JWT и без изменения текущего контракта.
2. **Session → JWT для дополнительных backend** — после полного входа текущая session позволяет получить короткий access token для одного разрешённого resource audience. Дополнительный backend получает JWT, не opaque cookie/raw session token. Обновление access token через живую session, отдельный refresh token в этом профиле не нужен.
3. **JWT + refresh без browser session cookie** — явный API/native профиль: те же account/login/MFA сценарии завершаются access JWT и opaque rotating refresh credential. На сервере остаётся общий session ledger, а не второй независимый user store. Отдельный результат login не означает stateless refresh или обход session revocation.

По одному deployment на проект, несколько заранее разрешённых resource audiences внутри его trust boundary. Общий SSO, multi-tenant/client registration, произвольный token exchange, service-account/client-credentials flow и OAuth authorization-server framework этим этапом не вводим. JWT от имени пользователя не является самостоятельной идентификацией вызывающего сервиса.

## Ключевое решение: отзыв и актуальность прав

**Strict online — default.** Локальная криптографическая проверка дополняется authenticated introspection/current-authority проверкой: session ID, user status/auth_version, expiry/revoke и текущие permissions. Один bounded online decision на запрос; no sliding refresh/write на каждый вызов. На собственных sensitive routes остаются прежние transaction-owned guards, JWT не превращаем в их обход. Недоступность authority — 503/fail-closed, не приём по старому positive cache. Introspection не должна быть публичным UUID lookup: service authentication, audience restriction и budgets обязательны.

**Local verification — отдельный opt-in профиль по ADR 004.** Дополнительный backend проверяет подпись/claims локально с готовым trusted key snapshot, без SQL/Redis/Auth authority на обычный запрос. Logout/block/revoke/смена роли не становятся видны до истечения токена. `auth_version`/`access_version` в JWT сами по себе ничего не отзывают. J1 выбирает default TTL 2m, ceiling 5m, без grace после exp и future-iat/nbf skew до 30s: при проверенной разнице часов ≤30s maximum local revocation delay — 5m30s. Trusted JWKS snapshot не старше 60s; его обновление требует bounded сетевого вызова, полной автономности от Auth нет. Admin/settings/role writes — не local-only; client не переключает strict token в local.

Strict режим сохраняет семантику проверок после commit ADR 002, но не обещает распределённую атомарность: отзыв после introspection не отменяет начатую операцию другого backend. Для критичного внешнего эффекта принимающий backend определяет момент повторной авторизации и собственную транзакционную защиту; без общей транзакции нельзя обещать отсутствие всех гонок с удалённым отзывом. Это явно описать в интеграционном контракте.

Одновременно обещать полную автономность, немедленный централизованный отзыв и отсутствие online dependencies нельзя. Не маскировать это Redis-кешем/TTL. Local mode включается только явно по ADR 004 и не ослабляет opaque session/admin authority ADR 002; при ошибке strict проверки переключения в local нет.

## Проверка проекта по безопасности — обязательные условия реализации

Дополнено 16 октября 2026 после отдельного анализа. Ниже — пробелы детализации и угрозы будущего решения, **не подтверждённые уязвимости текущего сервиса**. Отмеченные условия обязательны для strict JWT; local-only не получает его гарантий автоматически. Подход — deny-by-default и проверка разрешений для каждого действия, включая доступ к конкретным объектам ([OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)). Новые layers/stores вводить только для гарантии, которую нельзя получить существующим механизмом.

- [ ] **S1 / J1, J3, J5 — связать именно токен с authority.** Introspection проверяет полный подписанный credential, trusted key/issuer/type/audience/time и связь `sub` + session ID + выданная auth version с актуальным SQL ledger. Нельзя принимать одни присланные UUID/claims или доверять флагу «уже проверено» из HTTP-запроса. Срок/контекст проверки относится к этому токену, не к любой живой session пользователя; response должен однозначно соответствовать запросу, без cross-user/cache смешения. Тест: token A + session/user/version B, token старой версии после reset, отозванная family при живой session — deny; зависимости недоступны — 503, без fallback. Не требовать отдельную таблицу каждого access JWT, если проверяемых version/family bindings достаточно.
- [ ] **S2 / J1, J3–J5 — не расширять полномочия токена.** Effective access = пересечение scope, разрешённого при issuance, текущих user permissions и допустимых действий authenticated resource audience; object/field ownership проверяет backend данных. Нельзя выдавать token со scope read и после появления у пользователя роли admin разрешать им write. Scope нельзя расширять при refresh; запрос нового ресурса/расширение grants — новая авторизованная выдача, не произвольный audience из тела. Согласовать access-version policy: либо reject/reissue при изменении grants, либо current intersection без расширения; чувствительные proof/version guards обязательны в обоих случаях. Тест: чужой audience, removed grant, role upgrade без reissue, повторная выдача после revoke, чтение чужих строк/закрытых полей — не дают лишний доступ.
- [ ] **S3 / J4 — reuse refresh должен действительно прекращать доступ.** Opaque refresh не менее 256 случайных бит; stored verifier и использованные verifiers сохраняются bounded до конца нужного detection window, иначе reuse не распознаётся. Atomic rotate и reuse/revoke outcome должны commit, даже когда HTTP возвращает отказ; не откатывать family revocation вместе с ErrInvalidToken. Strict access tokens обязаны быть связаны с отзывом этой family через session или отдельную проверяемую family generation: недостаточно запретить только следующий refresh. Для local-only уже выданные access живут до опубликованной границы отзыва. Random/malformed/чужой refresh не отзывает произвольную family по UUID; нет глобального logout-all из-за любой ошибки. Тест: параллельный refresh, replay после successful rotation, dropped response, DB rollback, cleanup detection history — после committed reuse ни новый refresh, ни strict access не работают. Политику для легитимного concurrent retry/другой вкладки явно описать: безопасность может требовать повторного входа, а не небезопасного grace.
- [ ] **S4 / J1, J2, J7 — разделить обычную ротацию и компрометацию ключа.** Обычный overlap не подходит для украденного private key: attacker может подписывать новые токены. Нужен emergency запрет compromised kid во всех validators, включая strict authority, прекращение signing и безопасный rollout нового ключа. Точное maximum key-cache age/refresh/invalidation время и clock-skew часть exposure window фиксируются в ADR и проверяются на нескольких instances; удаление ключа только из JWKS не очищает кеши мгновенно. При утрате подтверждённого trusted key state — deny, без resurrection старого key set после failover. Тест: ранее закешированный compromised key, сеть недоступна, повторное появление старого key set, смешанный fleet — не дают продолжить доступ за принятой границей. Не обещать нулевое окно для автономных consumers; если окно неприемлемо — нужен online режим/остановка трафика.
- [ ] **S5 / J2, J4, J7 — restore не должен оживлять токены.** После восстановления БД принудительно инвалидировать session/refresh families по существующей recovery policy. Для local-only этого недостаточно: до допуска трафика сделать старые JWT непринимаемыми у всех consumers через проверенный key/trust-epoch reset либо дождаться max ранее разрешённого lifetime + skew при закрытом трафике; простая смена signing key без удаления старого verification trust недостаточна. Epoch в откатившейся БД сам по себе не защита. Backup signing material, fleet restore и аварийную процедуру разделить; никаких автоматических «новый ключ при ошибке загрузки». Тест: restore snapshot до logout/reset/reuse не возвращает ни access, ни refresh authority. Способ выбрать в J1, не добавлять epoch/registry ради симметрии.
- [ ] **S6 / J1, J5 — защитить служебную проверку и границы сервисов.** Выбрать минимальную проверяемую service authentication для introspection (например, deployment-managed per-service credential либо mTLS существующего ingress), с отдельной ротацией/отзывом и фиксированными разрешёнными audiences. Не встраивать общий секрет в браузер/native app, не считать CORS/Origin/IP доказательством service identity. Introspection только для предъявленного access token своего audience, без refresh/private profile/посторонних permissions; invalid/inactive ответы без account enumeration и без positive cache на shared proxy. Это отдельная identity вызывающего backend, не новый public client-credentials flow. Тест: service A проверяет token B, revoked service credential, недоверенные proxy identity headers, unauth scanning и утечка introspection body в logs — отклоняются/не раскрывают данные. Ориентир — [RFC 7662, защита introspection](https://www.rfc-editor.org/rfc/rfc7662.html#section-2.1); его wire compatibility не заявлять до выбора полного контракта.
- [ ] **S7 / J1, J3–J6 — не повышать authentication assurance при renew.** JWT/refresh renewal, смена transport profile и обычный session refresh не обновляют время password/MFA proof и не превращают неполный login/enrollment в полноценный. В admin/sensitive маршрутах проверить текущую policy, factor/version и fresh proof, а не одну подписанную MFA=true. Consumer не может сам включить local-only для admin, пропустить middleware или довериться user/roles headers от клиента. Default-deny для защищённых route groups, явный список public routes и тест покрытия middleware при добавлении ручек. Тест: старый MFA timestamp + свежий JWT iat, pending challenge, удалённый factor, required enrollment и попытка выполнить admin API обычным user access — deny; native/public client не «доказывает себя» встроенным client secret.
- [ ] **S8 / J1, J2, J5, J6 — изоляция окружений и строгий parser.** Prod/staging/локальные копии шаблона получают разные keys/issuer/trust sets; issuer/audience не строятся из входного Host/X-Forwarded-* или token claims. JOSE header/claims с duplicate names, неподдерживаемым crit/b64/compression/nested/JWE и неоднозначными JSON types — reject; key type/alg/use/key_ops должны соответствовать выбранному контракту. kid — bounded identifier, не путь/SQL/URL. Правила «cookie или bearer» проверяются на backend и ingress, включая duplicate Authorization и неоднозначность между proxy/app; не писать собственный HTTP parser или JWT-криптографию. Тест: dev token на prod, hostile Host/forwarded header, signed ambiguous claims, unknown critical extension, malformed key metadata — fail-closed.
- [ ] **S9 / J3–J7 — ограничить атакуемые ресурсы, а не только валидный трафик.** Admission/header/token bounds до дорогой verification; раздельные bounded signing/verify/introspection/refresh budgets, суммарные connection pools по fleet, timeout/cancellation и отсутствие retry storm. Unknown kid negative cache ограничивать по размеру/времени: случайные kid не создают бесконечную map и HTTP fetch на каждый запрос. Invalid tokens нельзя превращать в безлимитные синхронные SQL audit inserts: агрегированные/redacted security metrics и sampling для hostile отказов, durable audit для значимых successful/revoke/config операций по их транзакционным гарантиям. Тест: random-kid/token/refresh flood параллельно с легитимным трафиком, logs/storage saturation, SQL/Auth/JWKS outage — ограниченные RSS/queues/network/SQL calls, контролируемые 429/503 без fail-open. Пороги capacity/latency и alert budgets измерить, не выдумывать RPS.
- [ ] **S10 / J6, J7 — проверить browser границу и утечки на всём пути.** Token/login/refresh/introspection ответы no-store, без токенов в URL/redirect/Referer, analytics/APM, error dumps и proxy access logs. Browser profile по умолчанию BFF/HttpOnly session; bearer в памяти не защищает от действий XSS. До UI определить CSP по фактическим ресурсам/Swagger, запрет небезопасного HTML и framing для чувствительных экранов; не лечить XSS ослаблением CORS. Cross-site cookie deployment требует отдельного browser/CSRF/third-party-cookie теста, а не одного SameSite=None. GET/HEAD/OPTIONS не выполняют auth/account mutations; отсутствие Origin у служебного bearer не отключает browser protections на соседних cookie маршрутах. Тест: hostile sibling origin, preflight без credentials, cookie+bearer ambiguity, direct API и redaction всей цепочки ingress → app → consumer.

### Что блокирует публикацию JWT

Уточнение S5: ожидание lifetime + skew допустимо только при подтверждённом прекращении выдачи старым ключом и отсутствии его компрометации. Если ключ украден, attacker может подписывать новые токены: одно ожидание не помогает, необходим emergency distrust по S4. Для обычной cookie rotation отдельно зафиксировать судьбу производных JWT; новый JWT iat не обновляет assurance, а security-driven revoke не оставляет неучтённых дочерних credentials.

J1 обязан зафиксировать S1–S10 contract choices (включая scope/version, family revoke, service auth, key/restore и сроки), а не откладывать их до middleware. Перед J7 для каждого S-пункта указать test/evidence и PASS/FAIL/NOT RUN; критичные нарушения token validation, scope binding, MFA/revocation, secret handling или fail-closed блокируют включение JWT. Внешняя недоступная проверка — NOT RUN и открытый gate, не PASS.

Нужны targeted review issuance/refresh/verifier/consumer authorization, негативные contract/race/fuzz tests и staging abuse/fault/restore/load. Подписанная JWT-библиотека не аудирует логику вокруг неё. Отдельный внешний pentest перед публичным production rollout полезен как независимая проверка; без него и без измерений не объявлять безопасность/ёмкость доказанными. Автоматические проверки дополняют review, а не обещают отсутствие всех уязвимостей.

## Требования к проверке токена и middleware

На основе JWT BCP: жёстко проверять signature, expected algorithm/key type, trusted issuer, audience, explicit token type и время; разные назначения имеют несовместимые правила проверки. Не принимать `none`, algorithm confusion, ID/reset/MFA tokens вместо access JWT. Это baseline [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), а не заявление об аудите будущего кода.

- Обязательные claims нашего контракта: issuer, стабильный user UUID (`sub`), единственный целевой audience, `exp`, `iat`, `jti`, публичный session ID; при использовании `nbf` проверять его. Задать max lifetime, bounded clock skew, max age и строгие типы/длины/количество claims. Версии и MFA/primary proof time — серверные, не основание для доверия просроченному/отозванному proof. При выборе OAuth JWT profile соблюдать весь [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html), включая его mandatory claims; не заявлять совместимость по одному `typ=at+jwt`.
- Signed JWT обычно читается получателем: только нужные identifiers/minimal scopes, без PII, паролей/секретов и списка всех ролей/полей пользователя. Права на строки/поля остаются у backend данных; подпись не заменяет object-level authorization. Requested scopes не расширяют current grants, а active permissions для strict режима определяются актуально.
- Только один `Authorization: Bearer …`; отклонять duplicate/ambiguous credentials. На маршруте явно задан cookie или bearer профиль; отсутствие/невалидность Bearer не даёт fallback к более слабому cookie. Не принимать JWT в query/path и не логировать headers/токены, включая proxy/APM/error traces. 401 invalid/missing credential, 403 insufficient authority, 429 limits, 503 dependency; безопасные сообщения и корректный WWW-Authenticate.
- Bounded input/header/token/JSON sizes и concurrency **до** дорогой подписи/remote lookup, crypto verification deadline/cost budget. Не строить role helper, читающий непроверенные claims. Разделить authentication principal и authorization decision; не размножать предметную валидацию в каждом handler.
- `kid` ищется только в доверенном bounded key set. Не следовать входным `jku`/`x5u`, embedded keys/произвольным issuer URLs; запрет SSRF/redirect/private-network fetch. JWKS URL из server config, HTTPS, timeout/body/key-count bounds, coalesced refresh/backoff/negative caching unknown kid. Не сеть на каждый случайный kid и не безлимитный cache. Неизвестный/retired key — reject; expired trust cache/нет usable keys — fail-closed. Политику last-known trusted keys и emergency invalidation явно ограничить, не «доверять вечно».
- Публичный JWKS — только public material, bounded responses/cache/ETag. Обычный access JWT остаётся bearer: кража позволяет replay до expiry/revoke. Refresh reuse detection не предотвращает replay access JWT. TLS, короткий TTL, отсутствие секретов в logs/URL/storage уменьшают риск, но не дают неуязвимость. DPoP/mTLS-bound access tokens — не обязательный новый слой без конкретного требования.

## Browser и CORS/CSRF

CORS регулирует браузерное чтение cross-origin ответов, а не удостоверяет сервис и не блокирует curl/ботов. План следует [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html): CORS выключен без необходимости, точные origins/methods/headers без отражения произвольного Origin. `Authorization` добавить только там, где bearer cross-origin нужен, не во все browser routes; credentials=true только для действительно cookie-based профиля, никогда вместе с wildcard origin. Preflight не требует session/JWT, но проверяет разрешённые origin/method/header и не исполняет бизнес-операцию. Сохранять Vary и проверять null/multiple/malformed Origin, hostile subdomain, разрешённые порты и proxy настройки.

Для cookie login/session/exchange/refresh/logout сохранять CSRF/Origin enforcement и Secure/HttpOnly/host-only cookies. SameSite — дополнительный барьер, не замена защите ([OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). Browser access token — предпочтительно BFF либо память, не localStorage/URL; XSS всё равно может совершать действия. Служебный bearer запрос без browser Origin разрешается его authentication policy, не имитацией Origin; Origin не service credential. Никакого общего «JWT есть — CSRF выключаем» для cookie endpoints.

## Приёмка безопасности и производительности

- Подпись/claims: forged/tampered/none/wrong algorithm, чужой issuer/audience/key/type, ID token confusion, malformed/duplicate JSON claims, expired/future/oversized token, boundary clock skew; чужие user/session/audience, scope escalation и утечка PII. Fuzz parser/header/key selection, dependency vulnerability scan и review выбранного verifier.
- Lifecycle: выдача/refresh одновременно с logout/reset/block/delete/role revoke; один successor, reuse family, expiry/absolute deadline, потерянный ответ, revoked refresh и no MFA bypass. Strict mode не принимает старые positive grants после current authority decision; local-only тестируется с опубликованным окном устаревания, не под видом немедленного отзыва.
- Ключи/сеть: planned/emergency rotation, overlap expiry, unknown-kid flood, JWKS/Auth/SQL/Redis outage, stale keys, fleet inconsistency и restore без возрождения credentials. Никакого fail-open при ошибке.
- Browser: cookie/bearer ambiguity, CSRF включая login/exchange/refresh, CORS/preflight/hostile/null Origin, XSS exposure boundaries и прямой API без браузера. Admin и object/field authorization не обходятся JWT.
- Нагрузка: отдельно локальная verification, issuance/signing, strict introspection и refresh; valid/invalid/oversized/unknown-kid traffic. Несколько Auth и resource instances, realistic token sizes, login/MFA/refresh/logout mixes, P50/P95/P99, throughput/error rate, CPU/RAM/RSS/allocations/GC/goroutines, SQL/Redis calls/pools и key-refresh requests. Soak/нагрузка-отдых/cancellation/shutdown, проверка bounded caches/queues/retries и overload 429/503. Не считать config limit или crypto ops/s пропускной способностью системы.
- Для local path цель — ноль SQL/Redis/Auth calls на обычную локальную проверку с готовыми keys; для strict — один bounded online decision без N+1/sliding UPDATE и retry storm. Online режим всё ещё нагружает authority, JWT не устраняет это сам. Cache положительной authority с задержкой отзыва не вводить как незаметную оптимизацию. Криптографию и Argon2 не ослаблять ради RPS.

Refresh rotation/reuse detection проектировать с учётом [RFC 9700, раздел 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14); не объявлять этот сервис полным OAuth сервером. J1 зафиксировал deadlines/resource ceilings и local-only окно в ADR 004; проверка этих границ — J7/A8. Профиль нагрузки/hardware и latency/error targets зафиксировать перед нагрузочной приёмкой, не выдавать защитные budgets за измеренную capacity. До проверок нельзя заявлять ни нагрузочную ёмкость, ни отсутствие уязвимостей/утечек памяти.
