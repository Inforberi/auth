### Переключатели авторизации и проверка профилей

Независимо управлять password/email OTP/Telegram и каждым реализованным OAuth/OIDC provider; public registration отдельно. Для password registration поддержать disabled/optional/required email verification. Роли/MFA/admin access не зависят от выбора метода и не становятся отключаемой проверкой через смену login profile.

Один сервис должен поддерживать сайт с password+OAuth, password с обязательным email verification, passwordless Telegram/email OTP и защищённую админку. Это комбинации настроек, не отдельные приложения/SSO/schema. Подробная матрица — [roadmap](roadmap.md#настраиваемые-способы-входа).

Приёмка: disabled method отклоняется прямым API и незавершённым callback/link, не требует своих secrets, не удаляет existing identities. Required password verification ограничивает доступ до доказательства владения email; disabled не отправляет verification mail и не помечает адрес verified. Проверить invalid configuration, последний доступ админа, concurrent settings updates и изменение политики для existing users/sessions. Выключение login method не считать автоматическим logout-all; отзыв отдельный, enforcement status/version сохраняется.

Второй фактор настраивается отдельно: TOTP через совместимое authenticator-приложение, optional SMS только с выбранным provider. MFA optional/required по роли, без отключения защиты административных операций. Под телефоном пока подразумевается SMS, не самостоятельный phone-only login. Основной current-release factor — TOTP + recovery codes; SMS не блокирует выпуск. Подробные правила — [roadmap](roadmap.md#второй-фактор), задача 13.1 ниже.

## Как выполнять

Перед реализацией подэтапа проверить ближайшие согласованные сценарии: что переиспользуется, что остаётся внутри фичи, какие контракты и гарантии должны сохраняться. Известного следующего потребителя учитывать сразу, чтобы не переписывать и не переносить ту же логику на каждом шаге. Существенное решение кратко записать в подэтапе; абстракции для несогласованного будущего не добавлять. Это постоянное правило, а не запрет обоснованного рефакторинга.

Во всех этапах соблюдать [постоянные правила читаемости](../../AGENTS.md): сразу разделять самостоятельные обязанности и держать связанное рядом. Не экономить токены за счёт корректности и поддержки; не откладывать качество на отдельную уборку и не дробить код искусственно.

До написания кода продумывать минимальный достаточный сценарий: переиспользовать подходящее существующее, передавать необходимые зависимости напрямую и не раздувать решение файлами/helpers/слоями ради симметрии. Сохранять проверки с разными гарантиями и явные транзакции; объём tests/generated не смешивать с объёмом рабочей логики.

Для каждого затронутого сценария применять [постоянное правило производительности](roadmap.md#постоянное-правило-производительности) уже при реализации: оценить SQL/Redis round trips, убрать лишние чтения/записи, ограничить concurrency/ожидания/партии/повторы, проверить indexes/locks по риску и бюджеты нескольких экземпляров. Результат подэтапа включает применимые проверки и оставшиеся ограничения. Этап 6.8b подтверждает capacity полного сервиса, а не откладывает исправление уже известных неэффективных путей.

На текущей ветке сохранять пользовательские изменения. Один подэтап — один reviewable diff: изменить код/tests/config/docs, выполнить проверки, записать результат в таблицу основного плана. Не публиковать новый flow до готовности его security prerequisites. Независимые задачи можно выполнять параллельно, зависимые — после завершения prerequisites.

Обычная проверка изменений Go: `task check` (tests + lint). Дополнительные race/integration/security/container/API checks — только по затронутому риску и перед release; весь набор не повторять после каждой мелкой правки. Если обязательная для конкретного изменения проверка недоступна или падает, записать результат и не заявлять её прохождение. Задачи ниже не разрешают prod deploy/restore ради проверки.

Текущий порядок: 0, 1.1–1.8, 4, 5.1–5.4, 5.2r и 5.2h завершены; 5.5a–d реализованы и 5.5e-local проверен → 5.6/5.7 и остальное 6 → 7/8 → 9/10 → 11/12 → 14. 5.5e-staging остаётся внешним release gate. Детализация разделов 2–3 и перенос 4.2–4.3 выполнены внутри первого этапа. Этап 0 до зависимых решений; 13.1 после 6 до любых production admin endpoints. Docs и security audit ведутся на каждом шаге.
