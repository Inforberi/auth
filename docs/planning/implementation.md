### Совместимость настроек и безопасные переключения — A6.3 / A7

Согласовано 16 октября: добавить явные зависимости настроек, а не искусственную взаимоисключаемость методов. Это план доработки; действующие ограничения и границы реализации описаны в [Auth settings](../features/auth-settings.md). Не создавать отдельный rules engine, новые пакеты или переключатели ради этой матрицы.

| Настройка / переход | Правило |
| --- | --- |
| Password, email OTP, Google, Telegram | Разрешены одновременно в любых поддерживаемых комбинациях. TOTP — второй фактор, не конкурирующий метод основного входа. |
| Все публичные методы выключены | Допустимый профиль закрытой админки. Независимый административный password+MFA вход и его защита сохраняются. |
| Регистрация провайдера | Эффективна только при включённых самом методе, общей публичной регистрации и регистрации этого провайдера. Неактивное предпочтение можно сохранить; UI объясняет зависимость, backend не включает соседние флаги автоматически. Закрытие регистрации не запрещает вход существующим пользователям. |
| Password email verification | Один режим disabled/optional/required вместо противоречивых enabled/required booleans. При выключенном password сохраняется как неактивная настройка; включение password применяет её снова. |
| Email OTP и почтовые security-сценарии | Отключение автоматического подтверждения после password registration не отключает OTP, reset, подтверждение новой почты и восстановление админа. У каждого сценария свои условия и доказательства владения. Email OTP — основной вход, не дополнительный фактор к тому же email-доказательству. |
| Включение метода / почтового сценария | Отклонять, если отсутствуют необходимые adapters, валидная operational конфигурация или secrets. Для почтового сценария нужны настроенные SMTP/outbox. Сетевая проверка соединения отдельно: сохранённая конфигурация не гарантирует доступности провайдера. Не требовать credentials только ради неактивного предпочтения. |
| Обязательная MFA | Нельзя выключить необходимый фактор в обход обязательной политики роли или защиты административных действий. До enrollment выдавать только ограниченный enrollment flow, не полноценный доступ; recovery codes не становятся самостоятельным первым фактором. |
| Последний административный доступ | Не разрешать управляемое изменение, уничтожающее последний пригодный защищённый путь super-admin. | Выключение единственного метода обычных пользователей | Не вводить общий запрет: отключение может требоваться политикой проекта. ### Переключатели авторизации и проверка профилей

Независимо управлять password/email OTP/Telegram и каждым реализованным OAuth/OIDC provider; public registration отдельно. Для password registration поддержать disabled/optional/required email verification. Роли/MFA/admin access не зависят от выбора метода и не становятся отключаемой проверкой через смену login profile.

Один сервис должен поддерживать сайт с password+OAuth, password с обязательным email verification, passwordless Telegram/email OTP и защищённую админку. Это комбинации настроек, не отдельные приложения/SSO/schema. Подробная матрица — [roadmap](roadmap.md#настраиваемые-способы-входа).

Приёмка: disabled method отклоняется прямым API и незавершённым callback/link, не требует своих secrets, не удаляет existing identities. Required password verification ограничивает доступ до доказательства владения email; disabled не отправляет verification mail и не помечает адрес verified. Проверить invalid configuration, последний доступ админа, concurrent settings updates и изменение политики для existing users/sessions. Выключение login method не считать автоматическим logout-all; отзыв отдельный, enforcement status/version сохраняется.

Второй фактор настраивается отдельно: TOTP через совместимое authenticator-приложение, optional SMS только с выбранным provider. MFA optional/required по роли, без отключения защиты административных операций. Под телефоном пока подразумевается SMS, не самостоятельный phone-only login. Основной current-release factor — TOTP + recovery codes; SMS не блокирует выпуск. Подробные правила — [roadmap](roadmap.md#второй-фактор), задача 13.1 ниже.

## Как выполнять

| Dependencies/toolchain/deploy/security настройки | `task check:security`, build/Compose/image и другие existing checks для изменённого слоя; runtime настройки сверять без чтения реальных secrets |
| Browser/SMTP/providers/операторский flow/load/GC/restore | Профильная приёмка на разрешённом изолированном стенде. Фиксировать условия и PASS/FAIL/NOT RUN; отсутствие окружения не закрывает release gate |

После исправления повторять затронутые проверки; ранее успешные несвязанные проверки не перезапускать без причины. Логи ограничивать без потери exit status и причины ошибки, оставшиеся непроверенные гарантии указывать явно. CI отдельно выполняет `task check`, `task check:api`, `task check:security` и production image build; integration/race не запускаются автоматически на каждый push. Новые scripts для выбора проверок не нужны.
