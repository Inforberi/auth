# Управление шаблонами писем

Согласованное требование25 октября2026. Будущий backend/API и раздел админки; текущая реализация project email/outbox не заменяется этим документом. UI начинать только после отдельного согласования.

## Поведение

- У каждого вида письма есть поставляемый с сервисом стандартный шаблон: тема, HTML и текстовая версия. Без пользовательской настройки он работает сразу; администратору не нужно загружать HTML для запуска.
- Администратор проекта выбирает вид письма, редактирует тему/HTML либо загружает UTF-8 `.html`, смотрит предпросмотр, отправляет тест и публикует. Отдельные действия: сохранить черновик и вернуть стандартный шаблон. Визуальный конструктор не обязателен для первого выпуска.
- Шаблоны независимы для проектов. Сначала поддержать уже реализованные verification/reset; затем тем же механизмом подключать invitation/temporary activation, email OTP, смену/привязку email и security notifications по мере готовности их consumers. Оплата в этот scope не входит.
- Для каждого вида — понятный список разрешённых подстановок с примером: название проекта, отображаемое имя пользователя, срок действия и обязательный блок действия/кода. Не предоставлять шаблону произвольный доступ к user record, credentials, БД, файлам или сети. Неприменимые к сценарию переменные недоступны.

## Backend и безопасность

- Хранить опубликованные overrides в БД соответствующего проекта; defaults — в исходниках сервиса. Отсутствующий override использует default. Новый release не перезаписывает пользовательский шаблон; сброс override — явное действие. Для платформенных писем — отдельный platform scope.
- Один render/validation путь для admin API и UI. Сохранение черновика не меняет реальные письма; публикация атомарна, использует expected version и сохраняет предыдущую опубликованную версию для отката. До публикации проверить обязательные блоки, неизвестные переменные и ограничения размеров/рендеринга. Ошибка не должна публиковать частичный или небезопасный шаблон.
- Использовать ограниченные декларативные подстановки с контекстным экранированием, без пользовательского кода/произвольных функций. HTML импорт проходит проверку разрешённых элементов/атрибутов: исключить scripts, обработчики событий, формы, iframe/object/embed и опасные URL. Проверить CR/LF в теме и формат текстового письма.
- Защитные ссылки/коды создаёт backend из доверенных URL и текущего challenge. Критический action-блок вставляется только в разрешённое место HTML: не позволять помещать токен/код в внешние URL, изображения, CSS, скрытые атрибуты или подменять адрес подтверждения/reset. Администратор меняет оформление и текст, но не правила подтверждения, TTL, получателя или полномочия.
- Предпросмотр изолирован от origin админки, без scripts/forms, доступа к cookies/storage и загрузки внешних ресурсов по умолчанию. Использовать синтетические значения вместо реальных challenge/tokens. Backend не скачивает HTML/изображения/вложения по произвольному URL; импорт — файл/текст, не удалённый fetch.
- Доступы раздельные: чтение, изменение/публикация, тестовая отправка. Project scope, version checks, действующая fresh-auth/MFA/CSRF policy и audit без body/token/password обязательны и для прямого API. Тестовая отправка ограничена частотой/параллельностью, использует SMTP выбранного проекта и синтетическое действие, не выдаёт рабочий reset/verification token.
- Шаблон рендерится один раз при создании события; итоговые тема/тело и выбранная версия принадлежат существующему зашифрованному outbox. Retry отправляет тот же payload, а редактирование влияет только на новые события. Не хранить raw token отдельно ради последующего рендеринга и не читать шаблон из БД на каждом retry. Лимиты source/rendered payload согласовать с существующими outbox/MIME bounds до реализации.
- Отсутствующий override — штатный default; повреждение опубликованного override или неизвестная версия контракта — явная ошибка, не молчаливая отправка другого письма. Любой кеш ограничен и привязан к project/type/version, с явной актуализацией при публикации.
- Новые renderer/sanitizer/editor зависимости добавлять только после согласования библиотеки и версии. Точный контракт подстановок и безопасного action-блока утвердить до кода, не собирать собственный HTML sanitizer регулярными выражениями.

## Этапы

- [ ] Backend до подключения этого раздела UI: перечень типов/подстановок, стандартные шаблоны, защищённые read/draft/publish/reset/test API, project storage/version/audit, единый renderer и integration с issuance/outbox.
- [ ] Проверки: project isolation/permissions, неизвестные переменные, XSS/URL/token exfiltration и email header injection, обязательные action-блоки, bounds, concurrent publish, defaults/reset/rollback, queued-before-edit retry и test-send limits. Новые checks выполняет Luna на snapshot; текущие SQL/crypto гарантии сохраняются.
- [ ] В согласованном A7: раздел «Письма → Шаблоны» с выбором сценария, темой/HTML upload, каталогом подстановок, изолированным preview, тестовой отправкой и явной публикацией/сбросом. Управление SMTP остаётся отдельной настройкой.
