# План: управление Auth через административный UI

Дата: **11 ноября 2026**. Статус: **план, реализация не начата**.

Основание — [инвентаризация текущих возможностей](../admin-ui-specification.md). Она описывает то, что уже работает; этот документ — необходимые дополнения и порядок их выполнения. Наличие пункта в плане не означает существующий API. UI, стек frontend и макет отдельно согласовываются с пользователем перед началом реализации.

Перед переходом к этому плану завершить только [три блока старой приёмки, оставленные пользователем 12 ноября](implementation.md#остаток-старого-плана-перед-u1--уточнение-12-ноября-2026). Поиск maximum RPS, многопроектные нагрузочные и длительные GC-прогоны не являются дополнительными условиями старта U1. Их снятие не заменяет security/эксплуатационные проверки и не превращает NOT RUN в PASS.

## 1. Результат, который нужен

Владелец открывает одну панель, создаёт проект, выбирает подходящий вариант авторизации, подключает нужные сервисы и далее управляет пользователями, доступом и настройками без редактирования ENV для каждой повседневной операции.

Новый проект не требует ручного заполнения десятков технических полей. У него есть безопасные начальные значения; необязательные функции выключены, пока не подготовлены. При этом собственный вариант настройки не запрещён: профиль — начальная конфигурация, а не жёсткий тип проекта навсегда.

**Панель должна позволять:**

- Создавать и подготавливать независимые проекты с отдельными БД; видеть состояние, приостанавливать и возобновлять.
- Выбирать методы входа, регистрацию, подтверждение почты, обязательность MFA и допустимые каналы.
- Создавать пользователей, приглашать, выдавать временный пароль, назначать роли, блокировать и удалять.
- Управлять операторами панели и локальными администраторами с разными полномочиями.
- Создавать роли и разрешения, применять их к внешним backend через согласованные API/JWT.
- Настраивать SMTP, Google, Telegram-вход и отдельного Telegram-бота для MFA.
- Настраивать сессии, JWT, внешние сервисы-получатели и доступные защитные лимиты.
- Редактировать шаблоны писем, сохраняя работающий стандартный вариант.
- Настраивать хранение данных и видеть доступную диагностику/аудит.
- Понимать, что ещё не готово, почему действие запрещено и как исправить ситуацию.

Это не требует переносить в браузер управление всеми параметрами ОС, Docker, сетью и привилегиями PostgreSQL.

## 2. Что настраиваем в UI, а что оставляем при установке

| Область | Как будет управляться | Что уже есть / что добавить |
| --- | --- | --- |
| Способы входа, регистрация, email verification | UI проекта и общая панель | Локальные API и несекретный platform bridge есть; использовать и дополнить metadata |
| Политика MFA | UI отдельно для панели и каждого проекта | API есть; добавить отсутствующий project bridge |
| Личные TOTP/email/Telegram/recovery codes | Личный кабинет владельца аккаунта | Поддержанные сценарии есть; не давать администратору читать чужие секреты |
| SMTP и provider credentials | UI с write-only секретами | Локальные API есть; добавить управление из общей панели |
| Telegram-бот и webhook | UI проекта, затем общая панель | Проектные API есть; bridge отсутствует |
| Пользователи и назначения | Одна общая панель, в пределах прав | Локальные команды есть; общепанельные mutations пока неполные |
| Permission definitions и custom роли | UI проекта | Role API есть; редактор каталога permissions отсутствует |
| Сроки сессий, OTP и других процессов | UI, раздел «Безопасность»/«Дополнительно» | Значительная часть пока ENV/config; нужны типизированные сохраняемые настройки |
| Частота отправки/попыток, пользовательские квоты | UI с единицами и допустимыми границами | Существующее enforcement переиспользовать, добавить settings API |
| Разрешённые frontend origins и адреса страниц писем | UI проекта внутри доверенных HTTPS-границ установки | Пока во многом deployment; нужны защищённые settings/проверки совместимости browser-flow |
| JWT issuer/resources/consumers/rotation | UI интеграций с серверной валидацией | Сейчас в основном deployment; два issuance switches уже сохраняются |
| Шаблоны писем | UI редактора и стандартные шаблоны | Backend management пока не реализован; есть [согласованный план](email-templates.md) |
| Сроки хранения | UI | Локальный API есть; расширить общую панель |
| Проектная preparation/lifecycle | UI → защищённый backend-процесс | Сервисы/CLI и часть lifecycle API есть; нужен полный management workflow |
| Физическое удаление проекта | Отдельная owner-only операция | Пока план; не подменять приостановкой |
| Резервные копии и восстановление | UI общей панели с отдельными правами, подтверждениями и безопасным backend executor | CLI backup/restore есть; management API, расписание/каталог для UI и полный recovery workflow ещё нужны |
| Аудит и результаты операций | Read-only UI по правам | Audit/receipts есть; общего read API журнала пока нет |
| PostgreSQL/Redis подключения установки | Конфигурация запуска / secret manager | Не вводятся обычным проектным администратором |
| Корневые ключи шифрования и технические recovery credentials | Конфигурация запуска / привилегированная эксплуатация | Не отдавать и не заменять обычной settings-формой |
| Listener, TLS/ingress, trusted proxy/network/storage targets | Конфигурация установки; UI показывает безопасное состояние | Не путать с прикладным списком разрешённых frontend origins; изменение инфраструктуры зависит от rollout |
| Предельные CPU/RAM/пулы/worker budgets | Эксплуатация, read-only в UI | Не давать проекту выделять себе безлимитные ресурсы |

Для оставленных вне UI параметров дать короткую инструкцию первоначальной установки. Это небольшой технический фундамент, а не ежедневная настройка каждого проекта. Новый SMTP/storage target вне доверенного deployment allowlist может потребовать участия владельца инфраструктуры — UI не должен обходить эту границу ради удобства.

## 3. Defaults и понятное создание проекта

### 3.1. Начальные профили

Планируем три начальных варианта:

| Профиль | Начальная настройка | Что выбирает владелец |
| --- | --- | --- |
| Сайт с регистрацией | Пароль включён, самостоятельная регистрация включена, рекомендуется обязательное подтверждение email | SMTP, дополнительные провайдеры, режим MFA; без SMTP required-email проект не объявляется готовым к этому сценарию |
| Закрытая админка / внутренний сервис | Пароль включён, публичная регистрация выключена, доступ выдаёт администратор | MFA mode: рекомендуемый `administrators`, либо осознанно `optional`/`required`; способ приглашения/создания пользователей |
| Собственная конфигурация | Без скрытого включения внешних методов; явный выбор в мастере | Методы, регистрация, подтверждение, MFA, интеграции |

Выбор профиля только заполняет первоначальную форму. Это не реализация организаций, multi-app или SSO. Пресеты не должны обходить текущие guards или включать неподготовленные функции.

### 3.2. Общие исходные значения

- Внешние провайдеры, email/Telegram MFA и native JWT не включаются без подготовленных зависимостей.
- Роли не создаются пользователю автоматически только из-за выбранного метода входа.
- TOTP и резервные коды остаются доступным строгим MFA-путём в готовом профиле; слабые каналы не заменяют административные гарантии.
- Для JWT по умолчанию использовать строгую online-проверку; local — отдельный осознанный режим с объяснением окна до expiry и существующими запретами на чувствительные permissions.
- Текущие defaults хранения: резервирование email30 дней, завершённые сессии30 дней, audit180 дней.
- Текущие defaults обычных сессий: idle168h, absolute336h; административных: idle30m, absolute12h. Перед переносом в SQL сохранить совместимые текущие значения установки.
- Текущий default access JWT2m. Native refresh bounds согласуются с session bounds.
- Default лимита ролей на пользователя —32; будущий editor меняет его только в проверенных пределах, не бесконечно.
- Для остальных TTL, пауз и budgets использовать действующие defaults владельца фичи; не придумывать новые числовые значения без причины и проверки.
- Письма без пользовательского override используют поставляемый шаблон. Для старта не надо загружать HTML.

### 3.3. Как не потерять пользовательские настройки

- Defaults применяются при создании новой настройки/проекта, а не при каждом запуске.
- Существующие настройки, credentials и пользовательские шаблоны не перезаписываются обновлением сервиса.
- Изменение «defaults для новых проектов» не меняет автоматически все существующие проекты.
- «Вернуть стандартные значения» — явное действие с показом различий и без автоматического удаления секретов.
- Не вводить скрытое живое наследование настроек от платформы на каждый запрос. Для первого выпуска достаточно явного первоначального копирования выбранного профиля.
- Если обязательная SQL-настройка повреждена или отсутствует, не подменять её ENV так, чтобы случайно открыть доступ. Нужны диагностика и безопасное исправление.

## 4. Постоянные правила реализации

1. **Настройка принадлежит своей фиче.** Domain определяет правила, service — сценарий, repository — SQL и транзакции, transport — HTTP, app — сборку. Не создавать универсальную таблицу «key/value для всего», expression engine или новый контейнер конфигурации.
2. **UI показывает эффективное состояние.** Отличать «сохранено включено», «зависимости готовы» и «функция реально доступна». Не обещать успех внешнего SMTP/provider по одному bool.
3. **Значения типизированы.** Единицы, допустимые диапазоны, взаимные зависимости и причина read-only понятны. Metadata использовать там, где это помогает форме, без обязательного универсального генератора всех экранов.
4. **Секреты write-only.** Keep/replace/clear — явные отдельные действия по контракту фичи. Никаких plaintext GET, UI-масок в POST, токенов в логах или «прочитать старый пароль».
5. **Версии и authority сохраняются.** Expected version, fresh proofs, actor из session, permissions и last-owner guards проверяются backend в правильной транзакции. Связанные проверки не разносить ради уменьшения файлов.
6. **Изменения имеют объявленный момент действия.** Сразу, со следующей выдачи credentials, после подтверждения внешнего подключения либо после rollout. HTTP200 не должен обещать больше, чем фактически применилось.
7. **Обновление конфигурации ограничено по ресурсам.** Переиспользовать существующие версии/наблюдатели/профили, не делать SQL-read настроек на каждую мелкую операцию без необходимости и не крутить бесконечный polling. Сохранить немедленный SQL authority там, где он уже гарантируется.
8. **Проекты не получают глобальные секреты и чужие defaults.** Общепанельная команда работает в точном проектном контексте; platform session не превращается в произвольную project cookie или обход локального service.
9. **Рабочие данные сохраняются.** Для установленной схемы нужен согласованный upgrade, не сброс БД/повтор initial setup. Миграционный путь определить до реализации блока.
10. **Безопасность не настраивается до нуля.** UI не отключает parameterized SQL, hashing, проверку подписи/issuer/audience, Origin/CSRF, replay-защиту и контроль прав. Редактируемый budget остаётся внутри технического потолка установки.

### 4.1. Совместимость настроек, которую UI должен объяснять

| Сочетание / действие | Правило |
| --- | --- |
| Обязательная проверка почты | Нужна готовая доставка и корректная frontend-страница. Нельзя молча пометить email подтверждённым, чтобы завершить wizard |
| Google/Telegram-вход | Нужны соответствующие credentials, trusted callback и готовый adapter. Preference регистрации провайдера может храниться выключенным/неэффективным; не придумывать новый запрет там, где backend допускает это |
| Email/Telegram как второй фактор | Только допустимые primary/factor пары; текущий поддержанный профиль — после пароля. Подготовленный канал ещё не включённый фактор |
| MFA `optional` | Не удаляет личные факторы и не отменяет требование роли/действующего proof |
| Отключение фактора или метода | Сохранить текущие last-factor/last-administrator и factor-in-use guards; не выполнять скрытую массовую отвязку |
| Native JWT и session exchange | Независимые переключатели; не делать их взаимоисключающими |
| Local JWT | Явное окно действия до expiry и запреты на чувствительные permissions; не обещать мгновенный отзыв |
| Session/refresh/OTP сроки | Проверять совместные bounds в одном сохраняемом сценарии; предупреждать о последствиях для текущих credentials |
| Уменьшение retention | Отдельное явное подтверждение необратимой очистки; увеличение срока не восстанавливает данные |
| Одна панель, несколько проектов | Операторская authority не заменяет project session/proof и не открывает соседний project scope |

## 5. Блоки реализации

Блоки идут последовательно. Для каждого сначала фиксируется конкретный контракт, затем делается законченный набор изменений и его целевая проверка. Не переделывать уже работающие сценарии только ради новой формы UI.

В U1 фиксируется конечный перечень первого выпуска. Дополнительные интеграции, настройки и экраны после этой границы оформляются отдельным запросом, а не незаметно продлевают подготовку UI. Технические возможности, оставленные deployment-only, не являются незавершёнными UI-формами.

### U1. Контракты, области управления и defaults

**Задача:** перед кодом договориться, что именно сохраняет каждая форма и кто имеет право её менять.

- [ ] По инвентаризации185 ENV-параметров разметить каждый: сохраняемый через UI; seed при установке; read-only deployment; секрет; технический потолок.
- [ ] Для каждой формы зафиксировать scope: общая панель, defaults новых проектов, конкретный проект, личный аккаунт.
- [ ] Зафиксировать права владельца платформы, обычного оператора и проектного администратора; какой набор действий доступен из одной операторской сессии.
- [ ] Уточнить owner-only destructive authority: для управления физическими проектами — владелец платформы, не любой actor с обычным manage permission. Передачу этого права не выводить из названия роли.
- [ ] Зафиксировать начальные профили и правила явного применения defaults.
- [ ] Для каждой новой API-группы определить read/update/result, версии, secret actions, readiness, совместимость старых данных и ошибки. Существующие контракты переиспользовать.
- [ ] Отделить изменение бизнес-политики от включения технической capability. Новая кнопка не должна позволять включить отсутствующий adapter.
- [ ] Обновить UI-спецификацию матрицей «экран → данные → команда → последствия → ограничения».

**Готово, когда:** ни одна планируемая форма не сохраняет «непонятный ENV вообще»; есть конечный перечень настроек и их владельцев, без реализации интерфейса.

### U2. Сохраняемые настройки безопасности и API состояния для UI

**Задача:** добавить управление теми повседневными настройками, которые пока живут только в config.

- [ ] Добавить feature-local settings для обычных/admin session durations, свежести подтверждений и поддержанных OTP/verification/reset/invitation/temporary-password TTL/cooldown.
- [ ] Сохранить существующие Auth/MFA/retention APIs; расширять их только по ответственности, не объединять всё в один гигантский DTO.
- [ ] Добавить редактируемые пользовательские/IP/project/consumer budgets, где они нужны владельцу; технические пределы admission/пулов/памяти остаются deployment ceiling.
- [ ] Добавить управление допустимыми frontend origins и адресами frontend-страниц verification/reset/invitation/email-change. Только доверенные HTTPS-адреса и разрешённые переходы, без произвольных callback/redirect URL, ослабления SameSite/CSRF и передачи токенов на неподходящий origin. Browser same-site ограничения должны быть видны пользователю, а не «исправляться» отключением защиты.
- [ ] Включить настраиваемый предел ролей на пользователя с default32 и совместимостью уже существующих назначений. Не удалять лишние роли автоматически при понижении лимита.
- [ ] Для каждой смены TTL/политики определить влияние на существующие сессии/challenges: новые выдачи, отзыв или запрет нового действия. Не обещать ретроактивное изменение подписанного `exp` у local JWT.
- [ ] При ужесточении сохранять требования безопасности уже действующих сценариев; изменение срока хранения не должно менять lifetime доступа.
- [ ] Добавить минимальный публичный discovery для экрана до входа: разрешённые эффективные способы входа/регистрации и необходимые публичные признаки. Не отдавать секреты, внутренние топологии, администраторов или персональное состояние аккаунта.
- [ ] Добавить безопасные read-модели readiness/настроек для форм: текущее значение, единицы/ограничения, необходимость повторного входа или rollout там, где это необходимо.
- [ ] Проверить применение между экземплярами через существующие версии/наблюдатели. Не создавать владельца budgets/пулов заново на запрос и не сбрасывать Redis counters при каждом сохранении.

**Готово, когда:** UI может прочитать, изменить и объяснить основные повседневные security-настройки без редактирования ENV; глобальные пределы установки не обходятся.

### U3. Единое управление проектами и административными действиями

**Задача:** довести общую панель до выбранной модели «один оператор управляет проектами», не создавая impersonation.

- [ ] Добавить недостающие platform management команды пользователей: создание, приглашение, временный пароль, статус, удаление и initial email binding.
- [ ] Добавить отсутствующие bridge-операции настроек: MFA проекта, SMTP, providers, Telegram bot, retention и новые группы U2. Не возвращать секреты и не копировать platform credentials в проект.
- [ ] Довести подготовку проекта из UI: intent → существующие preparation services → проверенная активация → статус/result. Длительную работу не держать в HTTP-транзакции.
- [ ] Добавить изменение отображаемого имени/допустимых метаданных проекта. Immutable UUID/binding и используемый slug не переименовывать как обычную строку; custom domain/move storage — только отдельно согласованный защищённый workflow, не поле DSN в форме.
- [ ] Использовать существующие stage/receipt/idempotency и bounded execution; не добавлять отдельный брокер/оркестратор только ради кнопки. Привилегированный доступ к DDL отделить от обычного API runtime.
- [ ] Различать созданную запись, подготовленную БД, готовую конфигурацию и доступность входа. Ошибка показывает этап и допустимый retry, а не предлагает создать дубликат.
- [ ] Добавить CRUD/приглашение операторов общей панели в минимально нужном составе, ограниченное делегирование и защищённое назначение административных полномочий.
- [ ] Закрыть недостающий безопасный путь назначения local system administrator из общей панели без копирования identity платформенного владельца в каждый проект. Не обходить readiness/last-admin guards.
- [ ] Дополнить platform role bridge редактированием обычных ролей и корректной MFA readiness вместо постоянного отказа для mfaRequired.
- [ ] Физическое удаление проекта оформить отдельной owner-only командой: preview, серверная проверка наличия пользователей, явное подтверждение точного проекта/потери данных, ограниченный confirmation intent и отдельный проверяющий executor.
- [ ] Backup/restore включить в обязательный scope будущей админки по уточнению пользователя13 ноября: выполнить U3.1 ниже. Не изображать восстановление обычным unblock и не обещать восстановимость окончательного удаления без проверенной копии и ключей.

**Готово, когда:** поддержанные повседневные команды выполняются одной операторской сессией в точном project scope; создание проекта не заканчивается необъяснённым `pending`, dangerous actions не получают скрытого bypass.

#### U3.1. Резервные копии и восстановление из админки

Это будущий management-функционал. Сейчас существуют `task backup`, `task restore`, скрипты и recovery SQL/runbook, но HTTP-каталога копий/управления заданиями пока нет. Скрипты и текущие гарантии переиспользовать, не писать второй restore pipeline и не запускать shell/DDL непосредственно из HTTP handler.

- [ ] Отдельный раздел «Резервные копии» для проекта и отдельный — для общей БД панели. Доступы на просмотр, создание, скачивание, удаление, расписание и восстановление разграничить; project admin не получает копию общей панели/соседнего проекта. Восстановление и необратимые действия — явно уполномоченный владелец с fresh proofs, не любой actor с обычным users.manage.
- [ ] Показывать копии: opaque ID, область/проект, дата, размер, версия схемы/приложения, integrity/verification status, нужные key IDs, статус задания и безопасная ошибка. Не возвращать DSN, пароль БД, raw signing/master keys или произвольные server paths.
- [ ] Действия: «Создать сейчас», «Проверить копию», защищённое скачивание/удаление, «Восстановить». Скачивание содержит чувствительные данные и требует собственного права/аудита; архивы не становятся публичными файлами.
- [ ] Управлять расписанием и retention копий. Начальный профиль на основе существующего CLI: каждые24h, хранить7 копий; это стартовое значение, не гарантия достаточного RPO для любого проекта. Сохранённое расписание не переписывается обновлением. Задания/повторы/дисковый расход и суммарная concurrency ограничены; не создавать безлимитные pg_dump одновременно для всех проектов.
- [ ] Backup должен обозначать свой состав: БД, требуемая конфигурация и ссылка на защищённый recovery key set. Одного pg_dump недостаточно для восстановления зашифрованных данных. Не публиковать «полная копия», если необходимые ключи не сохранены/непроверены. Root keys защищённо резервируются отдельно; браузер их не читает. Архивы и key backups хранить с контролем доступа и шифрованием подходящим инфраструктурным механизмом, не самодельной криптографией. Локальный volume не защищает от потери хоста; место внешнего хранения выбирается из разрешённых backend targets, не произвольного URL/пути.
- [ ] Для общей панели и нескольких БД записывать manifest с точными project/realm IDs, binding и версиями. Не считать независимые pg_dump автоматически одной общей транзакционной копией всех проектов. Чужой/несовместимый архив/отсутствующий ключ/повреждённая копия — отказ до разрушительных действий.
- [ ] Restore: выбрать доверенную копию и точную цель → preview последствий → повторное подтверждение личности и имени проекта → проверка текущих полномочий/версий/наличия пользователей → maintenance/drain writers → защитная pre-restore копия → восстановление/upgrade/grants/security recovery → проверенный результат. UI передаёт IDs и подтверждения, не имя физической БД, DSN или исполняемый SQL.
- [ ] Обычный pg_restore-архив нельзя считать безопасным произвольным upload. Для первого выпуска восстанавливать управляемые доверенные копии; импорт внешнего dump требует отдельного привилегированного проверяемого workflow, а не выбора файла любым project admin.
- [ ] Старые cookie/refresh/одноразовые proofs инвалидируются; для JWT требуется согласованный новый trust. Восстановленные старые пароли, роли, блокировки, удаления и контакты сверяются с актуальной независимой историей либо проходят контролируемое восстановление. Одно увеличение auth_version не восстанавливает утраченную после backup историю. Доступ не открывается автоматически по одному успешному SQL healthcheck.
- [ ] При сбое API/traffic остаются закрытыми, UI показывает этап и допустимый recovery; повтор не исполняет заново уже подтверждённую destructive-команду без сверки outcome. Не обещать instant/безостановочный restore.
- [ ] Восстановление общей БД может временно отключить саму панель и её сессии. Статус/receipt restore хранить так, чтобы его не откатил целевой архив; завершение и восстановление доступа имеют проверенный независимый путь. Не переоткрывать initial setup как обход.
- [ ] При удалении проекта судьба retained backups и ключей определяется отдельной явной политикой; не удалять их молча и не обещать восстановление после окончательного уничтожения нужных ключей.

**Готово, когда:** владелец из панели создаёт/проверяет копию и инициирует защищённое восстановление выбранной области, видит результат, а тестовый restore с нужными ключами не возвращает отозванные credentials/права и не затрагивает соседние БД. Реальные production restore/deploy требуют отдельного разрешения.

### U4. Каталог разрешений и удобная работа с доступом

**Задача:** пользователь создаёт свои роли и определения разрешений, а не редактирует deployment-файл для каждого нового права.

- [ ] Добавить project-scoped CRUD определений permissions с key/name/description/group; built-in security keys оставить защищёнными от переопределения.
- [ ] Технический key после использования не переименовывать молча. Удаление/архивация обязаны учитывать ссылки из ролей, JWT resources и действующих интеграций; не создавать неизвестные grants.
- [ ] Разделить поставляемые definitions, проектные пользовательские definitions и доверенный каталог внешнего backend; определить владельца/namespace и разрешённые изменения.
- [ ] Добавить read API нужного каталога для общепанельной формы. Не подставлять каталог платформы вместо каталога выбранного проекта без явного контракта.
- [ ] Сохранить текущие create/update/assign/revoke service и транзакционные guards. Permission editor не должен позволять выдать себе системные полномочия.
- [ ] Для полного управления добавить явное удаление/архивацию обычной роли с проверкой назначений и зависимостей; не удалять её вместе с пользовательскими полномочиями молча. Системные роли этим API не удаляются.
- [ ] Поддержать ручное создание definitions и ограниченный проверяемый импорт JSON, если нужен первый согласованный consumer. Автоматический URL-fetch/discovery/hot-sync не добавлять без отдельного реального протокола и модели доверия.
- [ ] Если нужны поставляемые шаблоны ролей, отдавать их отдельным read-контрактом; применение создаёт обычную роль после явного действия, не автоматически выдаёт права.
- [ ] В UI явно различать определение разрешения, состав роли и назначение роли человеку; показывать итоговый доступ через существующий read API.

**Готово, когда:** свои definitions и роли управляются через UI/API; внешний backend понимает стабильные keys и сам защищает свои строки/поля. Универсальный визуальный конструктор бизнес-политик CRM в этот блок не входит.

### U5. Интеграции, JWT и секреты

**Задача:** подключать поддержанные внешние сервисы без ручного изменения manifest для каждого повседневного действия.

- [ ] Для SMTP/Google/Telegram использовать существующие encrypted settings/validators и дополнить общепанельный доступ из U3, а не писать второй pipeline.
- [ ] Дать формы подключения с понятной проверкой: SMTP connection test не называть доставкой письма; готовность webhook не выводить только из ответа Telegram.
- [ ] Добавить сохраняемые trusted JWT resource/audience definitions: scope allowlist, strict/local, TTL и явные гарантии отзыва. Client request не выбирает себе более слабую проверку.
- [ ] Добавить consumer management: создать, ограничить audiences, показать новый секрет один раз, ротировать с ограниченным overlap, отключить. Читать обратно raw secret нельзя; хранить verifiers по существующему контракту.
- [ ] Добавить безопасное серверное управление проектными signing keys: сгенерировать/ротировать, увидеть только metadata/public material, контролировать активный и retiring key. Корневой encryption key установки не становится полем этой формы.
- [ ] Проверить совместимое окно старых ключей, сроки уже выданных JWT, JWKS/consumer cache и несколько экземпляров. Emergency rotation и local-expiry последствия описать явно.
- [ ] Существующие sessionExchange/native switches, strict introspection, refresh reuse protection, browser/native разделение и немедленный SQL revoke сохраняются.
- [ ] Определить применяемость runtime-изменений без перезапуска по группам. Параметры, которые требуют rollout, показывать так, а не имитировать мгновенное сохранение.

**Готово, когда:** владелец подключает SMTP/providers/внешний backend и ротирует доступные проектные credentials через UI, не получая лишний доступ к чужим секретам или произвольным сетевым адресам.

### U6. Шаблоны писем, личные экраны и наблюдаемое состояние

**Задача:** закрыть оставшиеся пользовательские данные и формы, которые не следуют автоматически из технического API.

- [ ] Выполнить [существующий план шаблонов писем](email-templates.md): поставляемые defaults, project/platform scope, subject/HTML/text, разрешённые переменные, draft/preview/test/publish/reset/rollback.
- [ ] Использовать один безопасный render path; UI HTML не исполняет код и не получает произвольные user records/секреты/файлы/сеть. Action URL/OTP создаёт backend.
- [ ] Test mail разрешён только допустимым адресатам, с quotas/правами. Preview использует синтетические значения, изолирован от session origin и внешних запросов.
- [ ] Добавить минимальный self-profile read: понятные собственные контакты/привязанные способы входа и состояние аккаунта, чтобы кабинет не ограничивался UUID. Редактирование профиля — только согласованные поля, не схема будущей CRM.
- [ ] Свести данные личной безопасности в пригодный для экрана read-contract, переиспользовав текущие owners/guards. Подключение фактора, предпочтение, TOTP secret и recovery codes не превращать в обычные редактируемые поля пользователя.
- [ ] Добавить read API security audit с ограниченной пагинацией/фильтрами и redaction; права и scope отдельно для проекта/панели. Не отдавать credentials, bodies OTP и технические секреты.
- [ ] Добавить только реально нужную диагностику delivery/preparation/integration failures. Различать «принято», «доставлено», «получатель прочитал»; последний статус без внешнего доказательства не показывать.
- [ ] Для dashboard определить поддержанные counters/read API либо отказаться от выдуманных real-time графиков. Не выполнять полный проход users/sessions ради каждого открытия панели.

**Готово, когда:** у экранов есть настоящие данные, понятные ошибки и работающие defaults, а не только статические макеты и обещанные кнопки.

### U7. Приёмка management API и согласование UI

**Задача:** завершить backend-контракты и спроектировать интерфейс под них, не начинать новую бесконечную серию функций.

- [ ] Проверить сценарии создания нового проекта с defaults, повторного запуска существующей установки и обновления без потери пользовательских значений.
- [ ] Проверить две независимые проектные БД, platform/project/personal scopes, отсутствие authority через чужой origin/UUID/роль.
- [ ] Проверить версии, no-op, concurrent updates, lost-response/replay, unknown outcomes, last-owner/last-factor и необходимые freshness guards.
- [ ] Проверить секреты: write-only, rollback/rotation, отсутствие raw значений в API read/logs/аудите и отсутствие network/provisioning bypass.
- [ ] Для затронутых hot paths проверить настройки/версионирование/бюджеты: нет лишних SQL/Redis кругов, N+1, сброса admission, новых пулов/очередей на запрос. Нагрузку повторять только по реально затронутой гарантии.
- [ ] Luna выполняет целевые проверки законченного delta. Не повторять весь старый task check/MP7/нагрузку после каждой формы; reuse валидных PASS сохраняется.
- [ ] Обновить OpenAPI, текущую UI-спецификацию и правила defaults/переходов в том же блоке реализации.
- [ ] Вместе с пользователем сверить имеющийся примерный макет: страницы, навигация, доступы, основные/расширенные настройки, предупреждения и тексты ошибок.
- [ ] Перед первым frontend-кодом явно сообщить о переходе к UI и получить отдельное согласование стека/макета. Сам этот план не разрешает начать UI.

**Готово, когда:** согласованный перечень UI-действий имеет рабочие API и состояния. Оставленные deployment-параметры объяснены и не выглядят поломанными формами.

## 6. Как будет выглядеть повседневное использование

1. При установке оператор задаёт инфраструктурные подключения и корневые секреты один раз.
2. Первый владелец проходит защищённый setup, выбирает MFA policy и входит в общую панель.
3. Создаёт проект и выбирает начальный профиль.
4. Видит готовые defaults; заполняет только необходимые интеграции, например SMTP для обязательной проверки email.
5. Дожидается проверенной подготовки/активации или видит конкретную исправимую причину отказа.
6. Создаёт пользователей/приглашения или разрешает саморегистрацию, настраивает роли и permissions.
7. При необходимости подключает Google/Telegram, второй фактор и JWT для своего backend.
8. Далее меняет повседневные настройки, письма, доступ и сроки хранения в UI. Не переходит к ENV для обычной операции.

## 7. Границы и порядок старта

**Следующий согласуемый блок — U1**, затем U2. Начинать с редактора всех ENV, нового config framework, frontend-заглушек и декоративного dashboard не нужно.

Этот план не добавляет оплату, entitlements, общий пользовательский SSO, организации/multi-app, Mini Apps/Stars, SMS-MFA или passkeys. Они остаются отдельными будущими решениями. Нельзя считать backend уже реализованным только потому, что возможность подробно описана здесь.

Открытые security/эксплуатационные gates не закрываются подготовкой management API или макета. Реальные provider/SMTP проверки выполняются при подключении соответствующего окружения, UI-проверки — после появления UI. Предельная нагрузка снята пользователем с обязательного остатка старого плана; её дальнейшее измерение — отдельная задача. Неподтверждённую capacity не писать на странице «Статус системы».
