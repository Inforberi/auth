### Результат 5.7b — 11 октября 2026

Реализован внутренний ProvisionService.ReissueInvitation для существующего provisioned pending UUID. Actor/key/target команды сохранены отдельно от provisioning; повтор возвращает Reused без отправки, другой target с тем же ключом конфликтует. Пользователь блокируется до контакта; pending/deleted/activation marker/credential/contact guards проверяются внутри транзакции. Замена challenge и encrypted job, durable last_invited_at, command identity и reissued audit атомарны. Первичное Invite тоже учитывает cooldown; cleanup challenge не сбрасывает историю отправки. Истечение/исчерпание доставки не требует нового UUID.

Env явно задают reissue cooldown и actor/project attempts-per-minute; Redis fail-closed, HMAC keys, deadline 5s, существующие workers/GC. Новых routes/Swagger/admin permissions/UI нет; actor attribution не означает authorization. Только исходная 000001 up/down изменена, рабочая БД/env/secrets не тронуты. Durable command metadata не очищается как audit: поздний replay не становится новым письмом. Старое уже отправленное письмо не отзывается, но его token после replacement недействителен.

Проверено: task go:fmt, go test ./..., lint (0 issues после удаления лишнего параметра тестового helper), race account service/config, полный TestPostgresSchema на disposable PostgreSQL 18.6 up/down/up (3.938s). 16 одинаковых команд дают один replacement, 16 разных — один допуск; old token invalidation, cooldown/conflict, pending guards, activation/reissue race, audit rollback с сохранением старого token и выдача после cleanup. Это не нагрузочная приёмка, SMTP/browser E2E или Redis fault E2E нового flow. Нагрузочный mixed/multi-instance прогон 6.8b оставлен на конец перед release; оптимизацию каждой фичи не откладываем.

Временный контейнер PostgreSQL `auth-reissue-check-20261011` и его тестовые данные удалены после проверок. Рабочая БД не затронута; коммит не выполнялся.

### Результат 5.7a — 10 октября 2026

По запросу пользователя реализован backend password provisioning/invitations: pending user/profile/optional contact, actor-scoped durable request identity/HMAC fingerprint, отдельный digest/encrypted outbox/audit. Provisioning независим от public registration, не назначает роли/grants/verification/пароль/session. Повтор команды возвращает тот же UUID без нового письма, изменённый payload и занятый email дают конфликт без auto-merge. Actor — attribution, не permissions; публичный admin endpoint не подключён.

Optional POST activation с Origin/no-store и service policy/token validation, Redis IP/global budgets, indexed preflight перед shared Argon2. Account repository атомарно потребляет version/expiry-bound token, записывает credential/verification, active/version/marker/audit. Replay и stale authority дают invalid_invitation, cookie/session не создаются. Block/delete отменяют приглашение; durable activation marker исключает bypass через unblock даже после cleanup. Третья очередь account delivery использует текущий fair bounded worker/lease/backoff; expiry/exhausted GC и audit retention используют текущие indexed batches. Исходная 000001 up/down, без новой миграции или применения к рабочей БД; cfg disabled по умолчанию.

Проверено: formatter, `go test ./...`, lint (0 issues после исправления complexity guard), targeted race account/password services и router, Swagger generation/drift, disposable PostgreSQL 18.6 up/down/up/full correctness. SQL: 16 concurrent activations дают один успех; 16 одинаковых команд создают один UUID. Idempotency/conflict/unique email/purpose isolation/expiry/replay/version/block/delete, activation/provision audit rollback, delivery retry/stale lease/expiry cleanup и no status bypass проверены. HTTP: origin/format/errors/429/503/no cookie/GET/disabled route/no admin route и Swagger DTO/routes проверены. Это не full load test, external SMTP/browser или production acceptance. 5.7b reissue invitation и future non-password/admin flows остаются открытыми; [контракт](../features/invitations.md).

Временный PostgreSQL приглашений удалён с исключительно синтетическими данными после проверок. Рабочая БД/env/secrets не менялись; коммит не выполнялся. Уже применённую 000001 не сбрасывать: перенос схемы согласовывается отдельно.

### Аудит нагрузки — 10 октября 2026

Проверены текущие login/register/session validation/refresh/list/revoke, password change/recovery, verification/email change, PostgreSQL/Redis pools/лимиты и фоновые delivery/retention. Runtime-код и схема при аудите не менялись. На отдельном PostgreSQL 18.6 применена текущая 000001 и синтетические данные: 100 000 active users/emails/credentials/sessions/verification challenges/outbox/password audit/email-change intents, отдельно 10 000 недавно удалённых tombstones. Только SELECT EXPLAIN ANALYZE/BUFFERS, после ANALYZE; временный контейнер и его данные удалены. Это диагностика планов, не HTTP load test/P95/P99 или подтверждение capacity.

Приоритетные результаты для 6.4/6.8 перед дальнейшими фичами:

1. Login без распределённых IP/account/admission limits и общего hash concurrency budget: PasswordService.Login делает SQL lookup и Argon2 Compare; register/change-password/email-change Request также не входят в hashSlots recovery. Текущий новый hash использует 64 MiB и p=32; recovery ограничен двумя слотами, но это не общий бюджет процесса. При массовых запросах CPU/RAM могут исчерпаться раньше DB pool. Не ослаблять password hashing для экономии: нужны admission до дорогой работы, общий bounded budget с deadline/overload response и измеренный профиль. Read-only credential lookups/CreateUser не имеют собственного operation deadline, в отличие от password/session transaction helpers; HTTP WriteTimeout не заменяет такой deadline.
2. Delivery cleanup verification/reset выполняется перед каждым Claim, без LIMIT/партии. Verification predicate на стенде проверил все 100 000 challenges через joins с emails/users (Parallel Seq Scan, 100 000 суммарно отфильтрованных строк), хотя удалять нечего. Worker poll — раз в секунду, до десяти claims при jobs; каждый экземпляр API повторяет scans. Нужны отдельный paced bounded cleanup и дешёвый claim, согласованный lock order/SKIP LOCKED/timeout; обязательные актуальные status/version/expiry guards сохраняются, не считать lifecycle cleanup безопасно удаляемым дублем.
3. Retention и outbox eligibility используют volatile clock_timestamp() в range cutoff: наличие ORDER BY/index/LIMIT не ограничивает scanned rows. На стенде password audit и session retention вернули 0 кандидатов, но каждый отфильтровал 100 000 строк; owner reservation отфильтровал 10 000 tombstones. Outbox при 100 000 future available_at тоже отфильтровал все строки ради 0 jobs. Сравнительный SELECT с statement_timestamp() для индексной границы дал Index Cond и 2–3 shared buffers вместо полного прохода. Предыдущая функциональная приёмка worker подтверждает correctness, не его эффективность на больших таблицах. Для coarse candidate cutoff нужен stable statement time/однократное DB time, а фактические single-use/lease/expiry security decisions сохраняют свои гарантии. [PostgreSQL volatility](https://www.postgresql.org/docs/18/xfunc-volatility.html).
4. Session refresh у абсолютного deadline: timeLeft <= threshold запускает UpdateSession даже когда уже существующий expires_at равен absolute_expires_at. Последний день default lifetime может превратить каждый protected request в лишнюю transaction/user lock/UPDATE/WAL/Set-Cookie без продления. Concurrent snapshots также дают повторные writes; UPDATE может уменьшить expires_at относительно уже выполненного конкурентного refresh. Нужны no-op для неподлежающего продлению срока и атомарный монотонный conditional refresh с различением already-refreshed и genuinely inactive; отзыв/version enforcement не убирать.
5. Email-change cleanup фильтрует GREATEST(protect_until,recovery_expires_at), но индекс/order основан на protect_until. На 100 000 живых intents фильтровались все строки, даже после замены времени на stable: нужен совпадающий expression cutoff/order/index, не слепое добавление индексов. Этот путь opt-in, но до его включения исправление обязательно.
6. Нагрузочный профиль ещё не задан. MAX_CONNS=10 ограничивает pool одного API, не суммарные connections всех replicas и не очередь handlers/Argon2. Нет общего HTTP admission budget; global register/reset limits 100/min и IP-based rules за proxy требуют настройки продукта и trusted-proxy policy, не доверия произвольному X-Forwarded-For. Retention 100 rows/min/table/instance имеет потолок 144 000 rows/day/table/instance, не гарантирует отсутствие backlog при большем поступлении; добавить измерения lag/DB waits/ошибок/rows scanned/CPU/RAM и overload/recovery acceptance вместо обещания «любое количество».

Подтверждённые полезные ограничения: login SQL на стенде использовал email UNIQUE и user/credential PK, session validation — token/user PK (1 строка), N+1 в этих путях нет. Protected validation остаётся SQL-authoritative по ADR 002: Redis не заменяет revoke/status/version. Argon2/SMTP выполняются вне SQL transactions; recovery budgets/Redis expiry, session page 50+1/keyset, pool limits/deadlines большинства mutation paths, transaction rollback и retention batch size полезны. Вторичная проверка доступа в sensitive transaction и FK/UNIQUE не являются бесполезным дублированием. Существующая регистрационная проверка occupied email до Argon2 экономит expensive hash; UNIQUE всё равно обязателен для race.

Полная multi-instance нагрузка, production hardware/IO, Redis failover/шторм, bloat/autovacuum и SMTP throughput не проверялись. Readiness endpoint делает PostgreSQL/Redis ping на каждый запрос, malformed session cookie тоже доходит до SQL lookup; учитывать в admission/edge policy без отключения readiness/security. Результат: сейчас нельзя утверждать, что лишней нагрузки нет или что она не возникнет при большом онлайне. Рекомендация — сначала согласовать и исправить пункты 1–5 в рамках 6.4/6.8, затем нагрузочная приёмка с явными целями; не внедрять cache-only access или менять архитектуру без нового решения.
