### Результат AS6a-local и lifetime regression — 16 октября 2026

После анализа AS5/AS6 выбран минимальный первый security diff: новое обычное/system назначение активному пользователю повышает auth_version в существующем UPDATE users внутри assignment transaction. No-op grant ничего не меняет; revoke уменьшает live permissions без обязательного logout-all. Pending сохраняет auth_version, потому что live session ему запрещена, а version-bound приглашение/активация должны переживать назначение роли до входа. Повторный login/MFA выдаёт новую session; role API не выдаёт token и не обновляет старую session. Переиспользуются ordered user locks, текущие permissions, audit и auth_version boundary. Нет schema/env/dependencies, fan-out UPDATE sessions/users, дополнительных SQL/Redis calls на protected read, cache или новых workers.

Изменены applyAssignment, существующие access/system/HTTP SQL fixtures и session service boundary tests; контракт/ADR/план актуализированы. SQL tests проверяют две старые sessions после grant, stale refresh rejection, запрет старой authority, доступ новой synthetic session, отсутствие invalidation на no-op/revoke, 16 concurrent grants с одним auth_version bump, rollback assignment/обеих версий при audit failure и сохранение pending activation version. HTTP fixture теперь ждёт 401 для старой cookie; новое authenticated состояние моделируется отдельной synthetic session, не UPDATE auth_version старой session. Это не реальный primary/MFA/browser E2E. Сроки в service regression: сохранённый absolute deadline не растёт от новых defaults и не пересчитывается задним числом меньшим default; refresh не обновляет primary/MFA timestamps. Точные expiry/NoRefreshAuth/absolute clamp проверки существовали и сохранены.

Проверки: целевые Go tests PASS; go test -race ./internal/auth/session/service ./internal/access/... PASS; task go:fmt и task check PASS, lint 0 issues (прежнее предупреждение formatter extra-rules не исправлялось вне scope). Полный disposable PostgreSQL 18.6 package -race сначала выявил прежнее HTTP ожидание 200 со старой cookie; fixture исправлен, полный suite PASS 33.643s. После финального pending исключения TestAdministratorAssignmentsSchema/TestAccessHTTPSchema PASS в targeted run 3.161s; отдельный явно перечисленный TestPostgresSchema/(access_roles|invitations|invitation_reissue|temporary_password) -race -v PASS 4.271s, включая новый pending check. Полный suite после последнего узкого pending изменения не повторялся. Swagger paths/DTO/annotations не менялись, generation/drift не повторялись; Go route/contract tests прошли в task check.

Обоснование re-login при новом grant согласуется с [OWASP Session Management: privilege changes](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#renew-the-session-id-after-any-privilege-level-change); выбранная auth_version политика — проектное решение, не утверждение о требовании logout каждого пользователя при любом edit. AS6b (permissions edit уже назначенной роли без массового UPDATE), AS5 (отдельные admin idle/absolute значения и bounded activity touch) и A6.3 остаются открытыми. Не объявлены готовыми новое MFA-role enforcement, JWT, browser/SMTP/provider/fault/load/GC/restore и pre-ui/A8.

Тестовый PostgreSQL container/volume с synthetic data удалён после проверки точного ID. Рабочая БД/реальные ENV/secrets/defaults не менялись; прежние незакоммиченные правки организации контекста сохранены, staging не изменялся. Коммит по-прежнему только по запросу, статус проверять в Git.

### Результат A6.security AS1–AS4-local — 16 октября 2026

Сначала negative tests воспроизвели выбор одной duplicate session cookie и игнорирование malformed пар старым Request.Cookie. Helper использует строгий стандартный http.ParseCookie для всех Cookie строк, отказывает при malformed header и повторяющемся __Host-session до service/SQL; canonical base64url и quoted-valid value сохранены. Несколько корректных строк/чужие корректные cookies допустимы. Контракт ошибок 401/LogoutAuth cleanup прежний; добавлен strict reject даже для malformed сторонней cookie. Context7 Go 1.27.1 подтвердил silent discard Request.Cookie, local go doc установленного 1.27.2 подтвердил ParseCookie API. Skill повлиял на выбор стандартного parser вместо самописного raw scanner; новая dependency не нужна.

Logout-all, own revoke, change-password и email-change request переведены с Auth на NoRefreshAuth. Они больше не выполняют sliding UPDATE и не добавляют старый refresh Set-Cookie перед success/error/cleanup; reads me/sessions сохраняют прежний refresh, explicit rotation/reauth сохраняют token replacement. API paths/JSON/statuses, SQL transaction implementation/locks/audit и immediate-revoke semantics не менялись. Разница sliding поведения явно описана в contract/browser-security.

Добавлены actual production chi.Walk protected-route tests с explicit method/path exceptions для primary/challenge/operator flows: missing/duplicate cookie/hostile Origin не обращаются к storage, dependency failure возвращает sanitized 503; mutations не вызывают refresh. Составлена route→proof→SQL owner карта без второго runtime registry. Feature permissions/MFA/current SQL guards проверяются прежними feature suites, не выводятся только из 401.

Новый deterministic HTTP/real SQL schedule: A validated/refreshed → B rotate/password-confirm/logout/logout-all committed → A response completed late. Старый Set-Cookie остаётся возможен, но старый verifier не проходит новый read/management mutation; winner token действует. Это availability/session coordination limitation, не доказанный auth bypass и не повод для grace. Password-confirm выполняется SQL fixture с trusted proof input; настоящий password hashing/Redis проверяется другими tests. Реальный browser/ingress/multi-tab/network и stale cleanup после нового login остаются открытыми, новая harness их не симулирует как PASS.

Проверки: formatter; go test ./... PASS (из первого task check); после устранения contextcheck false path в test context sourcing финальный golangci-lint 0 issues; targeted session/router -race PASS; disposable PostgreSQL 18.6 TestPostgresSchema subtests session HTTP response ordering/management/rotation/fresh authentication/concurrent refresh с -race PASS (2.676s). Для lint test использует заранее прочитанный session ID и старый verifier вместо ненаследуемого HTTP callback context, suppression не добавлялся. Swagger annotations/paths не менялись, generation не повторялась; existing route/Swagger contracts входят в all tests. Ни mixed-load capacity, ни memory/GC, ни fault/restore этим прогоном не доказаны.

Прежние незакоммиченные планы JWT/security сохранены и уточнены фактическим результатом. Новых schema/env/secrets/dependencies/workers/pools/cache/проверочных scripts нет; рабочая БД не использовалась. Тестовый контейнер/volume только с synthetic данными удалён после проверок. Коммит не выполнялся. A6.security целиком не закрыт; далее AS5 lifetime policy и AS6 elevation/factors вместе с A6.3, затем остальные pre-ui backend этапы.

### Результат A6.2a-local — 16 октября 2026

Добавлен POST /api/v1/admin/auth/login/email: тот же password hash/rehash/Redis limit, но trusted administrative intent всегда направляется в MFA, без password-only session fallback. Нужны permanent credentials с verified email, active/nondeleted/current version, завершённый provisioning без temporary/change-required и system super_admin либо current core administrative permission. Custom роль с таким permission допустима, продуктовые permissions не дают административный вход. Новых permissions, ролей по умолчанию, dependencies, pools/workers/settings/env нет.

Intent сохраняется одним boolean в существующей MFA challenge source 000001; SQL constraint допускает его только для password. Не принимается из HTTP. ### Аудит нагрузки — 10 октября 2026

Проверены текущие login/register/session validation/refresh/list/revoke, password change/recovery, verification/email change, PostgreSQL/Redis pools/лимиты и фоновые delivery/retention. Runtime-код и схема при аудите не менялись. На отдельном PostgreSQL 18.6 применена текущая 000001 и синтетические данные: 100 000 active users/emails/credentials/sessions/verification challenges/outbox/password audit/email-change intents, отдельно 10 000 недавно удалённых tombstones. Только SELECT EXPLAIN ANALYZE/BUFFERS, после ANALYZE; временный контейнер и его данные удалены. Это диагностика планов, не HTTP load test/P95/P99 или подтверждение capacity.

Приоритетные результаты для 6.4/6.8 перед дальнейшими фичами:

1. Login без распределённых IP/account/admission limits и общего hash concurrency budget: PasswordService.Login делает SQL lookup и Argon2 Compare; register/change-password/email-change Request также не входят в hashSlots recovery. Текущий новый hash использует 64 MiB и p=32; recovery ограничен двумя слотами, но это не общий бюджет процесса. При массовых запросах CPU/RAM могут исчерпаться раньше DB pool. Не ослаблять password hashing для экономии: нужны admission до дорогой работы, общий bounded budget с deadline/overload response и измеренный профиль. Read-only credential lookups/CreateUser не имеют собственного operation deadline, в отличие от password/session transaction helpers; HTTP WriteTimeout не заменяет такой deadline.
2. Delivery cleanup verification/reset выполняется перед каждым Claim, без LIMIT/партии. Verification predicate на стенде проверил все 100 000 challenges через joins с emails/users (Parallel Seq Scan, 100 000 суммарно отфильтрованных строк), хотя удалять нечего. Worker poll — раз в секунду, до десяти claims при jobs; каждый экземпляр API повторяет scans. Нужны отдельный paced bounded cleanup и дешёвый claim, согласованный lock order/SKIP LOCKED/timeout; обязательные актуальные status/version/expiry guards сохраняются, не считать lifecycle cleanup безопасно удаляемым дублем.
3. Retention и outbox eligibility используют volatile clock_timestamp() в range cutoff: наличие ORDER BY/index/LIMIT не ограничивает scanned rows. На стенде password audit и session retention вернули 0 кандидатов, но каждый отфильтровал 100 000 строк; owner reservation отфильтровал 10 000 tombstones. Outbox при 100 000 future available_at тоже отфильтровал все строки ради 0 jobs. Сравнительный SELECT с statement_timestamp() для индексной границы дал Index Cond и 2–3 shared buffers вместо полного прохода. Предыдущая функциональная приёмка worker подтверждает correctness, не его эффективность на больших таблицах. Для coarse candidate cutoff нужен stable statement time/однократное DB time, а фактические single-use/lease/expiry security decisions сохраняют свои гарантии. [PostgreSQL volatility](https://www.postgresql.org/docs/18/xfunc-volatility.html).
4. Session refresh у абсолютного deadline: timeLeft <= threshold запускает UpdateSession даже когда уже существующий expires_at равен absolute_expires_at. Последний день default lifetime может превратить каждый protected request в лишнюю transaction/user lock/UPDATE/WAL/Set-Cookie без продления. Concurrent snapshots также дают повторные writes; UPDATE может уменьшить expires_at относительно уже выполненного конкурентного refresh. Нужны no-op для неподлежающего продлению срока и атомарный монотонный conditional refresh с различением already-refreshed и genuinely inactive; отзыв/version enforcement не убирать.
5. Email-change cleanup фильтрует GREATEST(protect_until,recovery_expires_at), но индекс/order основан на protect_until. На 100 000 живых intents фильтровались все строки, даже после замены времени на stable: нужен совпадающий expression cutoff/order/index, не слепое добавление индексов. Этот путь opt-in, но до его включения исправление обязательно.
6. Нагрузочный профиль ещё не задан. MAX_CONNS=10 ограничивает pool одного API, не суммарные connections всех replicas и не очередь handlers/Argon2. Нет общего HTTP admission budget; global register/reset limits 100/min и IP-based rules за proxy требуют настройки продукта и trusted-proxy policy, не доверия произвольному X-Forwarded-For. Retention 100 rows/min/table/instance имеет потолок 144 000 rows/day/table/instance, не гарантирует отсутствие backlog при большем поступлении; добавить измерения lag/DB waits/ошибок/rows scanned/CPU/RAM и overload/recovery acceptance вместо обещания «любое количество».

Подтверждённые полезные ограничения: login SQL на стенде использовал email UNIQUE и user/credential PK, session validation — token/user PK (1 строка), N+1 в этих путях нет. Protected validation остаётся SQL-authoritative по ADR 002: Redis не заменяет revoke/status/version. Argon2/SMTP выполняются вне SQL transactions; recovery budgets/Redis expiry, session page 50+1/keyset, pool limits/deadlines большинства mutation paths, transaction rollback и retention batch size полезны. Вторичная проверка доступа в sensitive transaction и FK/UNIQUE не являются бесполезным дублированием. Существующая регистрационная проверка occupied email до Argon2 экономит expensive hash; UNIQUE всё равно обязателен для race.

Полная multi-instance нагрузка, production hardware/IO, Redis failover/шторм, bloat/autovacuum и SMTP throughput не проверялись. Readiness endpoint делает PostgreSQL/Redis ping на каждый запрос, malformed session cookie тоже доходит до SQL lookup; учитывать в admission/edge policy без отключения readiness/security. Результат: сейчас нельзя утверждать, что лишней нагрузки нет или что она не возникнет при большом онлайне. Рекомендация — сначала согласовать и исправить пункты 1–5 в рамках 6.4/6.8, затем нагрузочная приёмка с явными целями; не внедрять cache-only access или менять архитектуру без нового решения.
