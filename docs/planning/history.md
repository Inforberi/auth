# История реализации Auth

Архив результатов и проверок. Исторические слова «далее», открытые задачи и имена файлов относятся к моменту записи. Текущие статусы — в [roadmap](roadmap.md) и [implementation](implementation.md); архитектура — [отдельно](../architecture.md).

### Результат 10.3-local — 12 октября 2026

Account status/delete получили last-system-admin guard: destructive операция требует другого active/nondeleted владельца super_admin. Обычная роль или pending/blocked/deleted владелец не считается резервным. Guard выполняется после existing version/deletion checks, но до recovery cancellation/credential/session cleanup/audit; отказ не изменяет состояние. System role edit/assignment/revoke через обычные Access use cases уже запрещены. Status cleanup сгруппирован в локальную функцию без изменения SQL и порядка операций.

Общий Access transaction advisory lock вынесен в adapter helper и используется account status/delete/security email report до row locks. Account и Access явно используют Read Committed, чтобы после ожидания следующий запрос видел committed состояние. Login/Authorize не берут этот lock; новых pools/caches/workers нет. Порядок блокировок и snapshots сверены с PostgreSQL 18 через Context7. Дополнительный запрос проверяет system assignments по имеющимся PK/role index, без прохода всех пользователей. Ожидание ограничено существующими deadlines; cleanup rollback остаётся 5s.

Security report намеренно может блокировать даже последнего украденного администратора, сохраняя системное назначение и protected recovery. Последующий administrative block/delete не отменяет последнее восстановление. Standard reset и protected recovery сохраняют роль, не создают session и не вводят permission/status bypass. Bootstrap, system assignment API, operator emergency recovery, MFA и usable-method/factor policy остаются открыты; trusted account ActorID по-прежнему не заменяет авторизацию. [Контракт и ограничения](../features/roles-permissions.md).

Formatter и task check прошли: tests + lint 0 issues; targeted Access/Account race suite прошёл. Полный disposable PostgreSQL 18.6 up/down/up/race — 9.326s: last owner/stale version/inactive backup, block-block/block-delete/delete-delete concurrency, сохранение account/session/audit при отказе, bounded advisory lock wait, reset-role retention и security report/recovery проверены. Тестовый контейнер a0bafe11c8c7521675025a1777dfd96239c22b3920d50ea3d160de80ffc878be и том с synthetic data удалены. Реальные env/secrets/БД, dependencies/migrations/Swagger/routes не менялись. Полная нагрузка, браузер и production MFA/bootstrap acceptance не измерялись. Коммит не выполнялся.

### Результат A4.1/2-local — 12 октября 2026

Продолжена основа access из dacb371. Реализованы внутренние create/update role, grant/revoke assignment, Authorize/UserAccess, role/assignment versions и atomic access audit с bounded role snapshot. Каталог расширяется проектом, core management permissions защищены от подмены; неизвестные права и wildcard закрыты. Роли не зависят от метода входа, назначений до 32/user, permissions до 128/role и 512/catalog. SQL proof проверяет active/nondeleted owner, session/auth_version/expiry/revoke и свежий password proof 5m для mutations. Оператор делегирует только собственные права; self-grant и обычное изменение/назначение/отзыв системной роли запрещены. Полный last-effective-admin guard для block/delete и системные операции ещё не реализованы, как и MFA/HTTP assembly/bootstrap/import/UI; A4 целиком не закрыт.

Access mutations используют transaction advisory lock без блокировки обычных permission reads; users lock в UUID-порядке, текущие permissions/versions проверяются внутри transaction. No-op не создаёт UPDATE/audit. Authorize/UserAccess — по одному SQL-запросу без кеша; массовый UPDATE owners при role edit не нужен. Audit добавлен в existing bounded retention 180d. Расширена только source 000001; реальные env/secrets/БД не менялись, applied installation требует согласованного upgrade. Контракт — [roles-permissions](../features/roles-permissions.md). ### Результат A3.4a-local — 11 октября 2026

Реализован optional email OTP: POST request/confirm с Origin/no-store, HttpOnly browser binding, восьмизначным crypto/rand кодом, TTL 5m и пятью неверными попытками. Поддержан существующий active verified current permanent-password email; неизвестные адреса получают generic acceptance без регистрации. Код не является verification/MFA/password fresh proof. Disabled профиль не подключает routes/worker. Новые понятные EMAIL_OTP_* budgets/TTL добавлены только в sample ENV.

SQL хранит scoped keyed verifier и encrypted delivery, сериализует consume по user/challenge. Неверные попытки коммитятся перед публичной ошибкой; успешный consume удаляет challenge/outbox и пишет audit одной транзакцией, затем создаётся обычная SQL-сессия с повторной проверкой status/version. Сбой второго шага не восстанавливает код. Общий существующий polling loop вынесен в auth/delivery для трёх очередей без отдельного pool/SDK/unbounded worker. Claim/ack используют lease, SKIP LOCKED, deadlines и bounded retries; retention очищает OTP даже после выключения профиля. Request budget по умолчанию 100/min согласован с текущей скоростью cleanup брошенных кодов; это не измеренный RPS сервиса.

Formatter, итоговый task check (tests + lint 0 issues), targeted race service/HTTP/shared delivery/router и Swagger generation/drift прошли. Полный disposable PostgreSQL 18.6 up/down/up/race — 7.965s после упрощения success consumption: 16 concurrent confirms/один winner, 16 неверных/ровно пять committed attempts, replacement/replay, current-contact/status/version/pending/expiry guards, общая SQL-сессия, lease/stale ack, audit rollback и bounded cleanup. Тестовый контейнер и его том с исключительно synthetic data удалены; рабочая БД/env/secrets не менялись. Расширена только source 000001; applied installation требует согласованного upgrade, не reset. Коммит не выполнялся.

Обновлены feature/API/schema/guide/architecture и implementation. В guide также исправлено прежнее описание transport токена: verification/reset используют query, invitation/email-change — fragment; runtime этим уточнением не менялся. Live SMTP/browser, Redis fault нового flow, multi-instance mixed load и memory/GC приёмка остаются открыты. Passwordless registration/external-only onboarding не реализованы; следующий backend шаг A3.4b — выбранный дополнительный OIDC provider.

### Результат A2-local — 11 октября 2026

Проверены существующие account/session service, SQL authority/locks и HTTP cookie/error contracts. ### Аудит нагрузки — 10 октября 2026

Проверены текущие login/register/session validation/refresh/list/revoke, password change/recovery, verification/email change, PostgreSQL/Redis pools/лимиты и фоновые delivery/retention. Runtime-код и схема при аудите не менялись. На отдельном PostgreSQL 18.6 применена текущая 000001 и синтетические данные: 100 000 active users/emails/credentials/sessions/verification challenges/outbox/password audit/email-change intents, отдельно 10 000 недавно удалённых tombstones. Только SELECT EXPLAIN ANALYZE/BUFFERS, после ANALYZE; временный контейнер и его данные удалены. Это диагностика планов, не HTTP load test/P95/P99 или подтверждение capacity.

Приоритетные результаты для 6.4/6.8 перед дальнейшими фичами:

1. Login без распределённых IP/account/admission limits и общего hash concurrency budget: PasswordService.Login делает SQL lookup и Argon2 Compare; register/change-password/email-change Request также не входят в hashSlots recovery. Текущий новый hash использует 64 MiB и p=32; recovery ограничен двумя слотами, но это не общий бюджет процесса. При массовых запросах CPU/RAM могут исчерпаться раньше DB pool. Не ослаблять password hashing для экономии: нужны admission до дорогой работы, общий bounded budget с deadline/overload response и измеренный профиль. Read-only credential lookups/CreateUser не имеют собственного operation deadline, в отличие от password/session transaction helpers; HTTP WriteTimeout не заменяет такой deadline.
2. Delivery cleanup verification/reset выполняется перед каждым Claim, без LIMIT/партии. Verification predicate на стенде проверил все 100 000 challenges через joins с emails/users (Parallel Seq Scan, 100 000 суммарно отфильтрованных строк), хотя удалять нечего. Worker poll — раз в секунду, до десяти claims при jobs; каждый экземпляр API повторяет scans. Нужны отдельный paced bounded cleanup и дешёвый claim, согласованный lock order/SKIP LOCKED/timeout; обязательные актуальные status/version/expiry guards сохраняются, не считать lifecycle cleanup безопасно удаляемым дублем.
3. Retention и outbox eligibility используют volatile clock_timestamp() в range cutoff: наличие ORDER BY/index/LIMIT не ограничивает scanned rows. На стенде password audit и session retention вернули 0 кандидатов, но каждый отфильтровал 100 000 строк; owner reservation отфильтровал 10 000 tombstones. Outbox при 100 000 future available_at тоже отфильтровал все строки ради 0 jobs. Сравнительный SELECT с statement_timestamp() для индексной границы дал Index Cond и 2–3 shared buffers вместо полного прохода. Предыдущая функциональная приёмка worker подтверждает correctness, не его эффективность на больших таблицах. Для coarse candidate cutoff нужен stable statement time/однократное DB time, а фактические single-use/lease/expiry security decisions сохраняют свои гарантии. [PostgreSQL volatility](https://www.postgresql.org/docs/18/xfunc-volatility.html).
4. Session refresh у абсолютного deadline: timeLeft <= threshold запускает UpdateSession даже когда уже существующий expires_at равен absolute_expires_at. Последний день default lifetime может превратить каждый protected request в лишнюю transaction/user lock/UPDATE/WAL/Set-Cookie без продления. Concurrent snapshots также дают повторные writes; UPDATE может уменьшить expires_at относительно уже выполненного конкурентного refresh. Нужны no-op для неподлежающего продлению срока и атомарный монотонный conditional refresh с различением already-refreshed и genuinely inactive; отзыв/version enforcement не убирать.
5. Email-change cleanup фильтрует GREATEST(protect_until,recovery_expires_at), но индекс/order основан на protect_until. На 100 000 живых intents фильтровались все строки, даже после замены времени на stable: нужен совпадающий expression cutoff/order/index, не слепое добавление индексов. Этот путь opt-in, но до его включения исправление обязательно.
6. Нагрузочный профиль ещё не задан. MAX_CONNS=10 ограничивает pool одного API, не суммарные connections всех replicas и не очередь handlers/Argon2. Нет общего HTTP admission budget; global register/reset limits 100/min и IP-based rules за proxy требуют настройки продукта и trusted-proxy policy, не доверия произвольному X-Forwarded-For. Retention 100 rows/min/table/instance имеет потолок 144 000 rows/day/table/instance, не гарантирует отсутствие backlog при большем поступлении; добавить измерения lag/DB waits/ошибок/rows scanned/CPU/RAM и overload/recovery acceptance вместо обещания «любое количество».

Подтверждённые полезные ограничения: login SQL на стенде использовал email UNIQUE и user/credential PK, session validation — token/user PK (1 строка), N+1 в этих путях нет. Protected validation остаётся SQL-authoritative по ADR 002: Redis не заменяет revoke/status/version. Argon2/SMTP выполняются вне SQL transactions; recovery budgets/Redis expiry, session page 50+1/keyset, pool limits/deadlines большинства mutation paths, transaction rollback и retention batch size полезны. Вторичная проверка доступа в sensitive transaction и FK/UNIQUE не являются бесполезным дублированием. Существующая регистрационная проверка occupied email до Argon2 экономит expensive hash; UNIQUE всё равно обязателен для race.

Полная multi-instance нагрузка, production hardware/IO, Redis failover/шторм, bloat/autovacuum и SMTP throughput не проверялись. Readiness endpoint делает PostgreSQL/Redis ping на каждый запрос, malformed session cookie тоже доходит до SQL lookup; учитывать в admission/edge policy без отключения readiness/security. Результат: сейчас нельзя утверждать, что лишней нагрузки нет или что она не возникнет при большом онлайне. Рекомендация — сначала согласовать и исправить пункты 1–5 в рамках 6.4/6.8, затем нагрузочная приёмка с явными целями; не внедрять cache-only access или менять архитектуру без нового решения.
