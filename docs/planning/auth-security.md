# План проверки безопасности Auth, прежде всего сессий

Статус: локально реализованы AS1–AS5 и AS6a/b (назначения и расширение прав роли), 17 октября 2026; результаты ниже. AS6/MFA-role policy и внешняя приёмка остаются открытыми. Это не pentest. Сессии — основной механизм и приоритет; [JWT S1–S10](jwt-access.md#проверка-проекта-по-безопасности--обязательные-условия-реализации) — будущее расширение, не условие исправления backend.

Цель — сохранять корректный отзыв и разграничение прав при краже cookie, конкурентных запросах, смене ролей/MFA, отказе зависимостей и высокой нагрузке. Не обещаем «невозможно взломать». Не переписываем работающую защиту и не вводим fingerprint/AI risk engine/cache/session framework без конкретного сценария.

## Что уже подтверждено чтением кода

Это наблюдения по указанным участкам, не доказательство всех возможных путей приложения:

- [TokenManager](../../internal/infra/tokengenerate/token.go): CSPRNG, по умолчанию 32 случайных байта; ledger получает SHA-256 verifier, не raw token. Для такого случайного credential быстрый hash уместен; не добавлять Argon2 и SQL cost на каждый запрос ради хеширования session ID.
- [Cookie helper](../../internal/auth/session/transport/http/cookies.go): `__Host-session`, Secure/HttpOnly/Path=/, без Domain, SameSite=Lax; canonical base64url, 43 символа/32 байта. При первоначальном анализе `r.Cookie` выбирал один duplicate и пропускал malformed пары. В AS2-local заменён строгим `http.ParseCookie` с reject duplicate session names; это hardening, не доказанный прежний account takeover.
- [SQL session repository](../../internal/auth/session/repository/postgres/sessions.go): lookup проверяет active/nondeleted user, current auth_version, revoked_at и оба срока; refresh — conditional UPDATE с clamp absolute и без resurrection. [Rotation](../../internal/auth/session/repository/postgres/rotate.go) потребляет старый verifier, сохраняет сроки и session ID. [Password reauth](../../internal/auth/session/repository/postgres/reauthenticate.go) меняет verifier и пишет proof только при current hash/version/status.
- [Middleware](../../internal/auth/session/transport/http/auth.go) различает Auth, NoRefreshAuth и LogoutAuth. После успешного refresh Auth может выдать Set-Cookie. Поэтому гонки позднего ответа с rotate/reauth/logout требуют browser-теста, а не только SQL assertions.
- [Config](../../internal/auth/session/service/config.go): общий SESSION_TTL=168h, absolute=336h, refresh threshold=24h; fresh password default=5m. Это текущие defaults, не оценка подходящего времени для админки и не доказательство точного idle timeout от последнего действия.
- [Management](../../internal/auth/session/repository/postgres/management.go): own session ownership, caller guard, logout-all с auth_version bump и audit. [AuthorizeMutation](../../internal/access/repository/postgres/authorization.go) вызывается внутри owner transaction; одного HTTP principal недостаточно для sensitive write.
- [BrowserProtection](../../internal/transport/http/middleware/browser.go)/Origin: exact allowlist, CSRF Origin для cookie mutations, CORS default-off. [Security headers](../../internal/transport/http/middleware/security.go) и [access logger](../../internal/transport/http/middleware/request.go) не заменяют ingress/UI защиту; logger использует route pattern без cookie/body/query. [Server](../../internal/server/http/server.go) ограничивает headers/timeouts; TLS может завершаться на доверенном ingress. HSTS/HTTP→HTTPS и закрытый внутренний порт — обязанности deployment, описанные в [browser security](../operations/browser-security.md).

Оставшиеся пункты — обязательные доказательства или проектные решения. Не объявлять все их найденными уязвимостями: для каждого сохранить статус «есть в коде», «нужен тест», «нужна доработка» либо «внешний NOT RUN».

## Результат первого блока AS1–AS4-local

- [x] AS1-local: [session_security_contract_test.go](../../internal/transport/http/router/session_security_contract_test.go) обходит реально зарегистрированные production API routes. Явный allowlist только **method + path** для primary/challenge/operator flow; остальные routes требуют session. Проверены missing/duplicate cookie, hostile Origin до lookup и SQL failure → 503. Ни одна проверяемая mutation не вызывает refresh. Это test guardrail, не новый runtime routing framework; permission/MFA/SQL semantics покрываются существующими feature contracts и transaction tests, а не выводятся из одного статуса 401.
- [x] AS2-local: сначала воспроизведено принятие ambiguous cookies, затем strict standard parser. Duplicate names в одной/разных Cookie строках, malformed пары (включая чужую cookie) и invalid session encoding дают 401 до session service. Несколько корректных строк с одним session name и quoted canonical value поддерживаются. Auth/NoRefreshAuth не меняют cookie на таком отказе; LogoutAuth сохраняет явную cleanup policy. Security attributes и valid-cookie контракт прежние. Новых dependencies/SQL/Redis calls нет.
- [x] AS3-local: целевая disposable PostgreSQL/race регрессия management/rotation/fresh-auth/concurrent refresh плюс новый [session_http_ordering_integration_test.go](../../internal/auth/methods/password/repository/postgres/session_http_ordering_integration_test.go). После committed replacement/logout старый verifier не авторизует read или новую management mutation; SQL implementation/locks/audit/version guarantees не менялись. Проверен конкретный набор schedules, не все возможные interleavings приложения.
- [x] AS4-local: `NoRefreshAuth` теперь используется также перед logout-all/own revoke/change-password/email-change request. Эти операции не выполняют лишний sliding refresh UPDATE и не выдают старую cookie перед результатом use case; явные rotate/reauth/new-login/cleanup ответы по своему контракту остаются. GET me/sessions по-прежнему могут продлевать session. В HTTP/SQL ordering fixture A валидирует/refresh, B завершает rotate/password-confirm/logout/logout-all, затем A заканчивает ответ: late Set-Cookie со старым token возможен, но **не возвращает серверный доступ**. Проверка deterministic HTTP handlers + настоящий SQL, не реальный browser/network scheduler; password-confirm использует SQL proof fixture, не выполняет реальный Argon2/Redis flow.
- [ ] AS1–AS4-release: реальный HTTPS ingress/browser/multi-tab, delayed logout cleanup после нового login, параллельные login, lost responses и network faults остаются открытыми pre-ui/A8 gates. Нельзя доказать их прохождение httptest. Не вводить old-token grace; UI lifecycle coordination не даёт гарантии переупорядочить уже отправленные ответы.

### Минимальная карта route → proof → owner guarantee

Пути относительно `/api/v1`; перечисление sessionless method/path закреплено тестом выше. Точные permissions/error contracts — в документации фич, это карта границ, не второй каталог permissions.

| Routes / сценарий | HTTP proof и authoritative use case |
| --- | --- |
| POST auth/register/email, auth/login/email, admin/auth/login/email | Primary password; registration/login policy, status/version/factor checks до final session/challenge. Admin intent отдельный, full MFA обязателен |
| POST auth/email-otp/request/confirm; POST auth/google/start, auth/telegram/start; GET их callback | OTP или provider/browser-bound state; shared account identity/current version и final SQL policy/session. Callback link дополнительно привязан к текущей session |
| POST auth/forgot-password, reset-password, invitations/activate, temporary-password/login/complete, email/resend, email/verify | Public или ограниченный purpose challenge, не наличие обычной session; SQL owner/TTL/attempt/consume и lifecycle guards по фиче |
| POST auth/mfa/login/complete, auth/mfa/recovery/start/complete | Browser-bound primary/MFA/operator recovery proofs; completed MFA и current authority перед full session, не public MFA bypass |
| POST setup/start, setup/complete | Operator-controlled first-install flow/initialized marker, email и TOTP proof; не обычная session и не повторная регистрация admin |
| GET auth/me, auth/sessions | Auth + SQL current ledger; list — собственный owner/cursor guard; sliding refresh разрешён |
| POST auth/logout, auth/logout-all; DELETE auth/sessions/{id}; POST auth/session/rotate | LogoutAuth или NoRefreshAuth; live caller/owner/version/deadline в SQL transaction. Logout cleanup явный; no fresh password requirement для собственного logout |
| POST auth/reauthenticate/password, auth/reauthenticate/email/request/confirm | NoRefreshAuth; current primary proof привязан к caller/session/version, смена verifier/proof атомарна. Это не обычное продление |
| POST auth/change-password, auth/email/change | NoRefreshAuth; change-password также RequireVerified; собственные credential/fresh-proof/version guards и audit в SQL сценарии |
| POST auth/email/change/confirm, report, recover | Purpose-bound token, не обязательная потенциально скомпрометированная session; atomic owner/security transition |
| POST auth/google/link, auth/telegram/link; DELETE эти link | NoRefreshAuth + current linking/unlinking proof, SQL identity owner/version/session/deadline и last-method guards |
| POST auth/mfa/totp/enrollment[/confirm], step-up, replacement[/confirm], recovery-codes/regenerate; DELETE auth/mfa/totp | NoRefreshAuth; current owner, scenario-specific primary/factor/fresh proofs, enrolled/protected-admin policy, transactional factor/version/revoke/audit |
| POST admin/users/{id}/email-binding, auth/email/binding/confirm | NoRefreshAuth; admin permission/fresh password+MFA approval либо owner approval-bound proof, текущая SQL authority при completion |
| GET auth/access; GET admin/permissions, roles[/{id}], users[/{id}], users/{id}/access, admin/auth/settings | NoRefreshAuth; own effective access либо текущее permission чтения по фиче; требование live caller не заменяет permission guard |
| POST admin/roles[/{id}], admin/users/{id}/roles/{roleId}, admin/users/{id}/administrator; DELETE assignments/administrator | NoRefreshAuth; Access current permission/delegation, fresh password+MFA, optimistic versions/audit; системный admin и last-admin отдельно защищены |
| POST admin/users, admin/users/{id}/invitation, admin/users/temporary-password, admin/users/{id}/temporary-password, admin/users/{id}/status, admin/auth/settings; DELETE admin/users/{id} | NoRefreshAuth; feature permission + current/fresh password/MFA + SQL versions/status/delegation/audit; issuance не выдаёт пользовательскую session |

Production не публикует dev send-mail; Swagger/health — отдельные operational routes, не бизнес-session bypass. Изменение table/schema/ENV/TTL/permission policy этим блоком не выполнялось. Далее AS5 lifetime и AS6 elevation с A6.3; новые guarantees не считаются готовыми по этой карте.

## Приоритет 1: сессии, до JWT и до UI

### Решение AS6a: новое назначение роли

Фактический grant обычной или system роли активному пользователю повышает auth_version цели существующим UPDATE users в той же транзакции, что assignment/access_version/audit. Старый verifier не получает новые права и не проходит refresh; нужен новый login с действующим MFA, не простая rotation. Pending не имеет live session и сохраняет auth_version для приглашения/активации. No-op grant и revoke auth_version не повышают: первый ничего не меняет, второй сразу уменьшает live permissions. Политика едина для всех новых назначений active-пользователю, без сложного вычисления sensitive-permission diff. Достаточно существующей auth_version boundary: не обновлять все session rows и не добавлять SQL/Redis calls на обычный read. [Контракт](../features/roles-permissions.md).

AS6b-local ниже закрывает permission edit через immutable role revisions без массового UPDATE владельцев; MFA-role settings остаются A6.3. На момент AS6a AS5 оставался открытым: текущий sliding refresh — не точный admin idle; stored absolute deadline не продлевается изменением defaults, а proof timestamps — обычным refresh. Это дополнено service regression; отдельные admin idle/absolute значения и batching пока не введены и должны быть согласованы до изменения defaults. AS5-local реализован 17 октября по отдельному контракту ниже; внешняя приёмка не закрыта.

- [x] AS6a-local: custom/system grant, две старые sessions и stale refresh, no-op, revoke, 16 concurrent grants/один version bump, audit rollback и pending activation version проверены SQL/race. HTTP regression требует 401 для старой cookie и доступ с новой fixture session; fixture не подменяет настоящий primary/MFA login acceptance. Tests — [access roles](../../internal/auth/methods/password/repository/postgres/access_roles_integration_test.go), [Access HTTP](../../internal/auth/methods/password/repository/postgres/access_http_integration_test.go), [system assignments](../../internal/auth/methods/password/repository/postgres/administrator_assignments_integration_test.go). [Пределы lifetime regression](../../internal/auth/session/service/boundaries_test.go) проверены отдельно. Внешние browser/load/fault gates и AS5/A6.3 открыты; AS6b-local выполнен ниже.

### Решение AS6b: расширение permissions роли

- [x] AS6b-local: отдельная role session_revision растёт только при добавлении permissions, вместе с прежним role UPDATE/audit. SQL-issued immutable role_revisions snapshot в sessions и общая role_bound_sessions view закрывают обычный lookup и транзакционные bearer guards, rotation/reauth/MFA step-up без fan-out UPDATE users/sessions. Metadata/no-op/removal не повышают ревизию; старые bindings сохраняются после revoke, чтобы cookie не оживала.
- [x] [SQL/non-owner/HTTP regression](../../internal/auth/methods/password/repository/postgres/role_revision_integration_test.go): stale cookie/principal/refresh/rotation/password/MFA proof rejection, новая synthetic session, unaffected owner, no-op/metadata/removal, immutable bindings/audit rollback и INSERT → edit commit → late INSERT commit. Это SQL/httptest, не настоящий browser/MFA login E2E. Formatter/task check (0 lint issues) и полный PostgreSQL 18.6 suite с race/up-down-up PASS; детали в history.
- [ ] AS6/pre-ui-release: MFA-policy tightening/enrollment выполнены локально в A6.3a; usable-admin transitions и остальные settings остаются A6.3; live browser/providers/SMTP/fault/load/GC/restore не закрыты. Applied schema/fleet upgrade с invalidation прежних sessions/challenges — отдельно, не выполнен. AS5-local добавлен 17 октября: отдельный admin lifetime реализован, browser/fleet gate открыт.

Снимок хранит только UUID/revision, не permissions; не cache и не новый trust source. View добавляет до 32 role PK comparisons к прежнему SQL statement, trigger — одно set-based чтение при issuance; новую capacity не измеряли. [Полный контракт, консервативные revoke semantics и upgrade](../features/roles-permissions.md#изменение-прав-роли-и-сессии--as6b-local).

### Контрольный список AS1–AS6

- [ ] **AS1. Инвентаризация и route coverage.** Для каждой ручки и use case составить минимальную матрицу public/session/permission/fresh password/MFA, метод/Origin, владелец SQL guard. Проверить default-deny и прямой API, не только UI; ошибки регистрации маршрута не должны случайно публиковать admin endpoint. Переиспользовать существующие route/Swagger/negative contract tests, не строить новый генератор. Sensitive operation повторно проверяет current authority в своей транзакции: это другая гарантия, не лишний дубль middleware. Результат — карта покрытых guards и конкретные пробелы.
- [ ] **AS2. Cookie ambiguity, fixation и transport.** Reject duplicate session-cookie names, неоднозначные Cookie headers и некорректные значения **до SQL**; одинаковое поведение ingress/app. Session credential только из согласованной cookie, не из query/body/UUID; public session ID и verifier не могут заменить raw token. После login новый серверный token, pre-login/challenge cookie не переиспользуется как session. Проверить cookie set/clear attributes, отсутствие Domain/небезопасных dev bypass в production, HTTPS/HSTS на реальном ingress и запрет прямого public HTTP API. Проверки основаны на [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html); browser/edge evidence обязательны, не «Secure=true значит весь deployment защищён».
- [ ] **AS3. Revocation и конкурентные записи.** Переиспользовать regression на create/validate/refresh/rotate/reauth/logout/revoke/reset/change-password/block/delete/MFA reset и добавить недостающие пары, особенно после lock wait. После committed revoke новая проверка не принимает старый credential; active→blocked→active и восстановление Redis не оживляют session. Read Committed/lock order/SQL constraints/audit rollback сохраняются. HTTP validation допускает завершение уже начатого чтения: sensitive write не полагается на старый principal; внешний эффект не получает невозможной гарантии распределённой атомарности. Реплика с replication lag не является strict auth authority — использовать writer либо отдельно доказанную согласованность, без fallback на старый snapshot.
- [ ] **AS4. Поздние Set-Cookie и multi-tab.** Browser schedule: запрос A прошёл refresh, затем B сделал rotate/reauth/logout, ответ A приходит последним. Проверить также stale 401/logout очистку после нового login и два параллельных login. Старый token никогда не возвращает серверный доступ; отдельно зафиксировать возможную потерю новой browser cookie/повторный вход — это availability/UX, не автоматически auth bypass. По результатам выбрать простейшую политику: ограничить, какие routes продлевают cookie, и координировать lifecycle операции в UI; тестировать задержки/потерю ответа/несколько вкладок. Не лечить гонку приёмом старого verifier или бесконечным grace и не обещать, что JS может надёжно упорядочить уже отправленные Set-Cookie ответы.
- [x] **AS5-local.** Реализован независимый admin idle/absolute профиль 30m/12h с bounded activity interval 1m. Profile выбирает SQL issuance по core admin permissions/system super-admin независимо от primary login URL, cookie получает реальный expiry. GET/NoRefreshAuth/generic refresh/rotation/reauth не обновляют admin idle/proofs/absolute. Policy хранится в session, defaults не переписывают existing deadlines. Проверки: unit/config, non-owner SQL/HTTP, concurrent activity, expired authority/rotate/reauth и actual MFA completion для обоих intents. [Контракт и границы](../operations/browser-security.md#сроки-административных-сессий--as5).
- [ ] **AS5-external.** A7 подключает interaction-only activity без polling heartbeat; реальный browser/multi-tab/sleep-resume/clock discipline/ingress и multi-instance нагрузка — pre-ui/A8. Upgrade прежней схемы и invalidation старых sessions/challenges выполняются контролируемо, не этим локальным блоком.
- [ ] **AS6. Повышение привилегий и смена факторов.** Проверить все role grants/edits/system administrator assignments вместе с existing sessions: украденная старая cookie не должна незаметно получить новый высокий assurance. Выбрать и записать политику: при повышении чувствительных полномочий invalidation/повторный вход со свежим verifier либо явно доказанный серверный step-up, который старый token не может наследовать. Сохранить актуальную проверку permissions на каждом административном действии и current password/MFA guards; role name или просто возраст session не proof. Для понижения/revoke — запрет по текущим правам после commit без stale cached grants. Проверить factor enrollment/remove/recovery, смену email/пароля, external-only метод и last-admin; automatic cookie rotation не обновляет MFAVerifiedAt/PasswordVerifiedAt. Совместить с A6.3, не создавать дублирующую MFA policy.

## Приоритет 2: весь Auth и browser/deployment boundary

- [ ] **AS7. CSRF/CORS и callbacks.** Проверить public login/registration, logout, rotate, reauth, linking, session/admin/settings mutations на missing/null/foreign/duplicate Origin, hostile sibling subdomain и exact ports. OPTIONS без аутентификации лишь проверяет CORS, не выполняет use case; credentials не сочетаются с wildcard/reflected origin. SameSite=Lax не поддерживает произвольные cross-site cookies — не переключать на None ради ошибки frontend. OIDC callback исключается только по проверяемому state/nonce/PKCE/browser binding, не общим Origin bypass. GET/HEAD/OPTIONS не меняют account/security state; email link не выполняет confirm/reset автоматически. CSP/XSS и экранирование UI-полей User-Agent/ролей — отдельная проверка перед A7, Swagger CSP не является policy админки.
- [ ] **AS8. MFA, recovery и одноразовые credentials.** Сохранить purpose/owner/browser/session/version binding, TTL/attempt bounds, atomic consume и один победитель для OTP/verify/reset/email-change/invitation/temporary/MFA recovery. Полная session только после всех требуемых шагов; email OTP/ownership proof не превращается в password/MFA. Fresh proof не продлевается refresh/rotation/ожиданием challenge. Ошибки/retry не откатывают committed attempt/reuse/security decisions. Rate limits и common responses защищают перебор/enumeration без подмены dependency failure «успешным» ответом; не раздувать слои там, где существующая транзакция уже даёт гарантию. Lost-factor operator drill 13.1d.4 и first-admin flow остаются обязательными и отдельно авторизованными.
- [ ] **AS9. Session theft, management и утечки.** Cookie — bearer credential: HttpOnly/MFA не делают украденную полную session бесполезной. Проверить own-only list/detail/revoke/cursor, отсутствие raw token/verifier в DTO/audit/logs/URL/APM/proxy/backup support bundles, одинаковые чужой/unknown ответы без IDOR. UI показывает активные session и даёт понятный logout/logout-all; not revoked row не означает пригодность без status/version/deadlines. IP/User-Agent — недоверенные диагностические признаки, не MFA и не жёсткая привязка по умолчанию: NAT/mobile смены не должны ломать вход. Не строить обязательный device fingerprint/geo-risk engine; при конкретном риске — действующий reauth/MFA/revoke. Session storage bounds и возможность злоупотребить повторным login проверить измерениями; user-wide lockout/caps не добавлять без сценария.
- [ ] **AS10. TLS/proxy/secrets/операторские границы.** Проверить trusted CIDRs/XFF цепочку и отсутствие limiter bypass через поддельные headers; proxy очищает внешние identity/forwarded headers, app недоступен в обход edge. HTTPS от пользователя до edge и защищённая доверенная внутренняя сеть, HSTS и redaction на ingress; mixed/HTTP origins запрещены. SQL runtime least privilege/non-owner, Redis/DB/SMTP не публичны, production debug/pprof/Swagger по отдельной policy, pprof не размещать на public API. Signing/SMTP/root/DB secrets не выдаются UI; audit administrative config и защита backup/rotation/operator recovery. Не считать root encryption key разрешением на смену admin или MFA bypass.

## Приоритет 3: безопасная производительность, отказы и восстановление

- [ ] **AS11. Нагрузка и resource exhaustion с реальными sessions.** Помимо корректного трафика включить canonical random 43-char cookies (проходят syntax и вызывают SQL miss), malformed/duplicate cookies, session list/revoke/login bursts и expired/revoked credentials. Admission/header bounds до SQL, одна основная indexed lookup на обычный защищённый read, refresh только при необходимости; не добавлять N+1/UPDATE на каждый запрос. Проверить cost SQL misses и Redis limiter, суммарные pools всех API/workers, очереди, timeouts/cancellation, sampling hostile logs, bounded retention. Ограничивать атаку минимально необходимым edge/app budget, не новым SQL запросом для каждого random verifier. Redis не становится positive-cache authority; SQL error — 503, не принятие cached session. Новый cache/задержка отзыва — только отдельный ADR по 6.9.
- [ ] **AS12. Fault/restore/memory acceptance.** На разрешённом изолированном стенде: несколько instances, SQL timeout/restart/lag/lock saturation, Redis failover/старые данные, SMTP faults, отмены, rolling restart и graceful shutdown. Revoke/reset/MFA/audit rollback сохраняют guarantees при каждом interleaving; lost HTTP response не считать откатом commit и не retry sensitive mutation бесконечно. После backup restore до трафика инвалидировать восстановленные sessions/challenges и учесть будущие JWT key/family правила; auth_version из backup не доказывает свежесть. Замерить mixed valid/attack throughput/P95/P99/error rate/SQL calls, heap/RSS/allocations/GC/goroutines/pools на нагрузка→отдых циклах; диагностические данные без secrets. Не заявлять RPS/отсутствие утечек по unit tests. Переиспользовать 6.8b/6.8c/A8, не создавать параллельные harness и sh-скрипты.

## Порядок выполнения и критерии закрытия

1. **Ближайший security-блок:** AS1/AS2, детерминированные AS3/AS4 сценарии, решения AS5/AS6. Сначала воспроизвести пробелы, затем только необходимые изменения/целевые тесты. Для duplicate cookie — конкретный parsing hardening; для Set-Cookie race — сначала browser reproduction и классификация эффекта. Не писать заново SQL/session механизм, уже обеспечивающий нужную гарантию.
2. AS6/AS8 согласовать с A6.3 MFA/enrollment/settings; AS7/AS9/AS10 — с существующей browser/operations приёмкой. Проверить все методы входа и административные use cases по AS1, а не только password route. Подтверждённые дефекты исправлять до UI/JWT, не ждать final pentest.
3. Backend correctness/security — обязательный pre-ui-backend gate; browser UI session coordination/XSS/role escalation — A7 и повторная сквозная приёмка; AS11/AS12 — общая A8/6.8 load/GC/restore. Отсутствующие реальные credentials/стенд/operator workflow — NOT RUN, не PASS; перенос внешней проверки явно согласовывается.

Для каждого AS-пункта записать code/test reference, конфигурацию/commit, PASS/FAIL/NOT RUN и конкретные ограничения. Готовые negative/concurrency tests переиспользовать и запускать по затронутому риску; отдельные полные suite/scan — при выпускной приёмке или реальном изменении общего контракта. Важнее гарантии и воспроизводимый evidence, чем число проверок.

Блокирующие дефекты: обход session/permission/MFA, acceptance отозванного/просроченного credential после своей strict authority boundary, resurrection после restore, утечка credentials, fail-open/CSRF sensitive mutation. Browser cookie race, ведущий только к повторному входу, фиксировать отдельно как availability defect; не маскировать его опасным grace. Независимый targeted security review и внешний pentest перед публичным production rollout дополняют тесты, а не дают обещание абсолютной защищённости.

Источники для дальнейшей приёмки: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Конкретные AS-решения и наблюдения выше — проектный анализ репозитория, не утверждение, что OWASP требует каждую выбранную реализацию.
