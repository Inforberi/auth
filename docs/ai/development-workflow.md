# Разработка с AI без лишней работы

Переносимый подход для существующих проектов. Цель — быстрее получать понятные, проверенные изменения; сокращение контекста и расходов не должно ослаблять гарантии. Это правила работы, а не установка плагинов или запуск фоновых задач.

## Один законченный блок

Перед реализацией определить результат, границы, владельцев данных, необходимые гарантии и достаточные проверки. Найти существующий механизм до добавления нового. Не дробить связную операцию на множество задач ради параллельности.

Код — источник фактического поведения; контракт и план — согласованных требований. Хранить одну актуальную заметку о текущей работе, карту первоисточников и подробные результаты проверок отдельно. Не копировать одинаковые статусы в несколько систем памяти.

Для кода использовать определения, ссылки и реализации через Serena/LSP, затем читать нужные тела. Точный текст, SQL и конфигурацию искать через rg. Внешние API сверять по установленной версии и документации. Не перечитывать неизменившиеся файлы и не загружать весь репозиторий по умолчанию.

## Поиск и контекст

Для задачи в нескольких незнакомых модулях основной агент задаёт локальному субагенту Luna medium ограниченный вопрос: какой сценарий найти, где искать и какие связи или гарантии выяснить. Простой поиск известного символа выполняет сам: делегирование должно заменять широкое исследование, а не добавлять второй обход кода.

Локальный исследователь и отдельный чат проверок — разные исполнители. Отдельному чату Luna передавать только verification; разведку выполнять локальным субагентом. Одного локального исследователя переиспользовать для связанных задач и уточнений до завершения блока/проверок; не создавать нового после каждого вопроса и не закрывать сразу после первого отчёта. При смене темы или устаревшем контексте — передать актуальные первоисточники, при необходимости заменить агента. Сохранение агента не гарантирует меньший суммарный расход токенов. Его актуальный ID/роль хранить только в current-task, не в параллельном индексе. Имя в интерфейсе не определяет модель; модель брать из фактического spawn.

Результат поиска — короткая карта первоисточников:

- пути и имена символов, при необходимости актуальные номера строк;
- связи между вызывающим кодом, реализациями и потребителями контракта;
- ограничения и подходящие тесты со ссылками на источник;
- что не найдено или осталось непроверенным.

Не возвращать целые файлы, большие фрагменты и пересказ всего модуля. Luna не меняет код и не принимает архитектурные решения в рамках поискового задания. Основной агент читает необходимые определения и зависимости, проверяет критичные SQL constraints, права, маршруты и транзакции в первоисточнике. Поисковый отчёт не доказывает полноту влияния изменения и не является результатом тестирования. Не ограничивать число читаемых файлов искусственной квотой.

Поиск и проверки передавать отдельными заданиями с явными границами. Не прерывать прогон ради поиска и не считать занятый чат свободным исполнителем: использовать доступного разрешённого помощника либо выполнить точечный поиск самостоятельно. Новый чат создавать только по явному запросу пользователя. Это не меняет правило делегирования всех исполняемых проверок Luna. Пока идёт исследование, продолжать только независимую работу; зависимые решения принимать после результата.

Уже полученный неизменившийся код не перечитывать в текущем контексте. После сокращения контекста восстанавливать только необходимые сведения из текущей заметки и первоисточников. Выдачу инструментов ограничивать вопросом: нужные символы, совпадения и диагностика вместо полных деревьев, перечней инструментов и успешных логов. Усечённый ответ не считать прочитанным; следующий запрос сузить.

Текущая заметка хранит результат и следующий шаг, документ фичи — контракт, evidence — проверки. Не добавлять параллельные статусы или индекс ради помощника. В общих правилах держать обязательные требования, подробные процедуры читать по необходимости; не создавать skill, если существующей инструкции достаточно.

При появлении frontend держать локальные правила и навигацию рядом с соответствующей частью проекта. Backend и frontend связывать через общий API-контракт; детали другого стека загружать по затронутым зависимостям. Это правило организации будущей работы, не разрешение начинать UI.

## Разделение работы

| Исполнитель | Задача |
| --- | --- |
| Основной агент | Контракты, проектирование, реализация, сложные ошибки, итоговая оценка безопасности и результата |
| Обычный процесс или CI | Выполнение заданных formatter/tests/lint и профильных проверок, сохранение логов и exit status |
| Luna или разрешённый помощник по необходимости | Ограниченный поиск с картой источников, независимая проверка или разбор сбоя; отдельное задание для каждого результата |

Для простого запуска команд отдельная AI-модель не нужна. Более простую модель можно использовать для ограниченного задания, если инструмент действительно позволяет выбрать её. Не обещать доступность модели или экономию без проверки. Дополнительный агент может увеличить суммарные токены; более низкая цена токена не означает меньшее их количество.

Не создавать отдельный чат, автоматизацию, worktree или менять модель без соответствующего разрешения пользователя. Пользоваться уже доступными средствами; отдельный навык нужен только для повторяющегося процесса, который обычные инструкции не покрывают.

## Проверки параллельно с реализацией

1. Назначить одного исполнителя проверок. В этом проекте по выбору пользователя все проверки, включая быстрые целевые, выполняет отдельный чат Luna; основной агент реализует и исправляет код, подготавливает formatter/generated artifacts и неизменяемый снимок. Проверку результата и работу со стендом выполняет Luna. Не дублировать её команды в основном чате.
2. Долгую проверку можно запустить в фоне. Для параллельных правок проверять неизменяемый снимок в отдельном checkout/worktree, включая все предназначенные для проверки изменения. Не коммитить ради снимка без разрешения.
3. В отчёте указать commit и, если есть незакоммиченные изменения, идентификатор патча/снимка, команды, окружение, PASS/FAIL/NOT RUN и путь к логам. Результат относится только к этому коду; skipped не означает PASS.
4. Пока идёт проверка, продолжать только независимую работу. Авторизация, отзыв, изоляция и миграции должны пройти свои проверки до признания соответствующего блока готовым. Зависимую работу не строить на непроверенной гарантии.
5. Общие БД, порты и стенды тоже могут конфликтовать при разных worktree. Изолировать данные и ресурсы, ограничивать параллельность с учётом CPU, памяти и общего бюджета подключений.
6. После правки повторять затронутые проверки. Изменение общих гарантий требует расширения набора; несвязанные успешные проверки не повторять без причины. Проверка старого снимка не подтверждает новый diff.

В основной контекст возвращать только ошибки/блокировки с командой, местом сбоя и диагностикой. Успех подтверждать одной строкой PASS с идентификатором снимка; подробные результаты, команды и exit statuses хранить в evidence/логах. Молчание и завершение процесса сами по себе не означают PASS. Успешные логи не передавать целиком в контекст. Сохранять полную диагностику ошибок и реальный exit status; компактный вывод не должен скрывать сбой. Фоновый запуск не гарантирует работу после остановки приложения или компьютера — это зависит от исполнителя.

### Выбор проверок и переиспользование стенда

По уточнению пользователя от3 ноября проверяем только затронутые сценарии и непосредственно зависимые гарантии. Перед реализацией задаём достаточный список пакетов/roots; расширяем его при обнаруженном влиянии или ошибке. Изменение документации не запускает Go/Docker. Локальная правка не требует автоматического полного task check; общий перенос, общие security contracts или зависимости могут потребовать широкого набора. Успешные несвязанные проверки не повторяем после каждого исправления. Матрица — в implementation.

Собственный изолированный стенд Luna можно сохранять между задачами. Не создавать его заранее без нужной проверки. При первом запуске записать Compose project/labels, владельца, ports, host data/config paths и версии сервисов в evidence; секреты не выводить. Предпочитать сохранённый собственный стенд, готовые images и совместимый Go cache; чужой auth-sandbox не занимать. При заполненном Docker VM disk можно использовать отдельный host PGDATA, как в R4, без изменения пользовательских настроек и global prune.

Переиспользуется инфраструктура, каждый прогон проверяет актуальную сборку из своего неизменяемого снимка. Перед использованием достаточно целевой проверки готовности и совместимости необходимых настроек. Тестовые БД/роли/схемы и Redis namespace должны принадлежать этому исполнителю, не конфликтовать с параллельными задачами и возвращаться к требуемому исходному состоянию. Если тест требует fresh DB, пересоздаётся только его собственная БД, а не весь PostgreSQL/Redis/сеть. Проверку rollback, изоляции и restore нельзя подменять повторным использованием загрязнённого состояния.

Изменение migrations/grants/TLS/roles/images учитывается в подготовке затронутой части; несовместимый или неисправный стенд пересоздаётся. Производительность такого correctness-стенда не переносится на production. Контейнеры не удаляем после каждого успешного снимка: очищаем данные/лишние временные артефакты и явно сообщаем retained project и paths. Сохранение стенда по этому режиму не блокирует приёмку/коммит. При завершении серии проверок или просьбе пользователя Luna останавливает/удаляет только свои ресурсы; никаких глобальных prune. Новый механизм автоматического управления стендом и новые scripts для этого не нужны.

### Обратная доставка результата

В каждом задании Luna явно указывать основной чат, снимок, достаточный список проверок и требование отправить итог в основной чат инструментом `send_message_to_thread`. В процессе Auth пользователь разрешил такую обратную отправку; в другом проекте сначала должно быть разрешение на переписку. Старый начальный запрет помощнику писать в другие чаты уточнять этим разрешением в самом задании.

FAIL/BLOCKED отправлять с конкретной диагностикой и evidence; PASS — после сверки ожидаемых и фактически выполненных сценариев, exit statuses и очистки своих тестовых данных. Если стенд сохранён для следующих задач, это явно указывается в отчёте вместо ложного cleanup/teardown PASS. Exit0 без actual RUN/PASS, SKIP и отсутствие сообщения не подтверждают прохождение. Короткий финальный ответ в чате проверяющего не заменяет отправку в основной. Если инструмент отправки недоступен или вернул ошибку, явно записать сбой доставки и путь к отчёту; не утверждать, что сообщение отправлено.

Основной агент сверяет результат с неизменяемым снимком и оставшимися gates; разрешение пользователя на коммит проверяет отдельно. Уже принятые проверки при чтении отчёта не повторяются. После полного PASS и разрешённого коммита статус задачи обновляется; проверяющий не коммитит код самостоятельно.

## Если проверка нашла проблему

| Ситуация | Действие |
| --- | --- |
| Ошибка реализации | Помощник возвращает команду, воспроизведение и диагностику; основной агент исправляет причину и оценивает влияние |
| Недоступное окружение | Указать NOT RUN/ограничение, восстановить разрешённый стенд; не переписывать корректный код ради отсутствующего сервиса |
| Подозрение на нестабильный тест | Сохранить первый сбой, воспроизвести и разобрать; успешный повтор сам по себе не закрывает проблему |
| Ошибка безопасности или контракта | Остановить зависимую работу и устранить проблему до продолжения |
| Помощник не уверен | Вернуть вопрос и факты основному агенту, не угадывать результат |

По умолчанию помощник не исправляет код: это исключает конфликтующие правки. При отдельном поручении на исправление выделить ему собственный scope и checkout; после интеграции проверить итоговый код. Независимая проверка дополняет тесты, а не заменяет их.

## Когда добавлять инструмент

| Наблюдаемая проблема | Что рассмотреть |
| --- | --- |
| Нужные решения трудно найти в большом объёме документации | RAG с путями/версиями источников, обновлением изменённых документов и проверкой первоисточника перед критичной правкой |
| Требования теряются между разработчиками или агентами | OpenSpec или другой единый процесс спецификаций, заменяющий дублирующиеся планы |
| Регулярно повторяется ручное действие | Существующая команда runner/CI; затем минимальная автоматизация, если она приносит пользу |
| Найден измеренный bottleneck | Профили CPU/heap/SQL, benchmarks, сравнение до/после; PGO — при наличии представительной нагрузки |

RAG дополняет семантический поиск кода; релевантный фрагмент не доказывает полноту влияния изменения. Не индексировать реальные env, secrets, дампы и пользовательские данные. Историю явно отделять от актуальных контрактов. Дополнительный индекс должен оставаться актуальным и окупать своё обслуживание.

Не ставить несколько AI-клиентов, MCP или анализаторов с одинаковой функцией без конкретной потребности. Подключение нового инструмента и зависимостей согласовывать по правилам проекта. Плагин сам по себе не устраняет лишние чтения, проверки или архитектурную сложность.

## Как оценить пользу

На нескольких сопоставимых задачах сравнить время до проверенного результата, ожидание проверок, повторные чтения и прогоны, переделки и найденные после завершения ошибки. Токены и стоимость сравнивать только при доступных фактических измерениях, отдельно для всех агентов и суммарно. Отделять время команды от времени чтения и разбора её результата. Если поиск помощника регулярно приходится повторять целиком, сузить задание или отказаться от делегирования для такого типа задач. Критерий пользы — снижение затрат при сохранении корректности, читаемости и необходимых проверок.

Параллельность может уменьшить ожидание, а точная навигация — лишнее чтение. Процент ускорения заранее неизвестен. Проверки конкурируют за ресурсы и иногда эффективнее выполняются последовательно. Производительность разработки и RPS/память самого сервиса — разные показатели; второй подтверждается отдельными измерениями.

## Перенос в другой проект

Скопировать этот документ, связать с AGENTS.md и указать местные карту, текущую заметку, команды проверок и правила работы со стендом. Не переносить Auth-специфичные команды или обязательные инструменты в проект с другим стеком.

Минимальное правило для AGENTS.md:

```text
Работать небольшими законченными блоками с явными контрактами и проверками.
Искать определения и связи, затем читать нужный код; не перечитывать неизменившееся.
Сложный поиск делегировать ограниченно: получить карту источников и проверить нужные первоисточники.
Тесты выполнять обычным процессом; помощника привлекать для конкретной проверки.
Параллельно продолжать только независимую работу, проверяя отдельный снимок кода.
Сохранять команды, версию кода, exit status, диагностику и ограничения проверки.
Повторять затронутые проверки после правок; общие гарантии проверять шире.
Не ослаблять безопасность и качество ради скорости или экономии контекста.
Новые инструменты добавлять под наблюдаемую проблему, пользу подтверждать измерениями.
```

В этом репозитории набор обязательных проверок определён в [implementation](../planning/implementation.md#режим-проверок-после-уточнения-пользователя), навигация — в [карте](index.md). Этот документ их дополняет, не отменяет gates и не запускает отдельную задачу автоматически.

### Уточнение scope проверок — 4 ноября2026

Luna проверяет delta к последнему принятому immutable snapshot и связанные с ним гарантии. В каждой передаче основной агент указывает изменённые пути/контракты, достаточные команды и конкретные прежние PASS для переиспользования. Для правки тестового file path достаточно затронутого test/SQL scenario и package lint; для Markdown — diff/links/status. Не повторять production image, dependency scan, полный suite или другие SQL roots без изменения их входов/гарантий. Environment failure не превращать в code failure или PASS; явно указывать ограничение и выбирать безопасную собственную fixture без изменения проверяемого поведения.
