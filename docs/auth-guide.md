# Руководство по Auth: подключение, сценарии и API

Состояние на 11 октября 2026 года. Документ описывает текущую реализацию и отдельно — согласованные будущие возможности. Это руководство для интегратора и владельца проекта, не подтверждение готовности к production release.

**Как читать статусы:**

- **Реализовано** — есть backend и локальные проверки.
- **Опционально** — backend есть, но профиль нужно включить в ENV; выключенная ручка отсутствует.
- **Внутренний сервис** — есть Go-сценарий для доверенного caller, но нет публичной административной ручки.
- **Запланировано** — возможности пока нельзя вызвать через API.

Swagger описывает также выключенные опциональные профили. Наличие метода в Swagger не означает, что он подключён в запущенном экземпляре.

## 1. Возможности и ограничения

| Возможность | Сейчас | Существенная граница |
| --- | --- | --- |
| Самостоятельная регистрация email + пароль | Реализовано | Создаёт аккаунт и обычную сессию; email первоначально не подтверждён |
| Вход email + пароль | Реализовано | Неподтверждённый email не запрещает сам вход; чувствительные операции ограничены |
| Подтверждение email | Реализовано | Ссылка → форма → явный POST; не вход и не восстановление |
| Восстановление забытого пароля | Реализовано | По токену из письма; отзывает сессии, не снимает административную блокировку |
| Смена своего пароля | Реализовано | Сессия, подтверждённый email и старый пароль |
| Смена email с защитой прежнего владельца | Опционально | Password-профиль; четыре отдельных действия request/confirm/report/recover |
| Вход через Telegram OIDC | Опционально | Реальная проверка с credentials провайдера отложена до подключения UI |
| Создание нового аккаунта при Telegram-входе | Опционально | Отдельное разрешение; существующая привязка работает и без этого разрешения |
| Привязка Telegram к password-аккаунту | Опционально | Подтверждённый email, постоянный пароль, свежая password reauthentication |
| Отвязка Telegram от password-аккаунта | Опционально | Та же свежая проверка; остаётся постоянный пароль; все сессии отзываются |
| Отвязка последнего входа у Telegram-only пользователя | Не поддерживается | Сейчас нет альтернативного доказательства и сценария безопасного восстановления |
| Список и отзыв собственных сессий | Реализовано | Только свои сессии; нет административного списка всех пользователей |
| Внутреннее создание пользователя | Внутренний сервис | Само по себе не выдаёт пароль, сессию или роль |
| Приглашение и установка пароля | Опционально | Создание/перевыпуск внутри Go, активация через HTTP |
| Временный пароль | Опционально | Даёт только установку постоянного пароля, не доступ к продукту |
| Блокировка/удаление аккаунта | Внутренний сервис | Административный HTTP/UI ещё не опубликован |
| Пользовательские роли и permissions | Запланировано | Нет действующего публичного RBAC API |
| MFA: authenticator, recovery codes, телефон | Опциональный TOTP/recovery API | [A5.2b/c-local](features/mfa.md): login challenge, enrollment/step-up/management; external-only — opt-in email proof на уже verified owned contact. Первичная привязка контакта и SMS не реализованы |
| Вход по одноразовому email-коду | Опционально | Существующий active аккаунт с verified current password email; без регистрации и MFA |
| Google OIDC login/link/unlink | Опционально | Отдельный enabled/registration профиль, без auto-merge по email; live acceptance ещё открыта |
| Другие OAuth/OIDC providers | Не реализовано | Новый provider требует проверяемого adapter/контракта, не произвольного URL из ENV |
| Настройки и секреты через UI, первый super-admin | Запланировано | Сегодня конфигурация читается из ENV при запуске |
| Оплата, платные статусы, entitlement | Вне текущего релиза | Не нужны для использования существующей авторизации |
| SSO между независимыми сайтами/проектами | Не реализовано | Текущий host-only cookie не является универсальным межсайтовым SSO |

Есть локальные unit/HTTP/SQL/Redis/race проверки отдельных сценариев. Они не заменяют внешнюю SMTP/provider/browser-приёмку, аудит безопасности и нагрузочный тест всей системы. Измеренный production RPS сервиса пока не установлен.

## 2. Основные понятия

| Термин | Что означает в этом проекте |
| --- | --- |
| Аккаунт / user | Внутренний UUID пользователя, профиль, статус и версия авторизационных полномочий |
| Контакт email | Адрес и факт подтверждения владения им; один адрес сам по себе не означает способ входа |
| Credentials | Данные для проверки пароля: сервер хранит hash, не исходный пароль |
| Внешняя identity | Привязка `issuer + subject` к внутреннему UUID |
| Issuer | Кто выдал проверенное доказательство личности; Telegram: `https://oauth.telegram.org` |
| Subject | Устойчивый идентификатор пользователя у этого провайдера; не nickname и не email |
| Метод входа | Например, постоянный пароль, Google, Telegram или email OTP; метод доказывает личность |
| Сессия | Собственная серверная запись доступа после успешного входа |
| Session token | Случайный секрет в cookie, необходимый для предъявления сессии |
| Session ID | Публичный UUID сессии для списка/отзыва; не секрет и не замена cookie |
| Fresh authentication | Недавнее повторное доказательство пароля для чувствительного действия |
| MFA | Дополнительный фактор сверх основного входа; API включается MFA_ENABLED, primary login возвращает 202/challenge до подтверждения. Управление требует fresh password/MFA proofs |
| Роль / permission | Что пользователю разрешено делать после входа; не метод входа |
| Challenge token | Одноразовый секрет конкретного действия: verify/reset/invite и т. д. |
| Outbox | Очередь писем, записанная вместе с бизнес-изменением в SQL |
| auth_version | Версия полномочий аккаунта; старое доказательство не должно работать после её изменения |

### Один пользователь — несколько способов входа

Парольный вход и Telegram могут вести к **одному UUID**, если Telegram был явно привязан к существующему аккаунту. Они используют одну реализацию сессий, но каждый новый успешный вход обычно создаёт отдельную сессию. «Переиспользуем сессию» означает общий механизм, а не один неизменный cookie для всех входов.

Два независимо зарегистрированных аккаунта автоматически не объединяются. Одинаковый email во внешнем профиле не даёт право привязать его к существующему пользователю.

### OAuth, OIDC и Telegram

OAuth — механизм делегирования доступа; OIDC добавляет проверенное доказательство личности. В текущем Telegram-входе backend проверяет OIDC-ответ и затем выдаёт **свой** cookie. ID/access token провайдера не становится session token нашего API.

Это не Telegram Mini App `initData`, не вход по одному nickname и не произвольные присланные клиентом `telegram_id`. Такие отдельные способы в текущем API отсутствуют.

## 3. Подключение и общий контракт

### 3.1. Адреса

Пути API начинаются с `/api/v1/auth`. Адрес сервера зависит от вашего deployment.

В примерах:

- API: `https://auth.example.test`.
- Доверенный frontend: `https://app.example.test`.
- Это условные адреса, не работающий стенд.
- Для local development пример доверенного origin: `https://localhost:8443`.

`Origin` — только схема, host и при необходимости порт, **без пути**. Например, `https://localhost:8443`, а не `https://localhost:8443/verify-email`.

### 3.2. Что подготовить

1. PostgreSQL со схемой проекта и отдельной runtime-ролью для production.
2. Redis для распределённых лимитов и временного Telegram flow.
3. SMTP; Mailpit подходит только для локальной проверки.
4. Доверенный HTTPS frontend или HTTPS origin Swagger.
5. `AUTH_ALLOWED_ORIGINS` и секреты вашего окружения.
6. Для Telegram — отдельные Client ID, Client Secret и зарегистрированный HTTPS callback.
7. Frontend-страницы для ссылок из писем: их URL в ENV не создаёт эти страницы автоматически.

Dev Compose запускает внутренний API по HTTP на localhost:8080. Это не полноценная схема browser auth: для Secure-cookie и разрешённого Origin нужен настроенный HTTPS-вход через proxy либо прямой TLS сервера. Не убирайте Secure/Origin-проверку для обхода локальной настройки.

Команды проекта: `task --list`, `task dev:up`, `task dev:logs`, `task dev:ps`, `task migrate:up`. Подготовка ENV и production role/grants описана в [README](../README.md). Здесь команды приведены для ориентации, не выполняются автоматически.

### 3.3. Заголовки, JSON и cookie

Для JSON-запроса:

```http
Content-Type: application/json
Origin: https://app.example.test
```

HTTP проверяет один JSON value, неизвестные поля и максимальный размер тела 1 MiB. Неверный формат возвращает `400 invalid_json`. Предметные правила применяет service/domain, не нужно дублировать их в клиенте как доказательство серверной безопасности.

Все POST/DELETE auth-операции требуют **один точно разрешённый Origin**, даже если запрос отправлен через curl. Отсутствие или несоответствие → `403 invalid_origin`.

GET/HEAD без Origin допускаются для CLI; если Origin передан, он должен быть разрешён. Telegram callback выполняется как переход браузера от провайдера, а не как обычная JSON mutation с frontend.

После входа:

```http
Set-Cookie: __Host-session=<secret>; Path=/; Secure; HttpOnly; SameSite=Lax; Expires=<date>
```

- Cookie host-only: нет `Domain`, нельзя раздать его на все независимые проекты.
- JavaScript не должен читать или сохранять session token.
- Token не возвращается в JSON login/register.
- `Authorization: Bearer ...` не заменяет этот cookie.
- Клиент должен принять обновлённый cookie после reauthentication/rotation/продления.
- Auth-ответы имеют `Cache-Control: no-store`; секреты нельзя кешировать CDN.

### 3.4. Frontend и CORS

Same-origin frontend использует обычные cookies. Для доверенного другого origin в рамках same-site deployment нужен `AUTH_CORS_ENABLED=true`, allowlist и:

```javascript
await fetch("https://auth.example.test/api/v1/auth/me", {
  credentials: "include"
});
```

Браузер формирует Origin сам. Не пытайтесь подменять его в frontend JavaScript. При JSON POST может потребоваться preflight; backend разрешает GET/POST/DELETE и Content-Type.

Разрешённый CORS origin **не отменяет** SameSite/host-only ограничения cookie. Независимые cross-site домены требуют другой, отдельно спроектированной схемы; добавление домена в allowlist не создаёт SSO.

Origin-защита — не разрешение вызывать административную команду. Для будущего admin API нужны серверные permissions, MFA/fresh-auth и аудит.

### 3.5. Пример curl с сохранением cookie

Только для изолированного тестового пользователя:

```bash
curl --fail-with-body \
  --cookie-jar auth-cookies.txt \
  --header 'Origin: https://app.example.test' \
  --header 'Content-Type: application/json' \
  --data '{"email":"user@example.test","password":"ExamplePass1"}' \
  'https://auth.example.test/api/v1/auth/login/email'

curl --fail-with-body \
  --cookie auth-cookies.txt \
  --cookie-jar auth-cookies.txt \
  'https://auth.example.test/api/v1/auth/me'
```

Не используйте примерный пароль в production. Для реальных секретов предпочтителен защищённый ввод/клиент, чтобы они не оставались в shell history и process arguments. Cookie jar содержит секрет: храните его локально с ограниченным доступом, не коммитьте и не прикладывайте к обращению об ошибке. Проверку TLS не отключайте через `-k`.

Swagger включается отдельно и защищён **своим Basic Auth**. Его username/password не входят в аккаунт Auth и не назначают роль. Для защищённых пользовательских методов нужна обычная пользовательская cookie в браузере. Swagger должен открываться через разрешённый HTTPS origin.

<a id="password-flows"></a>
## 4. Пароль, email и восстановление

### 4.1. Регистрация → подтверждение → вход

1. Клиент отправляет email и пароль в register.
2. Backend создаёт аккаунт, контакт, password credentials, профиль, verification challenge, outbox и audit.
3. После commit создаётся сессия и возвращается `201` с `userID` и cookie.
4. Worker отправляет письмо на email.
5. Пользователь открывает frontend-страницу подтверждения.
6. После явного действия frontend отправляет token в email/verify.
7. Email становится подтверждённым; отдельная новая сессия не создаётся.

Сам вход разрешён до подтверждения. Это не означает доступ ко всем чувствительным операциям: например, change-password требует verified email. Для будущих продуктовых ручек нужно явно подключить их access-политику; существующий `/me` не является универсальным gate подтверждения.

Email нормализуется: trim + lowercase, ограничение длины 255 байт, без display name. Новые пользовательские пароли: 8–128 **байт**, минимум буква, цифра и заглавная буква. Это текущая policy, а не обещание, что любые пароли такой длины устойчивы к угадыванию. Unicode может занимать несколько байт.

Сессия выдаётся после регистрационной транзакции. Если создание сессии/ответ сломалось после commit, аккаунт уже может существовать. Повтор регистрации способен вернуть `409 email_already_exists`; не делайте бесконечный retry. Попробуйте обычный вход либо восстановление, не создавайте второй UUID.

### 4.2. Для чего EMAIL_VERIFICATION_URL

`https://localhost:8443/verify-email` — адрес **будущей frontend-страницы**, а не backend-ручка подтверждения. Текущие verification/reset ссылки передают токен в query `?token=...`; invitation/email-change используют fragment `#token=...`. Frontend должен разбирать формат своего сценария. Query token виден серверу страницы: исключите его из proxy/access logs и сторонних запросов.

GET страницы сам ничего не подтверждает. Это защищает от почтовых scanners и автоматического предпросмотра ссылок. Frontend должен извлечь токен, убрать его из адресной строки, показать действие и отправить POST. Не подключайте аналитику/сторонние ресурсы на странице с секретом; используйте no-store и no-referrer.

### 4.3. Повторное письмо

Resend возвращает одинаковое `202 accepted` для неизвестного, подтверждённого, заблокированного email и cooldown. Это скрывает существование аккаунта. Ответ не гарантирует ни наличие пользователя, ни отправку письма, ни доставку.

После допустимого перевыпуска действует новая ссылка; старая становится недействительной. Уже отправленное письмо физически отозвать невозможно.

### 4.4. Забыл пароль

1. Forgot принимает email и возвращает одинаковое `202 accepted`.
2. Если сценарий допустим, worker отправляет reset-ссылку.
3. Frontend показывает форму нового пароля; GET ничего не меняет.
4. Reset принимает token, newPassword и confirmPassword.
5. При успехе пароль заменяется, все сессии отзываются, cookie очищается.
6. Пользователь входит заново.

Один token действует один раз и только для своего purpose. Неверный, заменённый, истёкший, использованный или заблокированный reset не получает разных публичных объяснений: `invalid_reset`.

Reset **не подтверждает email**, не выдаёт сессию и не снимает административную блокировку. Он не создаёт постоянный пароль для Telegram-only аккаунта, у которого такого credentials ещё нет.

### 4.5. Хочу поменять пароль, старый знаю

Change-password требует действующую сессию, подтверждённый email, oldPassword, newPassword, confirmPassword. После успеха все сессии отзываются, включая текущую. Ответ исторически содержит `{"Status":"ok"}` с заглавной S; остальные status-ответы используют маленькую s.

Не путайте это с reauthentication: повторное доказательство пароля само пароль не меняет.

### 4.6. Смена email и защита старого владельца

Профиль включается `EMAIL_CHANGE_ENABLED=true`; иначе четыре ручки отсутствуют.

1. Password-пользователь с подтверждённым текущим email просит смену.
2. Он предъявляет текущий пароль либо заранее получает fresh-auth через reauthenticate/password.
3. Новый адрес получает письмо для подтверждения, старый — защитное уведомление.
4. До confirm login email остаётся прежним.
5. Confirm из письма нового адреса завершает смену и отзывает сессии.
6. Старый адрес сохраняет ограниченную по времени возможность сообщить «это не я».
7. Если report пришёл до confirm — pending-смена отменяется.
8. Если report пришёл после confirm — аккаунт защитно блокируется, на старый подтверждённый email ставится отдельное recovery-письмо.
9. Recovery требует **другой** токен и новый пароль: возвращает старый login email, меняет пароль, отзывает полномочия, возвращает active.
10. После recovery нужен новый вход.

Confirm/report/recover не требуют cookie того браузера, который открыл письмо. Но confirm проверяет, что **исходная сессия инициатора** всё ещё действительна. Rotation/reauthentication после request меняют verifier: старый intent уже не подтверждается. Выполните fresh-auth **до** request, затем не rotating его между request и confirm.

Report не делает автоматический «откат и вход», а recovery не является общим admin-unblock. Потеря старой почты, истёкший recovery или административная блокировка требуют отдельно согласованного восстановления; публичного bypass нет.

Если report отменил ещё не завершённую смену, это не означает, что украденный пароль заменён. Для этого владелец использует обычный reset.

### 4.7. Вход по email-коду

Это отдельный optional способ входа, не verification и не MFA. При `EMAIL_OTP_ENABLED=true` request отправляет восьмизначный код, confirm проверяет код и HttpOnly cookie того же браузера и выдаёт обычную SQL-сессию. По умолчанию код действует пять минут, допускает пять неверных попыток и используется один раз.

Текущий профиль работает только для существующего активного аккаунта с подтверждённым текущим email постоянных password credentials. Неизвестный адрес не регистрируется; ответ request остаётся `accepted`. External-only и pending/temporary-password аккаунты не получают этот способ входа автоматически. Контракт — [request](#post-api-v1-auth-email-otp-request), [confirm](#post-api-v1-auth-email-otp-confirm), [подробности](features/email-otp.md).

<a id="telegram-flows"></a>
## 5. Telegram и управление методами входа

### 5.1. Подготовка профиля

`TELEGRAM_LOGIN_ENABLED=false` по умолчанию. При включении нужны Client ID/Secret и HTTPS redirect URI с точным путём `/api/v1/auth/telegram/callback`, без query/fragment.

Client Secret — серверный секрет OIDC-клиента, **не Bot API token**. Не передавайте его в браузер, Swagger-запрос login пользователя, Git или логи. Внешняя приёмка с настоящими credentials ещё не проведена; настройка конкретного провайдера должна сопровождаться проверкой реального flow.

`TELEGRAM_REGISTRATION_ENABLED` — отдельный переключатель создания новых пользователей:

| Login enabled | Registration enabled | Поведение |
| --- | --- | --- |
| false | любое | Telegram routes не подключены |
| true | false | Может входить уже привязанная identity; неизвестная не создаёт аккаунт |
| true | true | Неизвестная проверенная identity может создать новый Telegram-only аккаунт |

Разрешение регистрации не требуется для явной привязки к уже существующему допустимому password-аккаунту.

### 5.2. Вход только через Telegram

1. Frontend вызывает POST telegram/start с разрешённым Origin.
2. Backend сохраняет краткоживущий flow в Redis и ставит `__Host-telegram-flow`.
3. Ответ содержит authorizationUrl; браузер переходит по нему к провайдеру.
4. После действия у провайдера браузер возвращается на callback с code и state.
5. Backend одноразово потребляет flow и проверяет binding, PKCE/OIDC-доказательство.
6. По `issuer + subject` ищется владелец.
7. Если identity новая и регистрация разрешена, создаётся один UUID.
8. Backend выдаёт обычную `__Host-session` и JSON `{"status":"ok"}`.

Callback сейчас возвращает JSON, не готовую красивую UI-страницу и не автоматический redirect на произвольный returnUrl.

Telegram-only аккаунт не получает email/password/роль автоматически. Недостаточно просто добавить email-контакт, чтобы считать парольный вход доступным. Самостоятельное добавление постоянного пароля/другого метода для такого аккаунта пока не реализовано.

### 5.3. Почему нет объединения по email

Устойчивый внешний ключ — проверенные issuer и subject. Email/username из чужого профиля не дают права входить в существующий local account. Это предотвращает опасное автоматическое связывание.

Если пользователь сначала создал отдельный Telegram-only аккаунт, а затем отдельный password-аккаунт, текущие методы не объединяют два UUID. Привязка уже занятой identity к другому owner вернёт conflict.

Блокировка или soft-delete не освобождает identity для тихого повторного создания. Новая попытка входа не воскрешает аккаунт.

### 5.4. Добавить Telegram к существующему password-аккаунту

1. Войти обычным паролем.
2. Подтвердить email; нужен постоянный, не временный пароль.
3. Вызвать reauthenticate/password и сохранить **новый** session cookie.
4. В пределах fresh-auth окна вызвать POST telegram/link.
5. Пройти тот же provider flow и callback.
6. Backend проверяет владельца, исходную сессию и свежесть доказательства ещё раз.
7. Telegram identity связывается с этим UUID.
8. Текущая сессия сохраняется; callback не создаёт вторую сессию и не заменяет её cookie.

Текущий default fresh-auth — 5 минут; сам Telegram flow тоже 5 минут. Это независимые сроки: flow может ещё существовать, а fresh-auth уже истечь. Тогда нужно начать заново.

Связь нельзя направить на присланный клиентом userID: owner берётся из аутентифицированной сессии. Проверка Telegram проходит только на backend.

У одного local user сейчас максимум одна identity одного issuer. Чужой owner или другая identity этого же issuer → `409 identity_conflict`. Повторное подтверждение уже той же связи может быть безопасным no-op, но одноразовый state повторно использовать нельзя.

### 5.5. Отвязать Telegram

Для текущего password-профиля:

1. Войти, иметь verified email и постоянный пароль.
2. Заново подтвердить пароль через reauthenticate/password.
3. Вызвать DELETE telegram/link.
4. Backend удалит связь, увеличит auth_version и отзовёт **все** сессии аккаунта.
5. Ответ 204, текущая cookie очищена.
6. Для нового входа использовать пароль.

Удаляется связь, не аккаунт Telegram и не local user. Если identity уже была **явно отвязана**, будущая разрешённая Telegram-регистрация может создать другой UUID. Это не восстановление прежней связи.

Повторный DELETE после успешного ответа не обязан снова давать 204: текущая сессия уже отозвана, а связи больше нет.

### 5.6. Если Telegram — единственный вход

Сейчас такой пользователь не может самостоятельно отвязать его:

- Для управления нужен fresh-auth постоянным паролем, которого у Telegram-only нет.
- Дополнительно SQL защищает от удаления последнего оставшегося входа.
- Ошибка может быть `fresh_auth_required` до проверки `last_login_method`; не ожидайте один код во всех случаях.
- Нет готовой ручки «сначала добавь пароль Telegram-only пользователю» или «принудительно отвяжи как admin».

Не стоит отключать защиту последнего входа ради UI-кнопки. Если бизнес требует принудительно закрыть доступ, это отдельный административный сценарий с полномочиями, аудитом и явным статусом пользователя.

### 5.7. Три разных действия: отвязка, выключение, блокировка

| Действие | Что меняет | Текущая доступность | Уже выданные сессии |
| --- | --- | --- | --- |
| Отвязать Telegram у одного user | Удаляет identity этого owner | DELETE для допустимого password-профиля | Отзываются все его сессии |
| Выключить Telegram для проекта | Убирает Telegram routes после перезапуска с ENV | TELEGRAM_LOGIN_ENABLED=false | Автоматически не отзываются |
| Запретить новую Telegram-регистрацию | Запрещает создание нового owner | TELEGRAM_REGISTRATION_ENABLED=false | Не затрагиваются; существующие связи продолжают входить |
| Заблокировать user | Закрывает доступ аккаунту независимо от метода | Внутренний status service; admin HTTP пока нет | Отзываются/не проходят текущий status/version |
| Принудительно удалить последний метод | Намеренно оставляет без входа | Не реализовано | Будущий сценарий должен явно определить отзыв и recovery |

Если правило бизнеса звучит «этот пользователь больше не должен иметь доступ», одного выключения Telegram недостаточно: у него уже может быть действительная сессия или пароль. Нужна блокировка/отзыв в зависимости от конкретного требования.

### 5.8. Flow, вкладки и повторы

Flow привязан к browser cookie, purpose (login/link), а link ещё и к owner/session verifier. TTL — 5 минут. State и code не являются многоразовыми credentials.

В одном браузере используется один flow cookie. Второй start/link заменяет binding, поэтому первый параллельный flow в другой вкладке может перестать проходить. Запускайте один Telegram flow за раз.

Отсутствующий/повторный state, неверная cookie, потерянный code, неправильное OIDC-доказательство → общий invalid_login. Для link потеря/смена исходной session cookie → fresh_auth_required. При ошибке после одноразового consumption безопаснее начать flow заново, а не повторять callback.

### 5.9. Вход и управление Google-привязкой

Google использует отдельный optional GOOGLE_LOGIN_ENABLED профиль; новые UUID разрешаются только GOOGLE_REGISTRATION_ENABLED. Настроить Web OAuth client/consent screen в Google Cloud Console и точный GOOGLE_OIDC_REDIRECT_URI. Это независимые от Telegram credentials/budgets, не новый тип сессии.

POST /api/v1/auth/google/start → authorizationUrl и HttpOnly __Host-google-flow → переход на Google → GET /api/v1/auth/google/callback?code=…&state=… → status=ok и обычная __Host-session. State/browser binding/PKCE/nonce single-use; tokens Google не возвращаются. Callback пока JSON, UI redirect будет позже.

Google аккаунт определяется canonical https://accounts.google.com + subject. Scope только openid, email/UserInfo не используются; неизвестная identity при разрешённой регистрации получает отдельный UUID без email/password credentials. Похожий email не объединяет пользователей.

Для привязки к существующему password-аккаунту: verified email, свежая reauthenticate/password, затем POST /google/link. Callback требует неизменённую исходную session. Link не выдаёт session/UUID. DELETE /google/link требует тот же свежий proof и оставшийся рабочий пароль; отзывает все sessions. Telegram identity при этом не удаляется.

Google-only/Telegram-only аккаунт пока не управляет методами без verified permanent password; две identity rows не заменяют usable-method/step-up checks. Реальный Google browser flow и faults ещё не проверены. Полный контракт, ошибки и ENV — [Google login](features/google-login.md).

<a id="sessions"></a>
## 6. Сессии и повторное подтверждение пароля

### 6.1. Где хранится доступ

PostgreSQL — источник действительности сессии. Redis остаётся важным, но не выдаёт разрешение вместо SQL при его отказе.

При проверке учитываются owner/status/deletion, auth_version, revocation, idle expiry и absolute expiry. Смена security-состояния не должна обходиться старой сессией.

На каждый защищённый запрос есть SQL-проверка. Продление условное, не безусловный UPDATE на каждом запросе. Это сознательный выбор корректности и немедленного отзыва, а не обещание отсутствия нагрузки на БД.

### 6.2. Три разных срока

| Настройка | Пример | Значение |
| --- | --- | --- |
| SESSION_TTL | 168h | Скользящий срок сессии; активность может продлевать его |
| ABSOLUTE_SESSION_TTL | 336h | Абсолютный предел; скользящее продление за него не выходит |
| SESSION_FRESH_AUTH_TTL | 5m | Срок повторного доказательства пароля, не срок обычного входа |
| SESSION_RETENTION_DAYS | 30 | Хранение завершённых записей перед cleanup, не срок доступа |

SESSION_REFRESH_THRESHOLD=24h — порог, около которого выполняется условное продление. Без использования сессия истекает; постоянная активность не отменяет абсолютного предела.

### 6.3. Fresh-auth и rotation

Reauthenticate/password проверяет текущий постоянный пароль и заменяет verifier сессии, устанавливая fresh marker. Возвращает validUntil и новый cookie. Это не новый пароль и не MFA.

Обычный password/Telegram login не следует считать готовым fresh-proof для управления identities: чувствительный сценарий требует явного reauthenticate.

Session/rotate меняет случайный секрет существующей сессии. Не продлевает fresh-auth и не превращает старую сессию в новую бессрочную. Старый verifier перестаёт работать; конкурирующие rotations должны сериализоваться на клиенте. Потеря ответа после успешной замены может потребовать повторного входа.

### 6.4. Свои устройства

GET sessions возвращает до 50 активных собственных записей. Следующую страницу запросите с `?before=<nextCursor>`. Нет offset/произвольного limit; secrets не возвращаются.

DELETE sessions/{id} отзывает одну свою сессию; UUID чужой сессии не даёт право на удаление. Если удаляется текущая, клиенту очищается cookie.

Logout — только текущая сессия. Logout-all — все текущие сессии этого owner. Это не блокировка пользователя: он может снова войти с допустимыми credentials.

<a id="provisioning"></a>
## 7. Ручное создание, приглашение и временный пароль

### 7.1. Создание оператором

Внутренний `App.Provisioning.Provision` принимает actor UUID, UUID idempotency key, optional email и Invite. Профиль включается INVITATIONS_ENABLED.

Без Invite создаётся pending account/profile и optional неподтверждённый контакт. С Invite нужен email и ставится приглашение. Ни роль, ни обычный пароль, ни сессия автоматически не выдаются.

Actor нужен для attribution. Он **не подтверждает полномочия** вызывающего. Сегодня это функция для доверенного Go caller, не безопасная публичная admin-ручка.

Повтор той же команды с тем же actor/key и нормализованными параметрами возвращает прежний UUID без повторной выдачи. Другие параметры с тем же ключом конфликтуют. Не заменяйте idempotency key новым на каждый сетевой retry.

### 7.2. Приглашение

Основной рекомендуемый операторский сценарий:

1. Доверенный backend создаёт пользователя и invitation.
2. Письмо ведёт на frontend activation page.
3. Пользователь задаёт постоянный пароль через invitations/activate.
4. В одной транзакции подтверждается приглашённый email, устанавливается пароль и активируется тот же UUID.
5. Сессия не создаётся: затем обычный login.

Просроченное приглашение можно перевыпустить через внутренний ReissueInvitation при допустимом состоянии и cooldown. Старые token/job становятся недействительны. Публичного POST создания/перевыпуска приглашений сейчас нет.

### 7.3. Временный пароль

Дополнительный выключенный профиль, а не обязательная часть обычной регистрации.

1. Доверенный backend вызывает `App.TemporaryPasswords.Provision`.
2. Сервис генерирует случайный временный пароль и отдаёт plaintext только при первом успешном вызове.
3. Оператор передаёт его по защищённому каналу; готового admin UI выдачи пока нет.
4. Пользователь вызывает temporary-password/login.
5. Получает только setup token со status=password_change_required, без обычной session cookie.
6. Отправляет setup token, новый пароль и подтверждение в temporary-password/complete.
7. Временные credentials/authority отзываются, постоянный пароль записывается.
8. Далее обычный login; email отдельно подтверждается.

Setup token разрешает только установку пароля. Он не заменяет session cookie и не даёт доступ к /me. Каждый новый успешный временный login заменяет прежний setup token.

Постоянный пароль должен отличаться от временного. Complete не подтверждает email, не выдаёт роль и не создаёт сессию.

Повтор provision не раскрывает plaintext снова. Потерянный результат выдачи требует отдельного Reissue с новым ключом команды и cooldown, не чтения старого пароля из базы. Plaintext исключён из автоматической JSON-сериализации, его нельзя просто вернуть будущим общим admin serializer.

### 7.4. Что пока нельзя сделать через Swagger

Нет опубликованных административных методов:

- создать пользователя или выдать временный пароль;
- перевыпустить приглашение/временный пароль;
- назначить/custom создать роли и permissions;
- заблокировать/разблокировать/удалить user;
- принудительно отвязать последний вход;
- установить первого super-admin.

Существуют некоторые внутренние Go-сценарии, но для HTTP ещё нужны административная модель доступа и защищённая выдача секретов. Ниже в справочнике нет выдуманных admin paths.

<a id="http-reference"></a>
## 8. Справочник HTTP-методов

Карточка метода содержит назначение, условия, тело, ответ, изменение полномочий и ошибки. Общие HTTP/Origin/admission ошибки также применяются даже там, где Swagger перечисляет только ошибки сценария.

В JSON используются условные UUID, даты и секреты. Значения `<token>`, `<setup-token>` и `<UUID>` заменяются реальными данными, полученными в соответствующем сценарии. Все поля тела в примере нужно передавать, кроме явно названных optional.

Успешные ответы 204 не содержат JSON. Поле status само по себе не является доказательством права доступа: в обычном login нужно также успешно принять cookie.

### 8.1. Регистрация по email

**POST `/api/v1/auth/register/email`**

Условия: Всегда подключено в текущем password-профиле. Сессия не требуется; Origin обязателен.

Тело запроса:

```json
{
  "email": "user@example.test",
  "password": "ExamplePass1"
}
```

Успех: **201**:

```json
{
  "userID": "<UUID>"
}
```

Поведение и ограничения: Создаёт account/contact/credential и verification intent. Устанавливает обычную session cookie. Письмо отправляет worker, не HTTP-запрос. Email занят → 409; неизвестный результат после commit не повторять бесконечно.

Ошибки сценария по текущему Swagger:

| HTTP | Код или категория |
| --- | --- |
| 400 | Коды: invalid_json, email_required, password_required, invalid_email, password_too_short, password_too_long, password_no_letter, password_no_digit, password_no_upper_letter |
| 403 | Код: invalid_origin |
| 409 | Код: email_already_exists |
| 429 | Код: rate_limited |
| 500 | Код: internal_error |
| 503 | Код: temporarily_unavailable |

### 8.2. Вход по постоянному паролю

**POST `/api/v1/auth/login/email`**

Условия: Без текущей сессии; Origin обязателен. Неподтверждённый email допускается.

Тело запроса:

```json
{
  "email": "user@example.test",
  "password": "ExamplePass1"
}
```

Успех: **200**:

```json
{
  "status": "ok"
}
```

Поведение и ограничения: Устанавливает session cookie. Неверные credentials дают 400, не 401. Blocked/deleted/pending или временные credentials не становятся обычным успешным входом. SQL выдача проверяет актуальную версию после password Compare.

Ошибки сценария по текущему Swagger:

| HTTP | Код или категория |
| --- | --- |
| 400 | Коды: invalid_json, email_required, password_required, invalid_email, invalid_credentials |
| 403 | Код: invalid_origin |
| 429 | Код: rate_limited; Retry-After: 60 |
| 500 | Код: internal_error |
| 503 | Код: temporarily_unavailable |

### 8.3. Запросить письмо подтверждения

**POST `/api/v1/auth/email/resend`**

Условия: Без сессии; Origin обязателен.

Тело запроса:

```json
{
  "email": "user@example.test"
}
```

Успех: **202**:

```json
{
  "status": "accepted"
}
```

Поведение и ограничения: 202 намеренно одинаков для разных состояний email. Cooldown не означает ошибку формата. Новая допустимая выдача заменяет старый token. Не подтверждает адрес и не выдаёт session.

Ошибки сценария по текущему Swagger:

| HTTP | Код или категория |
| --- | --- |
| 400 | Коды: invalid_json, invalid_email |
| 403 | Код: invalid_origin |
| 429 | Код: rate_limited |
| 503 | Код: temporarily_unavailable |

### 8.4. Подтвердить владение email

**POST `/api/v1/auth/email/verify`**

Условия: Без сессии; нужен токен именно verification; Origin обязателен.

Тело запроса:

```json
{
  "token": "<token>"
}
```

Успех: **200**:

```json
{
  "status": "ok"
}
```

Поведение и ограничения: Однократно подтверждает email. Не устанавливает пароль и не создаёт сессию. Истёкший/заменённый/повторный token имеет общий invalid_verification. GET почтовой ссылки ничего не подтверждает.

Ошибки сценария по текущему Swagger:

| HTTP | Код или категория |
| --- | --- |

| 409 | Конфликт identity / защита последнего метода |
| 429 | rate_limited |
| 503 | temporarily_unavailable |

Для Telegram локальный mapper использует: `400 invalid_login`, `403 fresh_auth_required`, `409 identity_conflict`/`last_login_method`, `429 rate_limited`, `503 temporarily_unavailable`. Отсутствующая/невалидная сессия на защищённой link-ручке → `401 unauthorized`; Origin → `403 invalid_origin`. Выключенный профиль обычно даёт router 404 без обещания JSON `method_disabled`.

### 8.30. Запросить одноразовый email-код

**POST `/api/v1/auth/email-otp/request`**

Optional профиль EMAIL_OTP_ENABLED=true. Сессия не нужна; разрешённый Origin обязателен.

```json
{"email":"user@example.test"}
```

Успех: 202 `{"status":"accepted"}`, cookie `__Host-email-otp` (Secure/HttpOnly/Lax/Path=/, без Domain) на время EMAIL_OTP_TTL. Сырой код не возвращается. Неизвестный/неподтверждённый/неактивный адрес получает тот же ответ, но без действующего login challenge/письма.

Поддержан текущий verified login email существующего active password-аккаунта. Нет скрытой регистрации, auto-link, смены пароля, verification или session issuance. Код приходит отдельным письмом, не ссылкой подтверждения.

Новая допустимая выдача заменяет прежний challenge пользователя и browser cookie. Повтор раньше resend-window получает 429 без замены действующей cookie. Браузер должен сохранить cookie; не вести несколько OTP flows одновременно.

| HTTP | Код |
| --- | --- |
| 400 | invalid_json / invalid_email |
| 403 | invalid_origin |
| 429 | rate_limited |
| 503 | temporarily_unavailable |

<a id="post-api-v1-auth-email-otp-confirm"></a>
### 8.31. Войти по email-коду

**POST `/api/v1/auth/email-otp/confirm`**

Нужны Origin и cookie того браузера, где сделан request. Code — строка ровно из восьми ASCII цифр; ведущие нули сохраняются.

```json
{"code":"01234567"}
```

Успех: 200 `{"status":"ok"}`, обычная session cookie; OTP cookie очищается. Не передавать email/userID — owner определяется challenge. При новом входе browser cookie заменяет прежнюю, но старая SQL-сессия автоматически не отзывается.

Code действует 5 минут по умолчанию, максимум пять неправильных попыток на challenge. После успешного consume/замены/expiry повтор даёт invalid_email_login. Consume+audit атомарны, затем обычная выдача SQL-сессии с актуальным status/version guard. Если следующий commit/ответ потерян, получить новый код; старый не восстанавливается.

Код не подтверждает неподтверждённый email, не создаёт нового user, не устанавливает password fresh marker, не является MFA и не выдаёт роли. Telegram-only/pending/temporary профиль этим способом сейчас не активируется.

| HTTP | Код |
| --- | --- |
| 400 | invalid_json / invalid_email_login |
| 403 | invalid_origin |
| 429 | rate_limited |
| 503 | temporarily_unavailable |

Для browser flow и правил хранения — [email OTP](features/email-otp.md).

### 8.32. Начать Google-вход

**POST `/api/v1/auth/google/start`**

Optional GOOGLE_LOGIN_ENABLED=true, разрешённый Origin, session не требуется. JSON body не нужен. Успех 200: `{"authorizationUrl":"https://accounts.google.com/o/oauth2/v2/auth?…"}` и Secure/HttpOnly Google flow cookie на 5 минут. Перейти по URL в том же браузере. Это ещё не session issuance.

Ошибки: 403 invalid_origin, 429 rate_limited, 503 temporarily_unavailable; disabled route отсутствует. Registration flag контролирует создание аккаунта в callback, не start.

### 8.33. Завершить Google-вход или привязку

**GET `/api/v1/auth/google/callback?code=<code>&state=<state>`**

Provider redirect. Нужны ровно один code/state и одна __Host-google-flow того же браузера. Body нет. Если flow был link — также неизменённая исходная __Host-session и действующий password fresh proof. Telegram cookie не заменяет Google cookie.

Успех 200 `{"status":"ok"}`: Google flow cookie очищена; login выдаёт обычную session, link сохраняет прежнюю и только добавляет identity. Provider tokens/UUID не возвращаются. Google issuer нормализуется к https://accounts.google.com, subject — opaque ID, не email.

Ошибки: 400 invalid_login, 403 fresh_auth_required, 409 identity_conflict, 429 rate_limited, 503 temporarily_unavailable. Повтор после consumption/потери ответа требует нового start/link; flow не восстанавливается. UI redirect ещё не реализован.

### 8.34. Привязать Google к своему аккаунту

**POST `/api/v1/auth/google/link`**

Нужны Origin, session, verified email с постоянным паролем и свежая reauthenticate/password. Body/target user ID нет. Успех 200 authorizationUrl и Google flow cookie. Это только начало; привязка коммитится после callback/proof/current SQL checks. GOOGLE_REGISTRATION_ENABLED для linking не нужен.

Ошибки: 401 session, 403 invalid_origin/fresh_auth_required, 429 rate_limited, 503 temporarily_unavailable. Google-only/Telegram-only account без password proof этот API не использует.

### 8.35. Отвязать Google

**DELETE `/api/v1/auth/google/link`**

Те же session/Origin/fresh требования; остаётся verified permanent password login. Body нет. Успех 204: удаляется только Google identity, auth_version увеличивается, все sessions отзываются, caller session cookie очищается. Telegram identity не удаляется; потребуется новый вход.

Ошибки: 400 invalid_login, 401 session, 403 invalid_origin/fresh_auth_required, 409 last_login_method, 429 rate_limited, 503 temporarily_unavailable. Число других identity rows не является usable-method proof. Полные гарантии/ENV — [Google login](features/google-login.md).

## 9. Настройки ENV

Сейчас ENV читаются при startup. Изменения требуют согласованного перезапуска экземпляров, это ещё не runtime UI settings. Показанные значения — текущие defaults либо **локальные примеры** из .env.example, не рекомендуемые production secrets.

Не нужно включать все профили. Минимальное приложение может использовать только пароль/verification/sessions; Telegram, Google, email OTP, invitation, temporary password и email change подключаются по необходимости.

### 9.1. Процесс, HTTPS, Origin и Swagger

| Переменная | Пример/default | Для чего |
| --- | --- | --- |
| APP_NAME | auth-dev | Идентификатор Compose/project; у нового проекта свой |
| APP_ENV | dev / test / prod | Профиль приложения; dev mail route только dev |
| PORT | 8080 | Внутренний порт HTTP-сервера |
| HTTP_TLS_CERT_FILE | пусто | Путь TLS-сертификата при прямом HTTPS |
| HTTP_TLS_KEY_FILE | пусто | Путь private key; задавать вместе с сертификатом |
| AUTH_ALLOWED_ORIGINS | https://localhost:8443 | Точные HTTPS origins без path, список через запятую |
| AUTH_CORS_ENABLED | false | Credentialed CORS для доверенного frontend |
| HTTP_TRUSTED_PROXY_CIDRS | пусто | CIDR только своих reverse proxies; иначе forwarded IP не доверяется |
| LOG_LEVEL | debug в dev-примере | Уровень логирования; не включать секреты в logs |
| SWAGGER_ENABLED | false в runtime; true в dev-примере | Подключение /swagger и /swagger/* |
| SWAGGER_USERNAME | собственное значение | Basic Auth для документации, не local user |
| SWAGGER_PASSWORD | отдельный секрет | В production при включении минимум 16 символов |

За TLS ingress можно оставить API HTTP только в закрытой доверенной сети. Прямой обход proxy нужно исключить. Cookie Secure требует HTTPS на browser-facing адресе.

### 9.2. HTTP, hashing и распределённые бюджеты

| Переменная | Default | Область |
| --- | --- | --- |
| HTTP_MAX_IN_FLIGHT | 128 | Одновременно исполняемые обработчики одного процесса |
| HTTP_REQUEST_TIMEOUT | 10s | Контекст HTTP-запроса, не очередь для бесконечного ожидания |
| PASSWORD_HASH_CONCURRENCY | 2 | Общие параллельные hash/compare одного процесса |
| LOGIN_IP_LIMIT | 30 | Попытки login с одного IP за минутное окно |
| LOGIN_EMAIL_LIMIT | 10 | Попытки login для одного email за минутное окно |
| LOGIN_GLOBAL_LIMIT | 1000 | Общие попытки login проекта за минутное окно |
| REGISTER_IP_LIMIT | 5 | Регистрационные попытки с IP за минуту |
| REGISTER_GLOBAL_LIMIT | 100 | Общие регистрационные попытки проекта за минуту |
| PASSWORD_RESET_GLOBAL_LIMIT | 100 | Общие попытки reset + защитного recovery проекта за минуту |

Глобальный означает несколько API одного проекта с общими Redis и scoped operational key, **не все ваши независимые проекты**. Лимиты попыток не равны числу одновременных пользователей или максимальному RPS. Не увеличивайте их без оценки CPU/RAM, abuse и пропускной способности БД.

Например, PASSWORD_RESET_GLOBAL_LIMIT=100 ограничивает попытки **операции reset/recovery** в минуту. Это не «сервис выдерживает всего 100 запросов» и не пожизненный лимит. Обычные /me, Telegram и другие действия имеют свои условия/бюджеты.

### 9.3. Сессии

| Переменная | Default | Для чего |
| --- | --- | --- |
| SESSION_TTL | 168h | Скользящий срок, 7 дней |
| ABSOLUTE_SESSION_TTL | 336h | Абсолютный предел, 14 дней |
| SESSION_REFRESH_THRESHOLD | 24h | Порог условного продления |
| SESSION_FRESH_AUTH_TTL | 5m | Свежесть повторного доказательства пароля; допустимо 1m–15m |

Absolute TTL не меньше Session TTL; threshold положительный и меньше Session TTL. Эти сроки не совпадают с retention.

### 9.4. Почта и общие секреты

| Переменная | Пример | Для чего |
| --- | --- | --- |
| SMTP_HOST | mailpit в dev | SMTP host; для production реальный провайдер |
| SMTP_PORT | 1025 в dev | Порт соответствующего SMTP сервиса |
| SMTP_USERNAME | пусто в dev | Учётная запись провайдера, если требуется |
| SMTP_PASSWORD | секрет | SMTP credential; не пароль local user |
| SMTP_FROM | auth@example.com | Адрес отправителя |
| SMTP_DOMAIN | example.com | SMTP domain |
| SMTP_REQUIRE_TLS | false в dev / true в prod | Обязательный проверяемый STARTTLS для production |
| EMAIL_OUTBOX_KEY | отдельный base64 secret | 32 случайных байта для AES-GCM и scoped operational mechanisms |

EMAIL_OUTBOX_KEY нужен не только verification. Он используется существующими очередями/лимитерами/Telegram flow с разными purpose. Не переносите локальный example key в новый production проект.

Keyring/плавная ротация нескольких operational keys пока не реализованы. Не меняйте ключ отдельно на одной реплике: можно сломать расшифровку очередей, flow и согласованность лимитов. Плановую смену проводить согласованно после остановки новой выдачи и обработки outbox; аварийная смена требует принятия потери старых flow/payload и повторной выдачи.

Пароли пользователей хешируются отдельно; outbox encryption key не является ключом для «расшифровки пользовательского пароля».

| ACCOUNT_EMAIL_RESERVATION_DAYS | 30 | Срок резервирования email удалённого аккаунта по lifecycle policy |
| RETENTION_BATCH_SIZE | 100 | Максимум кандидатов одной cleanup операции; 1–1000 |
| RETENTION_INTERVAL | 1m | Интервал одного ограниченного прохода; 1s–1h |

Доступ заканчивается при revoke/expiry/status transition, а не через 30 дней retention. SQL-запись может храниться ещё для истории.

180 дней audit — не требование закона и не универсальное значение. Для конкретного продукта срок согласуется с безопасностью и требованиями хранения данных. Сокращение retention — намеренная потеря истории.

Email reservation — не удаление всего аккаунта и не гарантированный полный PII erasure. Для пользователя, заблокированного до удаления, действует дополнительная защита от автоматического освобождения; подробнее [account deletion](features/account-deletion.md). Identity reservation не следует считать тем же правилом, что освобождение email.

### 9.11. PostgreSQL, Redis и Compose

| Переменная | Пример | Для чего |
| --- | --- | --- |
| DATABASE_URL | ваш postgres DSN | Runtime connection; production без owner/superuser прав |
| MAX_CONNS | 10 | Максимум SQL connections каждого процесса |
| MIN_CONNS | 2 | Минимальный размер pool |
| MAX_CONN_LIFETIME | 10m | Возраст connection |
| MAX_CONN_IDLE_TIME | 5m | Время idle connection |
| REDIS_HOST | redis | Redis host |
| REDIS_PORT | 6379 | Redis port |
| REDIS_PASSWORD | отдельный secret | В production минимум 16 символов |
| POSTGRES_IMAGE | postgres:18.6-bookworm | Версия образа в текущем Compose-примере |
| POSTGRES_DB | auth | Имя базы в Compose |
| POSTGRES_USER | ваш owner | Bootstrap/migration owner; не production runtime role |
| POSTGRES_PASSWORD | отдельный secret | Пароль owner |
| POSTGRES_PORT | 5432 | Локальный опубликованный dev port |
| MIGRATION_DATABASE_URL | ваш migration DSN | Owner connection для миграций; search_path=public |
| BACKUP_INTERVAL | 24h | Интервал backup сервиса |
| BACKUP_RETENTION_COUNT | 7 | Число backup archives; не дни и не audit retention |
| RESTORE_HEALTHCHECK_SQL | SELECT count(*) FROM auth.users; | Проверка после restore; не HTTP readiness |

Pool каждого процесса ограничен. Несколько API дают общий бюджет примерно N × MAX_CONNS плюс отдельные operator/migration connections. Не увеличивайте pool без измерений; больше connections не всегда означает больше throughput.

Redis используется шире, чем просто «cache»: лимиты и encrypted transient flow. Сейчас нет SQL fallback, отключающего защиту, если Redis unavailable. При независимых проектах нужны собственные operational keys и isolation данных.

Backup содержит PII и password hashes. Нужны ограниченный доступ, внешняя зашифрованная копия и restore drills. Restore рабочей базы — отдельная разрушительная операция, а не средство исправления пароля администратора.

## 10. Ошибки, повторы и эксплуатация

### 10.1. Общий формат ошибок

```json
{
  "code": "temporarily_unavailable",
  "message": "temporarily unavailable"
}
```

Клиент принимает решение по HTTP status + code, не по свободному тексту message. Публичная ошибка не содержит SQL/Redis/SMTP details, token, hash или secret.

| Status / code | Значение | Реакция клиента |
| --- | --- | --- |
| 400 invalid_json | Не тот Content-Type/JSON/поля/размер | Исправить запрос; не повторять автоматически |
| 400 invalid_credentials | Обычный login не принят | Предложить проверить credentials/recovery, не раскрывать account status |
| 400 invalid_verification / invalid_reset / invalid_login | Доказательство недействительно | Получить новое допустимое доказательство/flow |
| 401 unauthorized | Нет допустимой сессии | Новый login; не бесконечный refresh |
| 401 или 403 fresh_auth_required | Нужна свежая проверка; status зависит от метода | Выполнить reauthenticate и начать действие заново |
| 403 invalid_origin | Не тот/отсутствующий Origin | Исправить deployment/allowlist; cookie это не исправляет |
| 403 email_not_verified | Чувствительный сценарий требует verified email | Завершить verification |
| 404 | Не подключён optional route или не найдена допустимая цель | Проверить профиль/путь/ownership; не обещать JSON для router 404 |
| 409 identity_conflict | Внешняя identity уже занята/ограничение issuer | Не выполнять авто-merge |
| 409 last_login_method | Нельзя безопасно убрать последний вход | Нужна допустимая альтернатива; сегодня Telegram-only management отсутствует |
| 409 email_already_exists | Email регистрации занят | Login/recovery, а не второй UUID |
| 429 rate_limited | Исчерпан защитный budget | Учитывать Retry-After; избегать tight retry loop |
| 500 internal_error | Неожиданная внутренняя ошибка | Зафиксировать безопасные диагностики; состояние commit может быть неизвестно |
| 503 temporarily_unavailable | Зависимость недоступна или ресурсный budget занят | Ограниченный retry с backoff/jitter; сначала учитывать одноразовость действия |

HTTP admission при перегрузке даёт 503 и Retry-After: 1. Distributed quotas обычно дают 429 и Retry-After: 60. Для срока реального повторного действия дополнительно учитываются cooldown/state и истечение токена.

Liveness исключена из обычного admission slot; readiness не должна постоянно создавать новые тяжёлые probes. Защита HTTP handlers не заменяет connection limits/slow-client защиту ingress.

### 10.2. Что безопасно повторять

| Действие | Ограничение повтора |
| --- | --- |
| GET /me, GET /sessions | Можно повторить после краткого сбоя; данные могут измениться |
| Register | Не общий idempotent API; после commit UUID уже мог появиться |
| Forgot/resend | Generic acceptance, cooldown/limits; не слать в цикле |
| Verify/reset/activate/complete/confirm/report/recover | Одноразовый token; повтор после успеха может дать invalid_* |
| Telegram callback | State одноразовый; после сбоя обычно новый flow |
| Reauthenticate/rotate | Меняют verifier; потерянный cookie может требовать login |
| Logout/unlink | Сессия после успеха уже отозвана; повтор может дать unauthorized |
| Внутренний operator Provision/Reissue | Использовать тот же UUID idempotency key для той же команды, без повторного раскрытия секрета |

После timeout нельзя всегда определить из клиентского ответа, был ли commit. UI должен учитывать это и не повторять опасное действие новым случайным ключом.

### 10.3. Доставка письма и частичные сбои

Письмо отправляется после commit через outbox, без удержания SQL transaction во время SMTP. Это обеспечивает согласованную постановку, но **не exactly-once delivery**.

Есть leases/SKIP LOCKED, deadline SMTP и ограниченные повторы: до пяти попыток с backoff 30/60/120/240 секунд. После crash/неоднозначного ответа возможно повторное письмо. Старое взятое worker письмо может уйти после перевыпуска, но старый token уже недействителен.

202 не означает «письмо доставлено». Проверять нужно очередь/возраст job/ошибки SMTP, доменную настройку отправителя и реальное получение. Полноценные metrics/alerts и внешняя SMTP-приёмка ещё относятся к release tasks.

### 10.4. Оптимизация и честная оценка нагрузки

Уже заложены:

- ограниченные HTTP in-flight и crypto concurrency;
- распределённые Redis budgets;
- условный session refresh вместо записи на каждый запрос;
- индексные lookup/cleanup и ограниченные batches;
- worker deadlines/leases, без бесконечного drain;
- SQL transaction checks против stale credentials и races.

Это не гарантия «любое количество пользователей». Общий API RPS ещё не измерен. В [performance](operations/performance.md) есть локальный SQL-only результат около 10 тысяч session reads/s, но он не включает HTTP/TLS/Redis/Argon2/SMTP и не является RPS приложения.

Для финальной оценки нужен смешанный multi-instance тест с выбранными login/read/mutation пропорциями, P95/P99, CPU/RAM, DB acquire/locks/IO, Redis latency, ошибками, outbox backlog и долгим steady-state прогоном.

GC/heap/goroutine/connection leak проверки под длительной нагрузкой входят в финальную приёмку. Не утверждаем отсутствие утечек только потому, что unit tests зелёные.

### 10.5. Развёртывание и обновление

- Использовать согласованные версии Go из go.mod и зависимости из go.sum, не произвольное @latest.
- Обновления crypto/provider library проверять отдельно вместе со старыми hashes/flows и resource bounds.
- Миграция 000001 в текущей pre-release разработке расширялась на месте.
- Уже применённая 000001 не обновится от простого migrate up; для существующей базы нужен отдельный согласованный перенос.
- Не делать down/reset рабочей БД и не удалять volume ради добавления новых колонок или восстановления admin.
- Production release требует финальных security/provider/browser/load/restore проверок из плана; этот Markdown не заменяет их.

## 11. Будущие настройки, роли, MFA и UI

В этом разделе описано **направление плана**, не действующий HTTP-контракт. Имена будущих routes/ENV намеренно не придуманы.

### 11.1. Выбор методов для проекта

Нужна отдельная сохраняемая политика:

- доступен ли password login;
- разрешена ли самостоятельная регистрация;
- требуется ли email verification и в какой момент;
- включён ли Telegram/выбранный OIDC/email OTP;
- можно ли новым внешним пользователям создавать аккаунт;
- какой MFA требуется для пользователя/роли/чувствительного действия.

Примеры будущих профилей:

| Профиль продукта | Планируемая политика |
| --- | --- |
| Обычный сайт | Пароль и/или внешний provider, public registration по выбору |
| Сайт с обязательной почтой | Password + verification, ограничение доступа до подтверждения |
| Закрытая админка | Operator provisioning/invitations, public registration off, роли, MFA |
| Telegram-oriented проект | Telegram login, явные правила добавления альтернативы/recovery |

Перед выключением метода нужно учитывать существующих пользователей с единственным способом входа. UI должен объяснять последствия, а backend — применять политику, не просто скрывать кнопку.

### 11.2. Роли и permissions

Пользовательская роль объединяет permissions. Можно будет создать свою роль и вручную назначить её пользователю. Название роли не должно подменять серверную проверку конкретных полномочий.

Планируется защищённый admin API для управления пользователями, приглашениями, временными паролями, ролями и permissions, с audit/fresh-auth/MFA. Административные permissions отличаются от публичных user methods этого руководства.

Последний активный super-admin должен быть защищён от случайного удаления/лишения доступа. Роль «оплатил» не нужна текущему auth релизу; финансовые статусы отложены.

### 11.3. Первый запуск и восстановление администратора

После появления UI первый запуск должен позволить один раз создать первого super-admin. При уже завершённой инициализации повторный посетитель не должен захватить admin через setup page. Конкурентные попытки setup должны обрабатываться атомарно.

Обычный забытый пароль — через email recovery, если применима настроенная политика. Для потери почты/второго фактора нужен отдельный контролируемый break-glass процесс без сброса базы: права operator, короткое полномочие, audit и отзыв сессий. Конкретный script/ENV ещё не реализован; постоянного публичного «admin password override» сейчас нет.

### 11.4. MFA

Authenticator — приложение с TOTP-кодами (например, Google Authenticator), а не «вход через Gmail». Gmail/Google account как provider — отдельный OIDC login.

План включает второй фактор и recovery codes. Телефонный/SMS/voice вариант требует выбора провайдера, затрат, защиты от SIM swap/abuse и recovery policy; нельзя объявить его готовым без этого.

Repeat password/fresh-auth не равен MFA. Включение MFA должно затрагивать issuance сессии и чувствительные операции на backend, а не только страницу с вводом кода.

### 11.5. UI и секреты

UI — финальная функциональная часть после защищённых backend-контрактов. Секреты провайдеров/SMTP должны задаваться admin, маскироваться, храниться и изменяться безопасно; read API не должен возвращать исходный secret обычному пользователю.

Сейчас ENV не является готовым хранилищем runtime settings. Перенос в UI требует отдельного lifecycle, validation, разрешений и согласованного поведения реплик. Нельзя считать это простым frontend поверх всех ENV без дополнительных правил.

### 11.6. Что сознательно не добавляем

В текущий scope не включаются billing/entitlement, межпроектный SSO, Telegram Stars/Mini Apps, passkeys и универсальная интеграционная платформа. Необходимые точки расширения не означают, что все возможные технологии уже реализованы.

## 12. Частые вопросы и источники

### Если просто перейти по ссылке из email, пароль/email сразу изменится?

Нет. Открывается frontend-страница. Действие — только после соответствующего явного POST. Verification, reset, email change и protective recovery имеют разные tokens и методы.

Telegram callback — исключение по типу flow: это серверное завершение уже начатого provider login/link с state/binding, не почтовая ссылка подтверждения.

### Можно ли подтвердить email reset-токеном?

Нет. Verification/reset/invitation/change/report/recovery/setup tokens имеют разные purpose и не взаимозаменяемы.

### Я выключил Telegram. Пользователь сразу выйдет?

Нет. Routes исчезнут после перезапуска с новым ENV, но уже выданная общая SQL-сессия сама не отзывается. Для немедленного запрета доступа нужен соответствующий lifecycle/отзыв; готовой публичной admin ручки пока нет.

### Можно отвязать Telegram, если это единственный способ?

В текущем self-service нельзя. Есть password fresh-auth и защита последнего метода. Принудительное административное отключение — отдельная будущая политика, не обход этой защиты.

### Роль admin появляется при Telegram-входе или invitation activation?

Нет. Метод входа подтверждает identity, но не назначает полномочия. Реализованного публичного назначения ролей пока нет.

### Можно сделать сервис общим для нескольких независимых проектов?

Как переиспользуемый шаблон — да, после адаптации и release-проверок. Как уже готовый общий multi-tenant SSO с единым cookie на любых доменах — нет.

Каждому независимому проекту нужны свои operational secrets, trusted URLs и изоляция данных. Ресурсные limits/TTL настраиваются под продукт; готовность определяется нагрузочными и security измерениями.

### Что прислать при ошибке?

Method/path, timestamp и timezone, HTTP status/code, безопасный request ID если есть, профиль/включённость функции и ожидаемую последовательность.

Не присылать полный Cookie/Set-Cookie, пароль, session/challenge tokens, Client Secret, SMTP password, реальные .env или дампы. Query callback и почтовая ссылка тоже могут содержать секреты: очистить значения перед диагностикой.
